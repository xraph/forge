## Merge 1 — `fefe2b7e`, the envelope / root-type fix

The branch was cut before chunk 5 reshaped the write path, so both of its `cache.ts`
hunks arrived carrying the pre-chunk-5 shape (`store.write` + a two-argument `settle`)
around a one-token improvement (`rootTypeOf` instead of `meta.entity`). Taking either
hunk wholesale would have deleted the ordering guarantee — which is the exact failure
mode this recovery exists to undo, reintroduced by hand.

### Hunk A — `mutate()`, the mutation write

Kept HEAD entirely; changed one argument.

```
store.stage(response, this.entities, meta.entity)
     ->  store.stage(response, this.entities, rootTypeOf(meta))
```

Retained verbatim: `racedSince(staged.records.keys(), dispatchedAt)`, the
`commit(staged, {skip})`, the **never-re-issue** rationale (a query that loses the race
is re-read for free; re-issuing a write is the duplicate-orders hazard, so the response
commits *around* the frames instead), and the `buried` branch.

The `buried` behaviour is preserved exactly, because it is doing two things and only one
of them is obvious. A raced key the store no longer holds means the frame that won was a
delete, so `store.read(staged.skeleton)` would resolve the mutation's own entity to
nothing — `undefined` for a scalar root, a silently dropped element for an array root.
That value is bad as a return value and worse as an input to placement: `[created,
...current]` becomes `[undefined, {...}]`, `adopt` re-normalizes it, and a literal
`undefined` is deliberately not a hole, so it survives into the rendered value. The
second reason is the load-bearing one — `adopt` re-normalizes a placement's return
straight back into the store with no frame stamp and no skip, so **placing the response
would resurrect the deleted entity**. Declining costs nothing: `undefined` from placement
already means "refetch instead", and the eviction frame synthesized `${entity}[]` on the
way through, so those lists are already queued.

### Hunk B — `settle()`

Kept HEAD's `settle(record, response, staged, skip?)` and its `commit`. The incoming
side's `store.write(response, entities, rootTypeOf(record.meta))` was **not** taken here,
because under chunk 5 the query path no longer normalizes in `settle` — it normalizes one
level up, in the request sequence, before the frame race can be judged. So the incoming
side's real contribution was moved to where the walk actually happens:

```
// in start()'s sequence, HEAD-only territory, no conflict marker to warn me
store.stage(response, this.entities, record.meta.entity)
     ->  store.stage(response, this.entities, rootTypeOf(record.meta))
```

That line is the one a marker-driven resolution would have missed. Verified by mutation:
reverting just it fails three tests (`shares a record between a paginated list and a
single read`, `normalizes a mutation response into the shared store`, and the new tags
test) and nothing else.

`adopt()` keeps `meta.entity`, as the branch intended and commented — a `Placement`
returns `unknown[]`, a list of records the application built, not a response document.
Handing it the root type would walk each element as though it were the envelope.

### A semantic conflict git could not see

`fefe2b7e` makes `EntityMeta.idField` optional — that is *what lets an envelope have a
row in the entities table at all*, so it is not incidental. `live.ts` arrived after the
branch was cut and indexed the payload with it unguarded:

```ts
const id = (payload as Record<string, unknown>)[meta.idField];   // TS2538 after the merge
```

Two files, neither in conflict, both correct on their own side. A delete frame naming an
envelope typename would have read a literal `"undefined"` property and evicted under
whatever it found. `identify()` now declines a type with no identity, matching the guard
`normalize.ts` already had. This is the only thing the merge broke that the conflict
markers did not point at, and `tsc --noEmit` is what caught it — `vitest` was green.

### New test

`__tests__/envelope.test.ts` → `records the entities inside a page as deps and tags`.
The branch's own tests prove an envelope *normalizes*; they do not prove it gets **cache
tags**, and `provides` alone would hand the query `Order[]` whatever the response did,
because that tag is static. The per-id tags and the dep set are derived from the entities
the walk lifted out, so an envelope normalizing to nothing settled with an empty dep set
and no `Order:o-1` — present in cache, reachable by no invalidation, serving a stale page
forever. The test settles through `stage`/`commit`, which is the combination neither
branch tested.

## Merge 2 — `037255f4`, the in-flight settle

Three hunks, all the same cause: chunk 5 had already reshaped `settle` for a different
race, and this branch reshapes it for a second one.

### The two stamping mechanisms are NOT the same. Both are kept.

This was the question worth getting right, because they are near-identical in shape —
read a monotonic reading before dispatch, compare it on arrival — and collapsing them
would look like a tidy deduplication.

| | `dispatchedAt` (chunk 5) | `startedAt` (this branch) |
| --- | --- | --- |
| clock | `store.frameVersion` | `registry.stamp` (the invalidation clock) |
| advanced by | stream frames, via `applyFrames` | `invalidated(tags)`, from mutations |
| question | did a frame overtake this response for an entity it carries? | was this query invalidated while its request was out? |
| granularity | per entity key | per query |
| remedy | commit around the raced keys (`{skip}`), or restart under the bound | settle as stale, so the next mount refetches |

A stream frame raises no tags, and a mutation bumps no frame version. So a response can
lose either race independently, or both, and neither clock can answer the other's
question. They are two mechanisms. Applying only one would have left the
prefetch-then-mutate case serving pre-write data exactly as before — which is what the
mutation test below confirms.

They meet in exactly one place, `settle`, where the entities commit around the frames and
the query settles stale if a tag it carries moved. Both readings are now taken per
attempt in `start()`, with the distinction stated at the read site rather than left to be
inferred by the next person to touch it.

### Resolutions

- **`start()`, the readings.** Kept both. Both are read per attempt rather than per
  sequence, which the branch argues for on its own terms (a restart issues a genuinely
  new request; settling it against the abandoned attempt's reading reports the fresh
  answer as behind the very invalidation it was sent to satisfy). Chunk 5's frame-restart
  `continue` also re-enters the loop and re-issues, so per-attempt is right for
  `dispatchedAt` too.
- **The `settle` call site.** `settle(record, response, staged, startedAt, raced.length > 0 ? new Set(raced) : undefined)`.
- **`settle`'s signature.** `(record, response, staged, startedAt, skip?)` — chunk 5's
  staged commit *and* this branch's stamp. The incoming side's
  `store.write(..., record.meta.entity)` is dropped twice over: the walk moved up into
  the sequence in chunk 5, and onto the root type in the previous merge.

`registry.ts` merged clean, including `get stamp()`, `SettleResult.startedAt`,
`entry.settledAt = result.startedAt ?? this.clock`, and the re-ask of `invalidatedSince`
after `retag`.

### Verified by mutation, on the merged tree

Reverting `entry.settledAt` to the arrival reading fails exactly three tests — the
branch's two prefetch tests and its registry dispatch-stamp test — and nothing else. So
the fix is live *on top of* the staging machinery, not merely compiling beside it. That
is the combination nobody had run before this branch.

## A third thing was lost, and it is the one with no deleted file to notice

`git diff --diff-filter=D --name-only origin/main main` lists **71 deletions** on the bad
local `main`, which is a wider set than the two chunks named in the brief:

- the stream/live runtime — `src/live.ts`, `src/stream.ts`, and
  `__tests__/{stream,live,frame-ordering}.test.ts`
- the devtools seam — `src/observe.ts` and the whole of `packages/client-devtools/`
- **and the entire Vue and Angular bindings** — `packages/client-vue/` and
  `packages/client-angular/`, every source file, test and config, plus
  `packages/client-react/__tests__/useQuery.live.test.tsx`

That last group is the third casualty by file count. But the one actually worth flagging
is a fourth, and it is invisible to `--diff-filter=D` because **no file was deleted**:

**chunk 5's staged-write machinery was reverted at the content level on local `main`.**

```
git show main:packages/client-core/src/store.ts | grep -c 'stage(|commit(|racedSince(|frameVersion'   ->  0
git show origin/main:...                        | same                                                ->  6
git show main:packages/client-core/src/cache.ts | same                                                ->  0
```

`store.ts` and `cache.ts` still exist on local `main` and still compile, so nothing in
the working tree looks absent — the frame-race ordering guarantee simply is not in them
any more. That is the same class of silent loss as the deleted directories (git saw
"unchanged on one side" for a file the branches predated), but it presents as a file that
is merely *older* rather than one that is gone, so no directory listing and no build
failure will surface it. `frame-ordering.test.ts` was deleted in the same merge, so the
tests that would have caught it went with the source.

This recovery is built on `origin/main`, which holds all four, and both merges preserve
chunk 5 explicitly — so nothing here needs fixing. It is recorded because anyone auditing
the damage by listing deleted files will undercount it, and because the reverted-content
case is the one a re-merge is most likely to reintroduce: it is exactly what taking the
incoming side of either `cache.ts` hunk would have done.
