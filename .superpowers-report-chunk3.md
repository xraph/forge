# Chunk 3 — query engine and REST transport

`packages/client-core` now runs an operation end to end: issue the request,
normalize the response into the entity store, record the skeleton's
dependencies on the registry entry, and hand back a denormalized value whose
object identity survives every read that did not change it.

Four new source files, ~2.45 kB gzipped on top of chunks 1+2:

| file | what it owns |
|---|---|
| `src/transport.ts` | `Transport`, `RestTransport`, retry policy, single-flight refresh, URL building, `manualClock` |
| `src/cache.ts` | `QueryCache` — the store, the registry and a transport, wired |
| `src/client.ts` | `query()`, `mutation()`, `configureClient()` — what generated `hooks.ts` imports |

## The stamps argument held

The claim was: only stamp a tag some remembered entry already carries, because
a stamp written when nothing carries the tag can never exceed any future
entry's `settledAt`.

**It holds, and I found no third tag-acquisition path.** Verified by reading
every write to `entry.tags`:

- `mount` constructs the entry literal with `tags: new Set(resolveTags(...))`
  and `settledAt: this.clock`.
- `retag` — the only other assignment, `entry.tags = tags` — is called from
  exactly one place, `settle`, which then sets `entry.settledAt = this.clock`.
- `place` also advances `settledAt`, but acquires no tags, so it cannot turn a
  dead stamp live.
- Nothing outside the class mutates `tags` (the field is documented read-only,
  and neither `Invalidator` nor the new `QueryCache` writes it).

Since `clock` is monotonic and `invalidatedSince` asks for *strictly* newer, a
stamp written at reading *c* is dead the moment it is written if nothing
carries the tag: every later acquirer gets `settledAt >= c`.

The same argument licenses the stronger half of the fix — **deleting a stamp
when its last carrier is dropped** — which is what actually bounds the map.
Without it the bound would only be "every tag ever carried by a remembered
entry", which still grows with entity tags across a long session with GC.

Implementation: a `carriers: Map<tag, count>` over *remembered* entries
(distinct from `index`, which holds mounted ones only, because an unmounted
query must keep its stamps). Maintained in entry creation, `retag`,
`drop` and `clear`. `invalidated` writes a stamp only when `carriers.has(tag)`;
`discharge` deletes the carrier count and the stamp together at zero.
`retag` now maintains carriers regardless of mount state — a settle can land
after the last unmount, and the tags it acquires must still be stampable.

New observable: `QueryRegistry#stampedTags`, because "this map does not grow"
is worth a test and is otherwise invisible.

The doc comment at the class head was rewritten: it now states the restriction,
names the entity-tag counterexample that broke the old "bounded by the API's
tag vocabulary" claim, and gives the argument.

Five tests, including the one asked for: a query settles carrying `Order:7`,
unmounts, `Order:7` is invalidated, it remounts and `onStale` fires exactly
once. Plus: 100 invalidations of uncarried tags leave `stampedTags` at 1; a
stamp survives one of two carriers being dropped and dies with the second; a
settle that stops providing a tag releases its stamp; `clear` empties the
carrier counts too, not just the stamps.

## Retry and deduplication semantics

**Retry.** Idempotent methods only (`GET`, `HEAD`, `PUT`, `DELETE`);
exponential backoff `min(maxDelay, base·2ⁿ)` with equal jitter (half fixed,
half random, so a retry still backs off and the herd still disperses); no retry
on 4xx except 408 and 429; a failure carrying no status at all (network, DNS,
parse) is retried; `AbortError` never is. The `sleep` and the `random` are
injected — there is not a single `setTimeout` in the tests.

The generated client has a retry loop of its own that retries any method on
408/429/5xx. Every request the transport builds sets `retry: { maxAttempts: 1 }`
to switch it off, so exactly one policy governs. Two compounding policies would
be three attempts each, nine requests. This is asserted.

**Deduplication.** The shared unit is **the whole retry sequence, not an
attempt.** N subscribers mounting the same query join one `Promise` that
resolves when the sequence terminally succeeds or terminally fails. Nobody is
ever resolved from a failed attempt while a neighbour waits for the retry,
because there is nothing to be resolved from: the retry loop lives inside the
transport, below the promise everyone holds. A subscriber that joins during a
backoff gap joins that same sequence.

A sequence that terminally fails clears its slot *before* rejecting, so the
next caller starts a fresh sequence rather than adopting a dead promise.

**The interaction with invalidation.** An invalidation landing while a request
is out does not resolve from it — the answer in progress was produced before
the write it is supposed to reflect. Rather than issuing a second concurrent
request, the in-flight one is marked `restart`: on arrival it is discarded and
the sequence runs again, on the same promise. So still one request at a time
per query, and the value a subscriber ends up with was fetched after the write
that invalidated it. Tested: a read is in flight, `Order[]` is invalidated, the
pre-write response resolves and is *not* shown, the post-write one is.

## How single-flight refresh is tested deterministically

The provider's `refresh()` awaits a deferred the test holds. Two requests are
started; both fail the guard with 401; `settleMicrotasks()` (eight
`await Promise.resolve()`, no timers) drains everything that can run without
the gate opening. At that point the test asserts `refreshes === 1` and
`calls.length === 2` — both requests are provably *inside* the refresh window,
because the gate has not been released and neither could have got past it.
The gate is then resolved and both are awaited: four calls total, the last two
both bearing `Bearer t1`.

There is no window that closes on its own, so there is no race for the test to
lose.

The transport keeps a `generation` counter alongside the in-flight promise. A
request that 401s compares the reading its credentials were taken at against
the current one; if a refresh has already landed since, it retries against the
new credential without asking for another. That is the difference between one
refresh per stampede and one per request in it. Four more tests cover the
edges: exactly one retry (a 401 against a fresh credential is an authorization
answer, not a transient failure); a failing refresh surfaces the original 401,
not the token endpoint's complaint; the in-flight promise is cleared on
completion so a later 401 starts its own refresh; a 401 with no `refresh`
configured is left alone.

The refresh retry deliberately applies to every method including `POST`: a 401
says the server rejected the request before acting on it, which makes
re-sending safe in a way a timeout is not.

## How referential stability is preserved through the cache

The cache stores a **skeleton per query, never a denormalized document**, and
computes the value on every read through `EntityStore#read`. Chunk 1 memoizes
that per subtree, so a read of an unchanged skeleton hits `memoByNode` on the
root node and returns the identical object in O(1) — re-denormalizing into
fresh objects on every read would have thrown chunk 1's work away, and is
exactly what was avoided.

Stability holds at three levels, each tested:

1. **`data`** — `fetch()` twice returns the same array object; a refetch that
   changes one order keeps the untouched `Customer` subtree's identity.
2. **`QueryState`** — the state object is memoized and only rebuilt when
   `data`, `status`, `error` or `isFetching` actually differs. `data` compares
   by *identity*, which is sound precisely because the store guarantees it; a
   deep compare would be slower and wrong.
3. **Placement output** — a value a placement callback produced is normalized
   back into the store rather than held as a document, so the placed list
   behaves like a fetched one. The test places `[created, ...current]` and then
   writes to `Order:9` directly; the placed list sees the new total.

`registry.entry.value` (what placement receives as `current`) is refreshed from
the store on every snapshot, and every tracked query is snapshotted immediately
before `invalidator.settled` runs — so a placement callback never prepends to a
list some earlier write already moved underneath it.

## Also in scope, also done

- **Identity partitioning.** `QueryCache#setPrincipal` drops the store, the
  registry and every record on a change, abandons every request in flight —
  including unwatched ones, which would otherwise normalize the previous
  principal's response into the store that was just emptied — and re-mounts and
  refetches whatever is still watched. Tested both ways: previous entities are
  unreachable immediately, and a response that lands after the switch is never
  committed.
- **Bounded memory.** The cache caps *unwatched* records (`limit`, 128 by
  default) and evicts LRU, calling `registry.drop`, which releases the tags and
  their stamps. A watched query is never evicted. This closes the "unbounded
  registry growth" gap chunk 2's README listed as open.
- **A compile-time assertion that the generated client fits.** The generated
  `RequestConfig`/`HTTPClient` declarations are copied into
  `__tests__/transport.test.ts`; `RestClientLike` accepting a
  `GeneratedRESTClient` is checked by the typechecker.

## Two deliberate non-decisions

- **The runtime drives `HTTPClient#request`, not the typed per-endpoint
  methods.** Those take positional, per-endpoint parameters
  (`(orderId, body, options)`) that no generic caller holding only an
  `OperationMeta` can fill. `request` is the seam every generated method
  funnels into anyway, so content-type dispatch, binary bodies and the base
  URL below it are unchanged. What is *not* reached this way is
  `bodyCodec`/`responseCodec`: those are set by the generated method above
  `request`, and `ops.ts` does not carry the codec ids. Under
  `NamingPreserve` with no `FieldOverrides` — where no codec table is emitted
  at all — this is exactly equivalent; otherwise a renamed JSON body would ship
  wire-cased through the hook path. **This is the one integration gap in the
  chunk**, and it wants two more fields on `OperationMeta` from
  `opsmanifest.go`, which was out of scope here.
- **No SSR `dehydrate`/`hydrate`.** A serialized skeleton is not recognised as
  a skeleton on revival (references are identified by object identity, not by
  the `__ref` property), so hydration needs the revive pass chunk 1's README
  already lists as open. Shipping a half-working pair would have been worse
  than not shipping it.
