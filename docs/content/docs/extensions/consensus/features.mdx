## Packages

You assemble a node from these packages yourself, the way the [quick start](/docs/extensions/consensus#quick-start) does. Most constructors take a config struct and a `forge.Logger`.

| Package | What's in it |
|---|---|
| `raft` | `raft.NewNode(config, logger, stateMachine, transport, storage)`, elections, pre-vote, replication, snapshots, `Propose`, `AddPeer` |
| `storage` | `NewMemoryStorage`, `NewBadgerStorage`, `NewBoltDBStorage`, and a write-ahead log (`NewWAL`) |
| `transport` | `NewLocalTransport` (in process), `NewGRPCTransport`, `NewTCPTransport`, `NewHTTPTransport`, TLS helpers and serializers |
| `statemachine` | `NewMemoryStateMachine` and `NewPersistentStateMachine` |
| `discovery` | `NewStaticDiscovery`, `NewDNSDiscovery`, `NewConsulDiscovery`, `NewEtcdDiscovery`, `NewKubernetesDiscovery` |
| `cluster` | Membership, quorum and topology tracking with `cluster.NewManager` |
| `middleware` | Checks for Forge handlers around leadership, quorum and read consistency |
| `admin`, `api` | HTTP handlers for cluster status and management. Nothing mounts them for you |
| `testing` | An in-process cluster harness and the cluster tests |

Only the in-process transport and memory storage have been run as a cluster in this repository. The networked transports, the BadgerDB and BoltDB backends and the discovery backends compile, but nothing here runs a cluster on them, and some of them don't fit the interfaces `raft.NewNode` takes yet. The sections below say which.

## Raft nodes

`raft.NewNode` takes a `raft.Config`, a logger, and your state machine, transport and storage. `raft.DefaultConfig()` gives you the timings from the Raft paper: a 50ms heartbeat and a 150ms to 300ms election timeout, with pre-vote and quorum checks on. If you build a `raft.Config` literal instead, zero timings fall back to a 1s heartbeat and a 5s to 10s election timeout.

How an election works: every node starts as a follower with a random election timeout between `ElectionTimeoutMin` and `ElectionTimeoutMax`. A follower that hears no heartbeat in that window becomes a candidate, runs a pre-vote if `PreVoteEnabled` is on, then asks its peers for votes. The node with a majority becomes leader and sends heartbeats every `HeartbeatInterval`. A new leader writes a no-op entry first, which is why the quick start's `set` lands at index 2.

| Method on `*raft.Node` | What it does |
|---|---|
| `Start(ctx)`, `Stop(ctx)` | Run and stop the node |
| `AddPeer(peerID string)` | Registers a peer ID. Call it before `Start`, and connect the transport to that peer separately |
| `IsLeader()`, `GetLeader()`, `GetRole()`, `GetTerm()` | Leadership state |
| `Propose(ctx, command []byte)` | Appends a command on the leader and returns once a majority has it. On a follower it returns a not-leader error naming the leader |
| `Apply(ctx, entry LogEntry)` | Appends a prepared log entry on the leader and waits for it to commit |
| `GetCommitIndex()`, `GetStats()` | Progress and a `RaftStats` snapshot |
| `AddNode(ctx, id, address, port)`, `RemoveNode(ctx, id)` | Membership changes, leader only. Not working yet: the goroutine that processes them is never started, so both block until your context ends |
| `StepDown(ctx)` | The leader steps down |
| `TransferLeadership(ctx, target)` | Steps down and lets the next election decide. It doesn't hand leadership to `target` yet |

Followers advance their commit index but don't apply committed entries to their state machine, so a read from a follower's state machine stays empty. Read from the leader.

## The memory state machine

`statemachine.NewMemoryStateMachine` keeps a `map[string]any`. It decodes each normal log entry as a JSON `consensus.Command`:

| `Command.Type` | Payload | Effect |
|---|---|---|
| `set` | `key`, `value` | Stores `value` under `key` |
| `delete` | `key` | Removes `key` |
| `increment` | `key` | Adds 1, starting from 1 when the key is missing |

`Query` takes a `map[string]any` with a `type`: `get` (with a `key`), `list` (the whole map) or `size`.

`statemachine.NewPersistentStateMachine` stores state in a `consensus.Storage`, but it has `Get`, `CreateSnapshot` and `RestoreSnapshot` where the interface wants `Query`, `Snapshot` and `Restore`, so it doesn't implement `consensus.StateMachine` and `raft.NewNode` won't take it.

## Your own state machine

Implement `consensus.StateMachine` and pass it to `raft.NewNode`:

```go
type StateMachine interface {
	Apply(entry LogEntry) error
	Snapshot() (*Snapshot, error)
	Restore(snapshot *Snapshot) error
	Query(query any) (any, error)
}
```

`Propose` stores whatever bytes you give it in `LogEntry.Data`. This key-value store expects the JSON `Command` the quick start proposes:

```go
type KVStore struct {
	mu   sync.RWMutex
	data map[string]string
}

func (s *KVStore) Apply(entry consensus.LogEntry) error {
	// Leaders write a no-op entry when they take over. Only normal entries carry commands.
	if entry.Type != consensus.EntryNormal {
		return nil
	}

	var cmd consensus.Command
	if err := json.Unmarshal(entry.Data, &cmd); err != nil {
		return err
	}

	key, _ := cmd.Payload["key"].(string)

	s.mu.Lock()
	defer s.mu.Unlock()

	switch cmd.Type {
	case "set":
		value, _ := cmd.Payload["value"].(string)
		s.data[key] = value
	case "delete":
		delete(s.data, key)
	}

	return nil
}

func (s *KVStore) Query(query any) (any, error) {
	key, ok := query.(string)
	if !ok {
		return nil, errors.New("query must be a key")
	}

	s.mu.RLock()
	defer s.mu.RUnlock()

	return s.data[key], nil
}

func (s *KVStore) Snapshot() (*consensus.Snapshot, error) {
	s.mu.RLock()
	defer s.mu.RUnlock()

	data, err := json.Marshal(s.data)
	if err != nil {
		return nil, err
	}

	return &consensus.Snapshot{Data: data, Size: int64(len(data))}, nil
}

func (s *KVStore) Restore(snapshot *consensus.Snapshot) error {
	s.mu.Lock()
	defer s.mu.Unlock()

	data := map[string]string{}
	if err := json.Unmarshal(snapshot.Data, &data); err != nil {
		return err
	}

	s.data = data

	return nil
}
```

The extension has no way to take your state machine. Use it with your own `raft.Node`.

## Snapshots

`raft.Config` has `SnapshotInterval`, `SnapshotThreshold` and `EnableSnapshots` (on in `raft.DefaultConfig()`, off in a `raft.Config` literal). With snapshots on, the node checks every `SnapshotInterval` and asks the state machine for a `Snapshot` when the log holds more than `SnapshotThreshold` entries. A node can receive an `InstallSnapshot` request, but no leader code sends one yet, so a follower that falls far behind isn't caught up from a snapshot.

<Callout type="warn">
The extension's `Service.Snapshot` and its auto-snapshot loop call a state machine that is never created, so both panic. The loop is on by default and fires every `raft.snapshot_interval` (30 minutes), which takes your process down. Set `advanced.enable_auto_snapshot: false` in your config file if you register the extension.
</Callout>

## Storage

`raft.NewNode` takes a `consensus.Storage`: `Start`, `Stop`, `Set`, `Get`, `Delete`, `Batch`, `GetRange` and `Close`.

| Backend | Constructor |
|---|---|
| In memory | `storage.NewMemoryStorage(storage.MemoryStorageConfig{}, logger)` |
| BadgerDB | `storage.NewBadgerStorage(storage.BadgerStorageConfig{...}, logger)` |
| BoltDB | `storage.NewBoltDBStorage(storage.BoltDBStorageConfig{...}, logger)` |
| Write-ahead log | `storage.NewWAL(nodeID, storage.WALConfig{...}, logger)` |

Only `MemoryStorage` implements `consensus.Storage` today. `BadgerStorage` and `BoltDBStorage` have `WriteBatch` where the interface wants `Batch`, and no `Close`, so `raft.NewNode` won't accept them until you wrap them in a small adapter.

The extension's config validator also accepts `pebble` and `postgres` for `storage.type`, but there's no implementation of either in this module.

## Transports

All four transports implement `consensus.Transport`: `Start`, `Stop`, `Send`, `Receive`, `AddPeer`, `RemovePeer` and `GetAddress`.

| Transport | Constructor |
|---|---|
| In process | `transport.NewLocalTransport`, connected to its peers with `Connect` |
| gRPC | `transport.NewGRPCTransport` |
| TCP | `transport.NewTCPTransport` |
| HTTP | `transport.NewHTTPTransport` |

`transport.NewTLSManager` loads certificates, and `NewJSONSerializer`, `NewGobSerializer`, `NewProtobufSerializer` and `NewCompressedSerializer` encode messages. The extension's `transport.type` only accepts `grpc` and `tcp`.

## Discovery

`consensus.Discovery` has `Start`, `Stop`, `Register`, `Unregister`, `GetNodes` and `Watch`, which returns a channel of `NodeChangeEvent`. The static and DNS backends implement it. Consul, etcd and Kubernetes use their own method names (`DiscoverPeers`, `WatchPeers` and so on), so they don't satisfy the interface.

| Backend | Constructor |
|---|---|
| Static list | `discovery.NewStaticDiscovery` |
| DNS | `discovery.NewDNSDiscovery` |
| Consul | `discovery.NewConsulDiscovery` |
| etcd | `discovery.NewEtcdDiscovery` |
| Kubernetes | `discovery.NewKubernetesDiscovery` |

## Leadership checker

The extension registers a `*consensus.LeadershipChecker` over its service. `RequireLeader()` returns a not-leader error naming the leader, and `RequireQuorum()` returns `ErrNoQuorum` when the cluster has no quorum. `IsLeader()` and `GetLeader()` pass through to the service.

Because the extension's node is never leader and has no cluster manager, `RequireLeader()` and `RequireQuorum()` always fail today. You can also build one yourself with `consensus.NewLeadershipChecker(service)`, but `*consensus.Service` is the only `ConsensusService` in the module.

## Middleware

The `middleware` package has two kinds of helpers.

| Type | Built from | Methods |
|---|---|---|
| `LeadershipMiddleware` | `NewLeadershipMiddleware(service, logger)` | `RequireLeader(next)`, `LeaderRedirect(next)`, `ReadOnlyRouting(next)` |
| `QuorumMiddleware` | `NewQuorumMiddleware(service, logger)` | `RequireQuorum(next)` |
| `MetricsMiddleware` | `NewMetricsMiddleware(service, logger)` | `AddConsensusHeaders(next)` |
| `ReadOnlyMiddleware` | `NewReadOnlyMiddleware(raftNode, logger)` | `Handle()`, `HandleStrict()`, `HandleWithStaleReads()` |
| `RedirectMiddleware` | `NewRedirectMiddleware(raftNode, manager, logger)` | `Handle()`, `HandleWithAutoRedirect()`, `HandleWithForward()` |
| `ConsistencyMiddleware` | `NewConsistencyMiddleware(raftNode, config, logger)` | `Handle()` |

The first three wrap a `func(forge.Context) error`. The leadership and quorum checks answer 503 with a JSON body when they fail, and `AddConsensusHeaders` sets `X-Consensus-Node-ID`, `X-Consensus-Term`, `X-Consensus-Role`, `X-Consensus-Leader` and related headers. They take a `ConsensusService`, and the only one in the module is the extension's, which is never leader and has no quorum, so `RequireLeader` and `RequireQuorum` reject every request today.

The other three take a `RaftNode`, so your own `*raft.Node` works with them. Their methods return a check function with no `next` parameter, and when a check fails they write the JSON error and return what `ctx.JSON` returns, which is `nil` once the response is written. Your code can't tell a rejection from a pass by the return value, so treat these as unfinished.

## Admin API

<Callout type="warn">
The extension doesn't mount an admin API. `admin_api.enabled` is on by default, and all it does is log "admin API enabled but not yet implemented".
</Callout>

The `admin` package has the handlers. `admin.NewAPI(service, healthChecker, metricsCollector, logger)` builds them and `RegisterRoutes(router, prefix)` mounts these under `prefix`:

| Route | Handler |
|---|---|
| `GET /health`, `GET /health/detailed` | Health from the service, or from the health checker when you pass one |
| `GET /status`, `GET /metrics`, `GET /leader`, `GET /nodes` | Stats, the metrics collector's metrics, leadership and membership |
| `POST /leadership/transfer`, `POST /leadership/stepdown` | Call `TransferLeadership` and `StepDown` |
| `POST /snapshot` | Calls `Snapshot` |
| `POST /nodes/add`, `POST /nodes/remove` | Call `AddNode` and `RemoveNode` |
| `POST /apply`, `POST /read` | Call `Apply` and `Read` |

The handlers call a `ConsensusService`, and with the extension's service they report the stub state above: `/snapshot` and `/read` hit the nil state machine. The `api` package has more handler sets (`NewClusterAPI`, `NewConfigAPI`, `NewNodeAPI` and a stats API) built from `cluster` managers and a `RaftNode`. Nothing registers them either.

## Statistics

`Service.GetStats()` returns a `ConsensusStats` with `NodeID`, `ClusterID`, `Role`, `Status`, `Term`, `LeaderID`, `CommitIndex`, `LastApplied`, `LastLogIndex`, `LastLogTerm`, `ClusterSize`, `HealthyNodes`, `HasQuorum`, `ElectionsTotal`, `ElectionsFailed`, `OperationsTotal`, `OperationsFailed`, `OperationsPerSec`, `AverageLatencyMs`, `ErrorRate`, `LogEntries`, `SnapshotsTotal`, `LastSnapshotTime`, `Uptime` and `StartTime`. On the extension's service most of these stay at zero.

The extension also implements `Metrics()` with a map of the same numbers. The service is created without a metrics sink, so the metrics collection loop it runs every `observability.metrics.collection_interval` records nothing.

## Errors

The root package re-exports these sentinels. Each is a `*errors.ForgeError` with a `CONSENSUS_*` code, so check them with `errors.Is`.

| Error | Meaning |
|---|---|
| `ErrNotLeader` | This node isn't the leader |
| `ErrNoLeader` | No leader is available |
| `ErrNotStarted`, `ErrAlreadyStarted` | Lifecycle errors from `Start` and the operations |
| `ErrNodeNotFound`, `ErrClusterNotFound` | Unknown node or cluster |
| `ErrStorageUnavailable`, `ErrTransportUnavailable`, `ErrDiscoveryUnavailable` | A backend is down |
| `ErrNoQuorum` | Not enough healthy nodes |
| `ErrInvalidTerm`, `ErrStaleTerm` | Term problems |
| `ErrLogInconsistent` | Log mismatch |
| `ErrSnapshotFailed`, `ErrCompactionFailed` | Snapshot or compaction failed |
| `ErrElectionTimeout` | Election timed out |
| `ErrInvalidPeer`, `ErrPeerExists`, `ErrPeerNotFound`, `ErrInsufficientPeers` | Peer problems |
| `ErrInvalidConfig` | Config validation failed |

| Helper | What it does |
|---|---|
| `IsNotLeaderError(err)`, `IsNoLeaderError(err)`, `IsNoQuorumError(err)`, `IsStaleTermError(err)` | `errors.Is` against the matching sentinel |
| `IsRetryable(err)` | True for no leader, no quorum, unavailable storage, transport or discovery, and timeouts |
| `IsFatal(err)` | True for invalid config and validation errors |
| `NewNotLeaderError(nodeID, leaderID)` | A not-leader error carrying both IDs |
| `NewNoLeaderError()`, `NewTimeoutError(operation)` | No-leader and timeout errors |
| `NewNoQuorumError(required, available)`, `NewStaleTermError(current, received)` | Errors carrying the counts or terms |
