## Packages

You can assemble a node from these packages yourself, the way the [quick start](/docs/extensions/consensus#quick-start) does, or let the extension build one from config. Most constructors take a config struct and a `forge.Logger`.

| Package | What's in it |
|---|---|
| `raft` | `raft.NewNode(config, logger, stateMachine, transport, storage)`, elections, replication, snapshots, membership changes, leadership transfer |
| `storage` | `NewMemoryStorage`, `NewBadgerStorage`, `NewBoltDBStorage`, a write-ahead log (`NewWAL`), and `NewEncryptedStorage` with `LoadKeyring`, `MigrateToEncrypted` and `MigrateToPlaintext` for encryption at rest |
| `transport` | `NewLocalTransport` (in process), `NewTCPTransport`, `NewHTTPTransport`, `NewGRPCTransport`, TLS helpers and serializers |
| `statemachine` | `NewMemoryStateMachine` and `NewPersistentStateMachine` |
| `discovery` | `NewStaticDiscovery`, `NewDNSDiscovery`, `NewConsulDiscovery`, `NewEtcdDiscovery`, `NewKubernetesDiscovery` |
| `cluster` | Membership, quorum and topology tracking with `cluster.NewManager` |
| `middleware` | Checks for Forge handlers around leadership, quorum and read consistency |
| `admin`, `api` | HTTP handlers for cluster status and management. The extension mounts the `admin` routes when `admin_api.enabled` is on |
| `testing` | An in-process cluster harness and the cluster tests |

Three node clusters on the in-process, TCP, HTTP and gRPC transports, with memory, BoltDB and BadgerDB storage, are covered by the module's tests. The discovery backends aren't wired into the extension, and some of them don't fit the module's `Discovery` interface. The sections below say which.

## Raft nodes

`raft.NewNode` takes a `raft.Config`, a logger, and your state machine, transport and storage. `raft.DefaultConfig()` gives you the timings from the Raft paper: a 50ms heartbeat and a 150ms to 300ms election timeout. If you build a `raft.Config` literal instead, zero timings fall back to a 1s heartbeat and a 5s to 10s election timeout.

How an election works: every node starts as a follower with a random election timeout between `ElectionTimeoutMin` and `ElectionTimeoutMax`. A voter that hears no heartbeat in that window becomes a candidate and asks the other voters for votes. The node with a majority becomes leader and sends heartbeats every `HeartbeatInterval`. A new leader writes a no-op entry first, which is why the quick start's `set` lands at index 2.

There's no pre-vote round. `PreVoteEnabled` is carried on vote requests but nothing acts on it. What stops a server that was cut off from forcing an election when it comes back is simpler: a voter ignores vote requests, without even adopting their term, while it has heard from a live leader within the minimum election timeout, and it ignores vote requests from servers that aren't voters in its configuration.

| Method on `*raft.Node` | What it does |
|---|---|
| `Start(ctx)`, `Stop(ctx)` | Run and stop the node |
| `AddPeer(peerID string)`, `AddPeerAddress(peerID, address string, port int)` | Add a voter to the first membership of a new cluster. Call them before `Start`. `AddPeerAddress` also records the address, so servers added later can reach this member. Both are ignored once the log or a snapshot holds a membership |
| `IsLeader()`, `GetLeader()`, `GetRole()`, `GetTerm()` | Leadership state |
| `Propose(ctx, command []byte)` | Appends a command on the leader and returns once it is committed and applied. On a follower it returns a not-leader error naming the leader. If a leadership change drops the entry before it commits, it returns `raft.ErrProposalDropped` and you can retry |
| `Apply(ctx, entry LogEntry)` | The same for a prepared log entry. Configuration entries are refused; use `AddNode` and `RemoveNode` |
| `GetCommitIndex()`, `GetStats()` | Progress and a `RaftStats` snapshot |
| `Configuration()` | The current membership: each member's ID, address, port and whether it votes |
| `AddNode(ctx, id, address, port)`, `RemoveNode(ctx, id)` | Membership changes, on the leader. See [membership changes](#membership-changes) |
| `TransferLeadership(ctx, target)` | Hands leadership to `target`. See [leadership transfer](#leadership-transfer) |
| `StepDown(ctx)` | The leader returns to follower and an election picks the next one |
| `Snapshot()` | Snapshots the state machine and compacts the log |
| `Peers()`, `HasQuorum()` | What this node knows about the other members, and whether it's in touch with a majority |

Followers apply committed entries to their own state machine too, usually a heartbeat after the leader. Reads from a follower can lag the leader, and there are no linearizable reads.

The node persists every entry, its term and its vote before it answers, and reloads them on restart. A follower that couldn't write an entry rejects the request instead of acknowledging it.

## Membership changes

Membership changes one server at a time, through configuration entries in the log, as in section 4.1 of the Raft dissertation. A configuration takes effect on every node as soon as its entry is appended, and only one change can be in flight: a second one returns `raft.ErrConfigChangeInProgress` until the first has committed.

To add a server:

1. Start it with `Join: true` in its `raft.Config` (or `join: true` in the extension's config). A joining server never starts an election on its own. Give its transport routes to the existing members, which the extension does from its `peers`.
2. Call `AddNode(ctx, id, address, port)` on the leader.

`AddNode` first adds the server as a learner: it receives the log but doesn't vote or count towards a majority, so an empty server can't stall commits while it catches up. Once the learner holds every committed entry, a second entry promotes it to voter. If it hasn't caught up within your context or twenty election timeouts, it's removed again and `AddNode` returns `raft.ErrLearnerNotCaughtUp`.

`RemoveNode(ctx, id)` removes a server. You can remove the leader itself: it keeps replicating without counting itself, then steps down once the new membership commits, and the remaining servers elect a leader. A removed server that never learned it was removed (because it was down at the time) can't disrupt the cluster when it comes back, because the members ignore vote requests from servers that aren't voters.

Membership survives restarts and compaction: configuration entries live in the log, and the membership at a snapshot's index is stored with the snapshot and sent with `InstallSnapshot`. Once it's recorded, `AddPeer` and the extension's `peers` no longer change anything.

On the extension, `Service.AddNode`, `RemoveNode` and `GetClusterManager()` (whose `AddNode` and `RemoveNode` go through the same log entries) do the same thing, as do the admin routes `POST /nodes/add` and `POST /nodes/remove`.

## Leadership transfer

`TransferLeadership(ctx, target)` hands leadership to a chosen voter, following section 3.10 of the Raft dissertation:

1. The leader stops accepting writes and membership changes. They return `raft.ErrLeadershipTransferInProgress`.
2. It brings `target`'s log up to date.
3. It sends `target` a TimeoutNow message, and `target` starts an election at once. Voters grant that election even though they heard from the leader recently.

If `target` hasn't taken over within an election timeout (it's down, say), the transfer is abandoned with `raft.ErrLeadershipTransferFailed` and the old leader carries on as before. `Service.TransferLeadership` and `POST /leadership/transfer` do the same.

## The memory state machine

`statemachine.NewMemoryStateMachine` keeps a `map[string]any`. It decodes each normal log entry as a JSON `consensus.Command`:

| `Command.Type` | Payload | Effect |
|---|---|---|
| `set` | `key`, `value` | Stores `value` under `key` |
| `delete` | `key` | Removes `key` |
| `increment` | `key` | Adds 1, starting from 1 when the key is missing |

`Query` takes a `map[string]any` with a `type`: `get` (with a `key`), `list` (the whole map) or `size`. The extension always uses this state machine, and its `Service.Apply` sends your `Command` as JSON.

`statemachine.NewPersistentStateMachine` stores state in a `consensus.Storage`, but it has `Get`, `CreateSnapshot` and `RestoreSnapshot` where the interface wants `Query`, `Snapshot` and `Restore`, so it doesn't implement `consensus.StateMachine` and `raft.NewNode` won't take it.

## Your own state machine

Implement `consensus.StateMachine` and pass it to `raft.NewNode`:

```go
type StateMachine interface {
	Apply(entry LogEntry) error
	Snapshot() (*Snapshot, error)
	Restore(snapshot *Snapshot) error
	Query(query any) (any, error)
}
```

`Propose` stores whatever bytes you give it in `LogEntry.Data`. This key-value store expects the JSON `Command` the quick start proposes:

```go
type KVStore struct {
	mu   sync.RWMutex
	data map[string]string
}

func (s *KVStore) Apply(entry consensus.LogEntry) error {
	// Leaders write a no-op entry when they take over. Only normal entries carry commands.
	if entry.Type != consensus.EntryNormal {
		return nil
	}

	var cmd consensus.Command
	if err := json.Unmarshal(entry.Data, &cmd); err != nil {
		return err
	}

	key, _ := cmd.Payload["key"].(string)

	s.mu.Lock()
	defer s.mu.Unlock()

	switch cmd.Type {
	case "set":
		value, _ := cmd.Payload["value"].(string)
		s.data[key] = value
	case "delete":
		delete(s.data, key)
	}

	return nil
}

func (s *KVStore) Query(query any) (any, error) {
	key, ok := query.(string)
	if !ok {
		return nil, errors.New("query must be a key")
	}

	s.mu.RLock()
	defer s.mu.RUnlock()

	return s.data[key], nil
}

func (s *KVStore) Snapshot() (*consensus.Snapshot, error) {
	s.mu.RLock()
	defer s.mu.RUnlock()

	data, err := json.Marshal(s.data)
	if err != nil {
		return nil, err
	}

	return &consensus.Snapshot{Data: data, Size: int64(len(data))}, nil
}

func (s *KVStore) Restore(snapshot *consensus.Snapshot) error {
	s.mu.Lock()
	defer s.mu.Unlock()

	data := map[string]string{}
	if err := json.Unmarshal(snapshot.Data, &data); err != nil {
		return err
	}

	s.data = data

	return nil
}
```

The extension has no way to take your state machine. Use it with your own `raft.Node`.

An error from `Apply` doesn't stop the node: the entry is committed on every server, so the node records it as applied and returns your error to the caller waiting on that entry.

## Snapshots

`raft.Config` has `SnapshotInterval`, `SnapshotThreshold` and `EnableSnapshots` (on in `raft.DefaultConfig()`, off in a `raft.Config` literal). With snapshots on, the node checks every `SnapshotInterval` and snapshots when its log holds more than `SnapshotThreshold` entries. You can also call `Snapshot()` on the node, or `Snapshot(ctx)` on the extension's service. A snapshot is taken at the last applied entry, stored with the membership at that point, and the log before it is dropped.

A follower whose next entry is already in the leader's snapshot gets the snapshot through `InstallSnapshot`, in chunks of at most `SnapshotChunkSize` bytes (1 MiB by default; the extension uses half of `transport.max_message_size`). It restores its state machine from it and keeps any later entries that agree with it.

## Storage

`raft.NewNode` takes a `consensus.Storage`: `Start`, `Stop`, `Set`, `Get`, `Delete`, `Batch`, `GetRange` and `Close`. The memory, BadgerDB and BoltDB backends all implement it.

| Backend | Constructor |
|---|---|
| In memory | `storage.NewMemoryStorage(storage.MemoryStorageConfig{}, logger)` |
| BadgerDB | `storage.NewBadgerStorage(storage.BadgerStorageConfig{Path: dir}, logger)` |
| BoltDB | `storage.NewBoltDBStorage(storage.BoltDBStorageConfig{Path: file}, logger)` |
| Write-ahead log | `storage.NewWAL(nodeID, storage.WALConfig{...}, logger)` |

BadgerDB always writes synchronously. `BoltDBStorageConfig` takes `Timeout` (how long to wait for the file lock, 1s by default), `NoSync`, `NoGrowSync`, `ReadOnly` and `MmapFlags`. Leave `NoSync` off: with it on, a crash can lose writes the node already acknowledged.

The extension's config validator also accepts `pebble` and `postgres` for `storage.type`, but there's no implementation of either, so the service refuses them when it's created.

## Encryption at rest

Turn on `security.enable_encryption` and give the node a key, and everything it writes through its storage backend is encrypted before it reaches disk: the Raft log, the current term and vote, snapshots and the snapshot metadata. It works the same on `badger`, `boltdb` and `memory`.

```yaml
extensions:
  consensus:
    security:
      enable_encryption: true
      encryption_key_file: /etc/consensus/raft.key   # or encryption_key_env: RAFT_KEY
```

You can make a key with `openssl rand -hex 32 > raft.key && chmod 600 raft.key`. A key is 32 bytes (AES-256), and a file can hold the 32 raw bytes, 64 hex characters or base64 text. An environment variable holds hex or base64. The key is read when the service starts, and a key of the wrong size, a missing file or an unset variable stops `Start` with `storage.ErrInvalidEncryptionKey`. Errors name the source but never the key, and logs only show key IDs. Inline keys (`encryption_key`, or `value` in a list entry) are refused unless you set `allow_inline_encryption_key: true`.

Each node encrypts its own disk, so each node can have its own key. Traffic between nodes isn't covered; use `enable_tls` or `enable_mtls` for that.

Every stored value becomes a version byte, a 4 byte key ID, a 12 byte random nonce, the ciphertext and a 16 byte tag, so 33 bytes more than the plaintext. The version, key ID and storage key are authenticated too, so a value copied to another key or edited fails with `storage.ErrDecrypt` instead of being read. Storage keys themselves stay readable: someone with the disk can see names like `log_42` and `snapshot_meta`, and roughly how big each value is, but not the content. The write-ahead log in `storage.NewWAL` isn't encrypted; the extension doesn't use it.

To rotate, list the keys with IDs. The highest ID (or `encryption_active_key_id`) encrypts new writes, and every listed key can still read:

```yaml
security:
  enable_encryption: true
  encryption_keys:
    - {id: 1, file: /etc/consensus/raft-1.key}
    - {id: 2, env: RAFT_KEY_2}
```

A single `encryption_key_file` or `encryption_key_env` counts as key ID 1. Restart the node with the new list, then call `Service.ReencryptStorage()` to rewrite everything still under the old key. It's safe while the node is serving. After that you can drop the old key. Never reuse an ID for a different key.

The store keeps a small check value per key ID, so a wrong key fails at `Start` with `storage.ErrWrongKey`. Turning encryption on over a store that already holds plaintext fails with `storage.ErrPlaintextStore`, and starting without encryption over an encrypted store fails with `storage.ErrEncryptedStore`. To encrypt a node that already has data, start it once with `security.encryption_migrate_plaintext: true`. To go back, stop the node and run `storage.MigrateToPlaintext` on its started backend with the same keyring. An interrupted migration makes the next start fail with `storage.ErrMigrationIncomplete` until you run it again. Mind you, old plaintext can stay in BoltDB free pages or Badger value log files after a migration, until they're reused or compacted.

When you build a node yourself, wrap the backend: load the keys with `storage.LoadKeyring`, then pass the backend and keyring to `storage.NewEncryptedStorage` and give the result to `raft.NewNode`.

## Transports

All four transports implement `consensus.Transport`: `Start`, `Stop`, `Send`, `Receive`, `AddPeer`, `RemovePeer` and `GetAddress`.

| Transport | Constructor |
|---|---|
| In process | `transport.NewLocalTransport`, connected to its peers with `Connect` |
| TCP | `transport.NewTCPTransport`. Length-prefixed frames on a connection per peer |
| HTTP | `transport.NewHTTPTransport`. One POST to `/raft/message` per message |
| gRPC | `transport.NewGRPCTransport`. One unary call per message |

The three network transports carry the same versioned JSON envelope. A message from a peer on another protocol version is refused with `transport.ErrProtocolVersion`, and one larger than `MaxMessageSize` (4 MiB by default) with `transport.ErrMessageTooLarge`. They listen on `127.0.0.1` unless you give them an address, cap inbound connections with `MaxConnections`, and close connections that sit idle too long.

The gRPC transport sends each message to `forge.consensus.raft.v1.Transport/Send` with a raw bytes codec, so there's no protoc step or generated code. It keeps one connection per peer, uses `MaxMessageSize` as the gRPC send and receive limit, and pings idle connections every `KeepAliveTime`. Refusals come back as gRPC statuses, which `Send` turns into the errors above or a permission error.

For TLS, build a config with `transport.NewTLSManager(...).GetTLSConfig()` and pass it as `TLSConfig`. With `RequirePeerIdentity` on, the transport needs mutual TLS, refuses any message whose sender isn't named in its client certificate, and checks that each peer it dials presents that peer's certificate. Each node's certificate must carry its node ID as a DNS subject alternative name. The extension sets this up from `security.enable_tls` and `enable_mtls`.

`NewJSONSerializer`, `NewGobSerializer`, `NewProtobufSerializer` and `NewCompressedSerializer` are there too, but the transports don't use them.

## Discovery

`consensus.Discovery` has `Start`, `Stop`, `Register`, `Unregister`, `GetNodes` and `Watch`, which returns a channel of `NodeChangeEvent`. The static and DNS backends implement it. Consul, etcd and Kubernetes use their own method names (`DiscoverPeers`, `WatchPeers` and so on), so they don't satisfy the interface.

| Backend | Constructor |
|---|---|
| Static list | `discovery.NewStaticDiscovery` |
| DNS | `discovery.NewDNSDiscovery` |
| Consul | `discovery.NewConsulDiscovery` |
| etcd | `discovery.NewEtcdDiscovery` |
| Kubernetes | `discovery.NewKubernetesDiscovery` |

The extension only uses `static`: its first members come from `peers`, and any other `discovery.type` stops the service when it's created.

## Leadership checker

The extension registers a `*consensus.LeadershipChecker` over its service. `RequireLeader()` returns a not-leader error naming the leader, or `nil` on the leader, and `RequireQuorum()` returns `ErrNoQuorum` when this node isn't in touch with a majority. `IsLeader()` and `GetLeader()` pass through to the service. You can also build one yourself with `consensus.NewLeadershipChecker(service)`.

## Middleware

The `middleware` package has two kinds of helpers.

| Type | Built from | Methods |
|---|---|---|
| `LeadershipMiddleware` | `NewLeadershipMiddleware(service, logger)` | `RequireLeader(next)`, `LeaderRedirect(next)`, `ReadOnlyRouting(next)` |
| `QuorumMiddleware` | `NewQuorumMiddleware(service, logger)` | `RequireQuorum(next)` |
| `MetricsMiddleware` | `NewMetricsMiddleware(service, logger)` | `AddConsensusHeaders(next)` |
| `ReadOnlyMiddleware` | `NewReadOnlyMiddleware(raftNode, logger)` | `Handle()`, `HandleStrict()`, `HandleWithStaleReads()` |
| `RedirectMiddleware` | `NewRedirectMiddleware(raftNode, manager, logger)` | `Handle()`, `HandleWithAutoRedirect()`, `HandleWithForward()` |
| `ConsistencyMiddleware` | `NewConsistencyMiddleware(raftNode, config, logger)` | `Handle()` |

The first three wrap a `func(forge.Context) error` and take a `ConsensusService`, such as the extension's. The leadership and quorum checks answer 503 with a JSON body when they fail, and `AddConsensusHeaders` sets `X-Consensus-Node-Id`, `X-Consensus-Term`, `X-Consensus-Role`, `X-Consensus-Leader` and related headers.

The other three take a `RaftNode`. Their methods return a check function with no `next` parameter, and when a check fails they write the JSON error and return what `ctx.JSON` returns, which is `nil` once the response is written. Your code can't tell a rejection from a pass by the return value, so treat these as unfinished.

## Admin API

The `admin` package has handlers for status and management. The extension mounts them on your app's router under `admin_api.path_prefix` (`/consensus`) when `admin_api.enabled` is on, which it isn't by default:

| Route | Handler |
|---|---|
| `GET /health`, `GET /health/detailed` | Health from the service |
| `GET /status`, `GET /leader`, `GET /nodes` | Stats, leadership and membership |
| `GET /metrics` | 404, because the extension mounts the routes without a metrics collector |
| `POST /leadership/transfer`, `POST /leadership/stepdown` | Call `TransferLeadership` and `StepDown` |
| `POST /snapshot` | Calls `Snapshot` |
| `POST /nodes/add`, `POST /nodes/remove` | Call `AddNode` and `RemoveNode` |
| `POST /apply`, `POST /read` | Call `Apply` and `Read` |

<Callout type="warn">
These routes can change membership and write to the replicated log. Whenever anyone else can reach your app's router, set `admin_api.enable_auth: true` and an `api_key`. Every route then needs `Authorization: Bearer <key>` or `X-Api-Key: <key>`, and anything else gets a 401. The key is compared in constant time, and `enable_auth` without an `api_key` fails validation.
</Callout>

If you mount the handlers yourself, use `admin.NewAPI(service, healthChecker, metricsCollector, logger, admin.WithAPIKey(key))` or `admin.NewAPIFromConfig(...)` with the extension's `AdminAPIConfig`, then `RegisterRoutes(router, prefix)`. The `api` package has more handler sets (`NewClusterAPI`, `NewConfigAPI`, `NewNodeAPI` and a stats API) built from `cluster` managers and a `RaftNode`. Nothing registers them.

## Statistics

`Service.GetStats()` returns a `ConsensusStats` with `NodeID`, `ClusterID`, `Role`, `Status`, `Term`, `LeaderID`, `CommitIndex`, `LastApplied`, `LastLogIndex`, `LastLogTerm`, `ClusterSize`, `HealthyNodes`, `HasQuorum`, `ElectionsTotal`, `ElectionsFailed`, `OperationsTotal`, `OperationsFailed`, `OperationsPerSec`, `AverageLatencyMs`, `ErrorRate`, `LogEntries`, `SnapshotsTotal`, `LastSnapshotTime`, `Uptime` and `StartTime`. The Raft fields and the cluster counts come from the running node. `ElectionsTotal`, `ElectionsFailed`, `AverageLatencyMs` and `LogEntries` aren't filled in.

The extension also implements `Metrics()` with a map of the same numbers. The service is created without a metrics sink, so the metrics collection loop it runs every `observability.metrics.collection_interval` records nothing.

## Errors

The root package re-exports these sentinels. Each is a `*errors.ForgeError` with a `CONSENSUS_*` code, so check them with `errors.Is`.

| Error | Meaning |
|---|---|
| `ErrNotLeader` | This node isn't the leader |
| `ErrNoLeader` | No leader is available |
| `ErrNotStarted`, `ErrAlreadyStarted` | Lifecycle errors from `Start` and the operations |
| `ErrNodeNotFound`, `ErrClusterNotFound` | Unknown node or cluster |
| `ErrStorageUnavailable`, `ErrTransportUnavailable`, `ErrDiscoveryUnavailable` | A backend is down |
| `ErrNoQuorum` | Not enough healthy nodes |
| `ErrInvalidTerm`, `ErrStaleTerm` | Term problems |
| `ErrLogInconsistent` | Log mismatch |
| `ErrSnapshotFailed`, `ErrCompactionFailed` | Snapshot or compaction failed |
| `ErrElectionTimeout` | Election timed out |
| `ErrInvalidPeer`, `ErrPeerExists`, `ErrPeerNotFound`, `ErrInsufficientPeers` | Peer problems |
| `ErrInvalidConfig` | Config validation failed |

The `raft`, `storage` and `transport` packages have their own sentinels, created with `errors.New`. Check them with `errors.Is` too.

| Error | Meaning |
|---|---|
| `raft.ErrProposalDropped` | A leadership change removed the entry before it committed. It wasn't applied, so you can retry |
| `raft.ErrConfigChangeInProgress` | Another membership change hasn't committed yet |
| `raft.ErrLearnerNotCaughtUp` | `AddNode` gave up because the new server didn't catch up, and removed it again |
| `raft.ErrLeadershipTransferInProgress` | The leader is handing over leadership and refuses writes and membership changes |
| `raft.ErrLeadershipTransferFailed` | The transfer target didn't take over within an election timeout. The old leader keeps leading |
| `storage.ErrInvalidEncryptionKey` | A key is missing, unreadable or not 32 bytes |
| `storage.ErrWrongKey`, `storage.ErrUnknownKeyID`, `storage.ErrDecrypt` | The configured keys don't match the store, a value uses a key that isn't configured, or a value failed authentication |
| `storage.ErrPlaintextStore`, `storage.ErrEncryptedStore` | Encryption is on over plaintext data, or off over encrypted data |
| `storage.ErrMigrationIncomplete` | An encryption migration was interrupted. Run it again |
| `consensus.ErrStorageNotEncrypted` | `ReencryptStorage` was called without encryption |
| `transport.ErrProtocolVersion`, `transport.ErrMessageTooLarge` | A peer speaks another wire protocol version, or a message is over the size limit |

| Helper | What it does |
|---|---|
| `IsNotLeaderError(err)`, `IsNoLeaderError(err)`, `IsNoQuorumError(err)`, `IsStaleTermError(err)` | `errors.Is` against the matching sentinel |
| `IsRetryable(err)` | True for no leader, no quorum, unavailable storage, transport or discovery, and timeouts |
| `IsFatal(err)` | True for invalid config and validation errors |
| `NewNotLeaderError(nodeID, leaderID)` | A not-leader error carrying both IDs |
| `NewNoLeaderError()`, `NewTimeoutError(operation)` | No-leader and timeout errors |
| `NewNoQuorumError(required, available)`, `NewStaleTermError(current, received)` | Errors carrying the counts or terms |
