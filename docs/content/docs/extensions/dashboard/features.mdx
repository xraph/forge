## The Contract

Every dashboard request goes through one endpoint, `POST {BasePath}/api/dashboard/v1`. The body is an envelope naming a contributor, an intent and its version, and the intent's kind:

```json
{
  "envelope": "v1",
  "kind": "query",
  "contributor": "core-contract",
  "intent": "services.list",
  "intentVersion": 1
}
```

A query reads, a command writes. The kind has to match the capability the intent declares, so you can't run a write intent as a query: a mismatch gets `BAD_REQUEST` before admission or any cache access. Commands also need an `idempotencyKey` and a `csrf` token, and a command missing either gets a 400.

With contract security on, a retried command with the same key gets the first answer back without running twice. The replay is bound to a digest of the request and the full principal, so the same key sent with a different payload, or by a user whose claims changed, gets `CONFLICT` with reason `idempotency.binding_conflict`. The "Generic command replay" section of the dashboard README has the binding rules and the rollout order.

### Errors and status codes

A failed envelope comes back as `{"ok":false,"envelope":"v1","error":{...}}`, with an HTTP status taken from its code. A handler error that wraps a `*contract.Error` keeps its code, a cancelled context becomes a retryable `UNAVAILABLE`, and anything else becomes `INTERNAL`.

| Code | HTTP status |
|---|---|
| `BAD_REQUEST`, `UNSUPPORTED_VERSION` | 400 |
| `UNAUTHENTICATED` | 401 |
| `PERMISSION_DENIED` | 403 |
| `NOT_FOUND` | 404 |
| `CONFLICT` | 409 |
| `RATE_LIMITED` | 429 |
| `UNAVAILABLE` | 503 |
| `INTERNAL` and any other code | 500 |

A bad CSRF token is the one exception: it carries `UNAUTHENTICATED` with a 403.

Subscriptions don't go through the POST endpoint. A client opens `GET /api/dashboard/v1/stream`, reads its stream ID from the first `hello` event, and then subscribes to intents on it through `/stream/control`.

Each intent can declare a `Requires` predicate: `all`, `any` and `not` lists of `role:X`, `scope:X` or `claim:K=V` tokens, plus an optional named warden for anything a token can't express. The transport checks it before the handler runs.

## Core Intents

The dashboard registers its own contributor, `core-contract`, with the app's data:

| Intent | Kind | What it returns |
|---|---|---|
| `overview` | query | Health status, service and metric counts, uptime |
| `health` | query | Per-service health with check results |
| `services.list` | query | Registered services and their status |
| `services.detail` | query | One service in detail |
| `metrics-report` | query | Aggregated metrics report |
| `metrics.summary` | subscription | Metric totals, pushed every few seconds |
| `traces.list` | query | Recent request traces |
| `traces.detail` | query | One trace and its spans |
| `extensions.list` | query | Every extension registered with the app |
| `apps.list` | query | Contributors that declared an app for the switcher |
| `audit.list` | query | Recorded command runs |
| `audit.tail` | subscription | Command runs as they happen |

## Contributing from an Extension

An extension adds to the dashboard in two halves. The Go half registers intents. The UI half is a React plugin, built with `definePlugin` from `@forge-go/dashboard-plugin`, that calls them.

For the Go half, implement `ContractContributorAware`. The dashboard finds it during `Start()` and hands you its dispatcher and registries:

```go
func (e *ReportsExtension) RegisterContractContributor(
    disp *dispatcher.Dispatcher,
    reg contract.Registry,
    wreg contract.WardenRegistry,
) error {
    return reportscontract.Register(disp, reg, wreg, reportscontract.Deps{
        Store: e.store,
    })
}
```

Inside `Register` you load your YAML manifest, validate it, register it, and bind a handler to each intent with `dispatcher.RegisterQuery`, `RegisterCommand` or `RegisterSubscription`. Handlers are typed: you get the decoded params and the caller's `contract.Principal`, and you return a value that becomes the response's `data`.

### Reporting Status

If your extension can be installed but not configured yet, implement `DashboardStatusAware` too:

```go
func (e *ReportsExtension) DashboardStatus() dashboard.DashboardStatus {
    return dashboard.DashboardStatus{
        Version:    "1.4.0",
        Configured: e.warehouse != nil,
        Message:    "Pick a warehouse in reports.yaml",
    }
}
```

The capabilities endpoint reports it per contributor, and the plugin host uses it to choose between rendering your plugin, a setup guide, or a version mismatch notice. Set `Configured` on every value you return. Its zero value is `false`, which asks for the setup screen.

### Remote Contributors

A contributor can live in another service. Serve its intents there with `contract/server`, which is an `http.Handler` for everything under `/_forge/contract`:

```go
srv := server.New(reg, wreg, disp, contract.NoopAuditEmitter{})
mux.Handle(srv.Prefix()+"/", srv)
```

Then register it with the dashboard:

```go
err := dashExt.RegisterRemoteContractContributor(ctx, "https://reports.internal:8443", apiKey)
```

The dashboard fetches the manifest from `/_forge/contract/manifest`, validates it, and forwards envelopes for that contributor to `/_forge/contract/dispatch`. The API key goes out as a bearer token. The end user's identity rides along in `X-Forwarded-Authorization` and `X-Forwarded-Cookie`.

### Discovering Remote Contributors

You don't have to register each service by hand. Turn discovery on and give the dashboard your discovery service:

```go
dashExt := dashboard.NewExtension(dashboard.WithDiscovery(true))

// In a PhaseAfterRegister hook, once the discovery extension is up:
dashExt.(*dashboard.Extension).SetDiscoveryService(myDiscoveryAdapter)
```

Every healthy instance registered under the `forge-dashboard-contributor` tag (change it with `WithDiscoveryTag`) is fetched and registered exactly as `RegisterRemoteContractContributor` would. If an instance carries `forge-api-key` metadata, that key is sent as its bearer token.

The dashboard checks discovery every minute by default (`WithDiscoveryPollInterval`). A service that changes its manifest is re-registered, and a service that leaves discovery is removed. When you run several replicas of one service, one of them serves the contributor at a time, and another takes over in the same pass if it goes away. The dashboard skips its own instance.

## Authentication

The dashboard doesn't sign anyone in. You give it an `AuthChecker`, and it attaches the result to every contract request:

```go
import dashauth "github.com/xraph/forge/extensions/dashboard/auth"

type MyChecker struct{ /* your auth service */ }

func (c *MyChecker) CheckAuth(ctx context.Context, r *http.Request) (*dashauth.UserInfo, error) {
    // Return nil (not an error) when nobody is signed in.
    // Return an error only for infrastructure failures.
}
```

Auth extensions do this for you by implementing `DashboardAuthAware`, which the dashboard calls during `Start()`:

```go
func (a *AuthExtension) RegisterDashboardAuth(ext *dashboard.Extension) {
    ext.SetAuthChecker(a.checker)
    ext.SetRequiredRoles(a.config.DashboardRoles)
    ext.EnableAuth()
}
```

With auth on, `/principal` answers 401 for a signed-out caller and includes the login path, so the client knows where to send them. With `RequiredRoles` set, `/principal` answers 403 for a signed-in user without one of the roles. Only `/principal` reads `RequiredRoles`; the envelope endpoint enforces each intent's `Requires` predicate instead. The login page itself belongs to your auth extension's plugin.

Handlers read the caller from the context with `dashauth.UserFromContext(ctx)`, or from the `contract.Principal` they're given.

## Security

When `EnableCSRF` and `EnableContractSecurity` are both on (the default), commands need a token from `GET /api/dashboard/v1/csrf`, and a bad token gets a 403. Contract security also turns on idempotency dedup and OpenTelemetry tracing on the dispatcher.

Every envelope is capped at `ContractMaxBodyBytes`, 1 MiB unless you change it. The cap applies before the body is decoded and before any `Requires` predicate runs, so a caller with no access at all can't make the server read an unbounded body.

## Request Tracing

The dashboard records request traces from the whole app, not just its own routes, and serves them through `traces.list` and `traces.detail`. To keep that cheap, spans are kept only while somebody is using the dashboard: a dashboard request or an open stream holds the gate open, and it shuts `TraceIdleTTL` after the last one (five minutes by default). A negative `TraceIdleTTL` keeps tracing on all the time.

Request bodies aren't captured unless you turn on `TraceCaptureRequestBody`. Even then, the body is size-limited and credential-shaped keys are redacted.

## Data Export

With `EnableExport` on, three routes serve a snapshot outside the contract:

| Endpoint | Format |
|---|---|
| `GET /export/json` | Overview, health, metrics and services as JSON |
| `GET /export/csv` | Registered services as CSV rows: name, type, status and registration time |
| `GET /export/prometheus` | Four gauges in Prometheus text format: total services, healthy services, tracked metrics and uptime |

The export routes don't run the auth middleware, even with auth on. Put them behind your own middleware, or turn export off, when the dashboard is reachable from outside. `ExportFormats` isn't read yet, so all three routes register whenever export is on.

<Callout type="info">
If you only need Prometheus scraping, forge already serves the app's metrics at `/_/metrics`. The export route is there for a one-off snapshot.
</Callout>
