<Callout type="warn" title="Removed">
The Cron extension has been removed. Use [Dispatch](https://github.com/xraph/dispatch) instead.
</Callout>

Dispatch is a durable execution engine, and distributed cron is one of the
things it does. You get leader-elected scheduling, so exactly one node in the
cluster fires a given job rather than all of them racing. You'll also get
retries with backoff, a dead letter queue for jobs that exhaust them, worker
heartbeats and work stealing, and the execution history this extension kept.

## Moving over

```bash
go get github.com/xraph/dispatch
```

Jobs are typed definitions rather than handler registrations:

```go
import (
    "github.com/xraph/dispatch"
    "github.com/xraph/dispatch/engine"
    "github.com/xraph/dispatch/job"
    "github.com/xraph/dispatch/store/memory"
)

type ReportInput struct {
    Tenant string `json:"tenant"`
}

var NightlyReport = job.NewDefinition("nightly_report",
    func(ctx context.Context, in ReportInput) error {
        return generate(ctx, in.Tenant)
    },
)
```

Inside a Forge app, register the extension and let it build the engine:

```go
import dispatchext "github.com/xraph/dispatch/extension"

app.RegisterExtension(dispatchext.New(
    dispatchext.WithStore(store),
    dispatchext.WithConcurrency(8),
))
```

Pick a store that outlives the process. `store/memory` is fine while you find
your way around. It isn't fine in production, where a schedule that resets on
every restart is not really a schedule. Postgres, SQLite, Redis and Grove
backends are all there, so pick whichever you already run.

Your cron knobs have direct equivalents. `WithCronTickInterval`,
`WithCronLeaderTTL`, `WithCronLockTTL` and `WithCronRefreshInterval` control
what this extension buried in its scheduler config, and you set them where you
register everything else rather than in a separate block.
