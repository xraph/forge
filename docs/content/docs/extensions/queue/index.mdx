## Overview

`github.com/xraph/forge/extensions/queue` puts one `Queue` interface in front of four backends:
in-memory, Redis Streams, RabbitMQ and NATS JetStream. You publish background jobs from an HTTP
handler and process them in workers, and you swap the backend by changing the driver. Your
publishing and consuming code stays the same, though the backends differ in a few corners (see
[Features](/docs/extensions/queue/features#backend-differences)).

## What It Registers

| Service | How to resolve it | Type |
|---|---|---|
| Queue service | by type, or the alias `queue` | `*queue.QueueService` |
| Queue interface | by type | `queue.Queue`, backed by the same `*QueueService` |

Get it with `queue.GetQueue(c)`, `queue.MustGetQueue(c)`, `queue.GetQueueFromApp(app)` or
`forge.Inject[queue.Queue](c)`. The extension's `Start` connects to the backend, so if the broker
isn't reachable, the app doesn't start. The queue opens every connection it uses itself and
depends on no other extension.

## Quick Start

The default driver is in-memory, so nothing else has to be running. This app queues the body of
every `POST /emails` and a worker picks each job up:

```go
package main

import (
	"context"
	"io"
	"log"
	"net/http"

	"github.com/xraph/forge"
	"github.com/xraph/forge/extensions/queue"
)

func main() {
	app := forge.NewApp(forge.AppConfig{
		Name:        "mailer",
		HTTPAddress: ":8080",
		Extensions: []forge.Extension{
			queue.NewExtension(), // in-memory driver
		},
	})

	// Declare the queue and start a worker once the extension has connected.
	err := app.RegisterHookFn(forge.PhaseAfterStart, "email-worker",
		func(ctx context.Context, a forge.App) error {
			q, err := queue.GetQueue(a.Container())
			if err != nil {
				return err
			}

			if err := q.DeclareQueue(ctx, "emails", queue.DefaultQueueOptions()); err != nil {
				return err
			}

			opts := queue.DefaultConsumeOptions()
			opts.AutoAck = true

			return q.Consume(ctx, "emails", func(ctx context.Context, msg queue.Message) error {
				log.Printf("sending email: %s", msg.Body)

				return nil
			}, opts)
		})
	if err != nil {
		log.Fatal(err)
	}

	err = app.Router().POST("/emails", func(ctx forge.Context) error {
		q, err := queue.GetQueue(app.Container())
		if err != nil {
			return err
		}

		body, err := io.ReadAll(ctx.Request().Body)
		if err != nil {
			return err
		}

		if err := q.Publish(ctx.Context(), "emails", queue.Message{Body: body}); err != nil {
			return err
		}

		return ctx.JSON(http.StatusAccepted, map[string]string{"status": "queued"})
	})
	if err != nil {
		log.Fatal(err)
	}

	if err := app.Run(); err != nil {
		log.Fatal(err)
	}
}
```

Queue a job with `curl -X POST localhost:8080/emails -d 'welcome ada@example.com'` and the worker
logs it. To move to RabbitMQ, change the extension line:

```go
queue.NewExtension(
	queue.WithDriver("rabbitmq"),
	queue.WithURL("amqp://guest:guest@localhost:5672/"),
	queue.WithPrefetch(10),
	queue.WithDeadLetter(true),
)
```

On RabbitMQ, declare the queue before you publish to it. The default exchange drops messages for
a queue that doesn't exist yet.

## Using Queue in Your Services

Take `queue.Queue` in your constructor and Vessel fills it in:

```go
type EmailWorker struct {
	queue  queue.Queue
	logger forge.Logger
}

func NewEmailWorker(q queue.Queue, logger forge.Logger) *EmailWorker {
	return &EmailWorker{queue: q, logger: logger}
}

func (w *EmailWorker) Enqueue(ctx context.Context, email Email) error {
	body, err := json.Marshal(email)
	if err != nil {
		return err
	}

	return w.queue.Publish(ctx, "emails", queue.Message{
		Body:    body,
		Headers: map[string]string{"type": "transactional"},
	})
}

func (w *EmailWorker) Start(ctx context.Context) error {
	opts := queue.DefaultConsumeOptions()
	opts.AutoAck = true

	return w.queue.Consume(ctx, "emails", w.processEmail, opts)
}

func (w *EmailWorker) processEmail(ctx context.Context, msg queue.Message) error {
	var email Email
	if err := json.Unmarshal(msg.Body, &email); err != nil {
		return err // goes to the dead-letter queue on in-memory and Redis
	}

	return send(ctx, email)
}
```

Register it with Vessel:

```go
forge.ProvideConstructor(app.Container(), NewEmailWorker)
```

Return an error from the handler to fail a message and `nil` to succeed. On Redis, RabbitMQ and
NATS the consumer loop acknowledges for you based on that return value.

<Callout type="warn">
`Ack`, `Nack` and `Reject` only do something on the in-memory driver. On Redis, RabbitMQ and NATS
they return `nil` and change nothing. On the in-memory driver with `AutoAck` off, a message your
handler succeeds on stays in flight until you call `Ack(ctx, msg.ID)`.
</Callout>

## Key Concepts

- Drivers: pick `inmemory`, `redis`, `rabbitmq` or `nats` with `WithDriver` or the `driver` key. Each implements the same `Queue` interface.
- Queue declaration: `DeclareQueue` with `QueueOptions`. RabbitMQ honours durability, auto-delete, exclusive, TTL, max length, max priority and a dead-letter queue. NATS maps max length and TTL onto the stream. Redis and in-memory ignore most of the options.
- Publishing: single messages, batches, and delayed messages. Delayed publishing works differently on every backend and doesn't deliver at all on Redis yet.
- Consuming: a handler function per queue, with prefetch, concurrency (in-memory only) and a per-message timeout (RabbitMQ and NATS).
- Dead letters: failed messages land in a dead-letter list on in-memory and Redis, and RabbitMQ dead-letters through the broker when the queue has `DeadLetterQueue` set.

## Important Runtime Notes

- The Redis backend uses Redis Streams, one stream per queue (`queue:<name>:stream`) with the consumer group `consumers`, over a connection the queue opens itself.
- `Message.Retries` is never incremented. On RabbitMQ and NATS a message with `MaxRetries` above zero keeps coming back until your handler succeeds.
- `ConsumeOptions.RetryStrategy` isn't read by any driver.
- `Stats` and `GetQueueInfo` fill counts (queues, messages, consumers) and uptime. The rate fields, `MemoryUsed`, `UnackedMessages` and `ReadyMessages` are always zero, and RabbitMQ's `Stats` reports zero queues and messages.
- `Health` on the extension reports whether it started. `QueueService.Health` pings the backend.
