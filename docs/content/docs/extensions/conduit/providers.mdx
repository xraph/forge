title: Broker providers
description: Choose NATS JetStream, Redis Streams, PostgreSQL or Kafka with explicit durability and recovery guarantees
---

You can supply a provider in Go or choose its type in Forge configuration. Your event handlers keep the same API.

| Provider       | Durable acceptance                     | Event cursors                                  | Dead letters            | Broker RPC                 | Pause and backfill     | Discovery              |
| -------------- | -------------------------------------- | ---------------------------------------------- | ----------------------- | -------------------------- | ---------------------- | ---------------------- |
| NATS JetStream | File store with configured replicas    | Native stream sequence                         | Persisted KV records    | Native request/reply       | Supported              | Leased KV records      |
| Redis Streams  | Confirmed local and replica AOF writes | Per-stream sequence and consumer groups        | Persisted Redis records | Request and reply streams  | Supported              | Leased keys            |
| PostgreSQL     | Committed transaction                  | Per-stream sequence, read in commit-safe order | Rows                    | Request rows with NOTIFY   | Supported              | Leased rows            |
| Kafka          | All configured in-sync replicas        | One-based offsets in one partition             | Retained failure log    | Unsupported                | Unsupported            | Use Forge discovery    |
| Memory         | Process memory                         | Process-local retained records                 | Process-local records   | Development implementation | Process-local controls | Process-local leases   |

All providers support competing and broadcast subscriptions. None promises ordered business processing by message key.

JetStream, Redis Streams and PostgreSQL report the same capabilities and pass the same conformance groups, so you can choose by what you already run. JetStream handles the most traffic and clusters natively. Redis Streams suits you if Redis is already in your stack. PostgreSQL adds no infrastructure at all and lets you publish in the same transaction as your business write.

## NATS JetStream

```go
broker := jetstream.New(jetstream.Options{
    URL: "nats://localhost:4222",
    DeadLetterReplicas: 3,
})
```

Set stream `Replicas` to your required replication factor. Stream settings are verified on startup. You can use native `NATS` options for authentication and TLS. JetStream also supplies leased service discovery records.

`Options.LeaseTTL` has to match the TTL of a discovery bucket that already exists (`FC_DISC_*`). A different value returns a conflict from every registry call, so check the bucket before you change the lease.

## Redis Streams

```go
broker := redisstreams.New(redisstreams.Options{
    URL: "redis://localhost:6379",
})
```

You'll need Redis 7.2 or later with AOF enabled. Publication uses `WAITAOF` on the same connection as the write. `Replicas` counts the primary plus the required AOF-confirming replicas. Missing replica confirmation returns `ErrOutcomeUnknown`. `PersistenceTimeout` defaults to five seconds and accepts values up to one minute. Your caller context can set a shorter deadline.

The adapter supports age and message-count retention. Competing replicas share a consumer group; durable broadcast has a group per stable subscriber. Pending messages can be claimed after the handler timeout plus five seconds. Retry delays use the same broker-owned pending entries.

Publication IDs are deduplicated for 24 hours by default. Set `DeduplicationWindow` to change that window. Native `redis.Options` lets you configure TLS and authentication. This adapter targets a primary/replica Redis deployment; it does not create a Redis Cluster or Sentinel client.

Pause, backfill progress, discovery leases and RPC requests use the same Redis server. RPC requests and replies skip `WAITAOF`: they're transient, so a failover can drop an in-flight call and its caller then sees `DEADLINE_EXCEEDED`. A call to a procedure nobody serves also ends at its deadline.

RPC holds at most two pooled connections blocked, however many procedures you serve: one in `XREADGROUP` for serving, which reads every procedure's requests at once, and one waiting for replies on a provider that calls procedures. Everything else RPC does, like taking a request, writing a reply or sending a call, borrows a pooled connection for a round trip. Leave room for the two blocked ones when you set `PoolSize` in `Options.Redis` (or `pool_size` in the URL). A procedure you start serving joins that read within a quarter of a second. When you close a server, a request the reader picked up in that last quarter second goes to another server for the same procedure on the same provider, if there is one. Otherwise it gets `UNAVAILABLE`, and your caller can retry it on another replica.

## PostgreSQL

```go
broker := postgres.New(postgres.Options{
    URL: "postgres://localhost:5432/billing",
})
```

You'll need PostgreSQL 13 or later. Pass `Pool` instead of `URL` to share your application's pool; closing the provider leaves it open. `Migrate` creates the `forge_conduit_` tables, and `Migrations(schema)` returns the same statements for a central migration runner. Set `AutoMigrate` to run `Migrate` on connect. Providers built from Forge configuration (`type: postgres`) do this for you.

`Migrate` and `AutoMigrate` create whatever is missing and do nothing when the schema is current, so they don't take table locks on a database that's already migrated. Only the first deploy, or a release that adds tables or indexes, needs a role that can create and own the `forge_conduit_` tables. Your runtime role needs:

- `USAGE` on the schema
- `SELECT`, `INSERT`, `UPDATE` and `DELETE` on the `forge_conduit_` tables
- `USAGE` and `UPDATE` on the `forge_conduit_seq_` sequences, one per stream

`ALTER DEFAULT PRIVILEGES` saves you granting the sequences one by one. Declaring a new stream creates its sequence, which needs `CREATE` on the schema, so either give the runtime role that or declare the stream once as the owner. Creating the schema needs no database-level `CREATE` privilege when the schema already exists.

Use `PublishTx` to publish inside your own transaction. Subscribers see the message, and wake for it, only when you commit. A rollback leaves nothing behind. `SQLTx` adapts a `database/sql` transaction.

A stream with `MaxMessages` trims its old rows inside each publish. A long-running `PublishTx` on a capped stream therefore makes other publishers to that stream wait for your commit, so keep those transactions short. Rolled-back and duplicate publishes leave gaps in the sequence, and the cap counts sequence numbers, so the stream keeps slightly fewer rows than you configured.

The provider keeps one dedicated connection for `LISTEN`. PgBouncer in transaction mode loses `LISTEN` registrations, so if your `Pool` goes through it, set `URL` as well and point it straight at PostgreSQL: with `Pool` set, `URL` is only used for the listener. Hooks on your pool, such as `BeforeConnect` for IAM tokens, don't apply to the listener. When the listener is down, delivery carries on by polling every `PollInterval` (one second by default) and `ListenerConnected` reports `false`. Set `Logger` and you'll hear about it: a failed connect or a dropped connection logs at Warn (repeated failures at most once per backoff step, then every 30 seconds), and the reconnect logs at Info.

Delivery takes an advisory lock per consumer group. It holds no row locks, and an idle subscriber doesn't use a transaction ID. An idle subscriber polls at `PollInterval`. While committed rows wait behind the oldest open transaction, the provider re-polls after 50ms, then doubles the wait each time up to `PollInterval`. After that transaction ends, delivery lags by at most the current wait, so a short transaction costs you about 50ms and a long one up to `PollInterval`.

Plan for the load on your database. Every publish sends a `NOTIFY` that wakes each worker calling `Next` on that stream, and each worker holds a pooled connection while it takes a message. An idle worker runs one short read-only transaction per `PollInterval`. PostgreSQL also serializes the commits of transactions that sent a `NOTIFY` across every database in the cluster, so publishing commits queue behind each other, and behind any other application on that cluster that uses `NOTIFY`. Size the pool for `Concurrency` times your subscriptions, plus what your application needs. To measure your own setup, point `CONDUIT_TEST_POSTGRES` at a scratch database on the same kind of server you'll run in production and run `go test -run '^$' -bench . -benchtime=2000x ./providers/postgres` from `extensions/conduit`. `BenchmarkPublish` and `BenchmarkPublishParallel` time publishing from one and from many goroutines, and `BenchmarkPublishAndDeliver` reports `msgs/s` from publish to ack for one competing subscription with four workers on two providers. The benchmarks create the `forge_conduit_` tables and leave their rows behind, so don't point them at a database you care about. Your numbers will follow the database's commit latency, so measure on the hardware and storage you'll deploy to.

Two behaviours differ from JetStream. Sequence numbers rise for each publisher, but with several publishers delivery follows commit order, so a consumer can see 42 before 41. And a transaction left open anywhere in the cluster holds delivery back until it ends, because a consumer never reads past the oldest open transaction. `VisibilityLag` tells you how long the oldest one has been open. It reads `pg_stat_activity`, so the role needs `pg_read_all_stats` (or `pg_monitor`) to see other roles' transactions, and prepared transactions aren't counted. RPC costs about two commits per call, and a call to a procedure nobody serves ends at its deadline.

Cursors store transaction IDs from the cluster that wrote them. `pg_upgrade` keeps those IDs, but a dump and restore, logical replication or a Blue/Green major upgrade can start the new cluster from lower ones, and new messages would then sit behind every cursor. `Subscribe` refuses with "consumer cursor is ahead of this cluster's transaction IDs" when that happens. To repair it, call `Rebase` once on the copy before you start your subscribers. It moves the old cluster's rows to the front of the log and sends each affected consumer back to its oldest retained message, so those messages get delivered again, including ones that were in flight. Your handlers have to tolerate the duplicates. On a healthy database `Rebase` changes nothing. It takes every consumer's delivery lock in one transaction, so if you have thousands of consumers, raise `max_locks_per_transaction` first. It can also fail on a deadlock with the retention sweep. Nothing is changed when it fails, so run it again.

## Kafka

```go
broker := kafka.New(kafka.Options{
    Brokers: []string{"kafka-1:9092", "kafka-2:9092"},
    DeadLetterReplicas: 3,
})
```

Each Conduit stream has one partition. A competing group therefore has one active replica, with other replicas available for failover. Broadcast groups have independent offsets. The adapter settles one event before fetching the next, preventing a later commit from skipping an earlier failure.

Set stream `Replicas` to the topic replication factor. The adapter requires the same `min.insync.replicas` and uses all-replica acknowledgements. Age retention is supported; `MaxMessages` returns `ErrUnsupported` because Kafka has no equivalent message-count retention guarantee. Physical log cleanup follows the broker's segment retention schedule, and consumers skip expired records.

Topology declarations are stored in immutable companion topics. If a process creates a declaration topic and crashes before writing its declaration, startup fails closed. Repair that empty declaration topic before retrying. Subscriber and declaration topics need an operator cleanup policy when you retire services or ephemeral instances.

Use native `Transport` or `Dialer` options for TLS and SASL. Kafka does not deduplicate stable application message IDs, and retries can restart their attempt count after a rebalance. Use the PostgreSQL inbox for effects that must survive duplicate deliveries.

Dead letter listings fold a retained service-specific failure log. Listing cost grows with that log. Concurrent replay commands can produce duplicates, with the original message ID preserved.

## Add a provider

Implement `core.Provider`, then report only guarantees your adapter provides through `Capabilities`. Add `core.Management` for inspection and dead letter recovery, `core.Registry` for discovery, `core.RPCProvider` for request/reply, or `core.Operations` for consumer controls and backfill.

Run `providers/conformance.Run` against a factory that creates connections to the same real broker. The suite checks competing replicas, broadcast, namespace isolation, restart cursors, unsettled takeover, retries, targeted recovery, topology conflicts, sequence starts and age retention. It then runs a group for each capability you claim: `operations` for consumer controls, `backfill`, `rpc`, and `registry` when you implement `core.Registry`. Pass `conformance.WithLeaseTTL` with the lease your factory's providers use. The `operations` group doesn't assume a retried message comes back before newer ones, so your provider can redeliver it later.

Redis, PostgreSQL and Kafka conformance tests run in the required Conduit integration CI job. You can run them locally with `CONDUIT_TEST_REDIS`, `CONDUIT_TEST_POSTGRES` and `CONDUIT_TEST_KAFKA`; `CONDUIT_REQUIRE_PROVIDERS=1` makes missing broker configuration fail the check.
