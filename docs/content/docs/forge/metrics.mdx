Forge includes a built-in metrics system for collecting counters, gauges, and histograms. Metrics are exposed via the `/_/metrics` endpoint in Prometheus format and can be exported to various backends.

## Metrics Endpoint

The metrics endpoint is available at:

```
GET /_/metrics
```

It returns metrics in Prometheus exposition format by default, and in OpenMetrics when the scraper asks for it (Prometheus does). That matters for [exemplars](#exemplars).

## Metrics Interface

The `Metrics` interface provides methods for creating and managing metrics.

```go
type Metrics interface {
    // Counter creates or retrieves a counter metric
    Counter(name string, opts ...MetricOption) Counter

    // Gauge creates or retrieves a gauge metric
    Gauge(name string, opts ...MetricOption) Gauge

    // Histogram creates or retrieves a histogram metric
    Histogram(name string, opts ...MetricOption) Histogram
}
```

## Metric Types

### Counter

A monotonically increasing value. Use counters for request counts, error counts, bytes processed, etc.

```go
func handler(ctx forge.Context) error {
    metrics := app.Metrics()

    // Create/get a counter
    requestCounter := metrics.Counter("http_requests_total",
        forge.WithLabel("method", "GET"),
        forge.WithLabel("path", "/api/users"),
    )

    // Increment
    requestCounter.Inc()

    // Read current value
    total := requestCounter.Value()

    return ctx.JSON(200, map[string]any{
        "total_requests": total,
    })
}
```

### Gauge

A value that can go up or down. Use gauges for current connections, queue depth, temperature, etc.

```go
func trackConnections(metrics forge.Metrics) {
    activeConnections := metrics.Gauge("active_connections",
        forge.WithLabel("protocol", "websocket"),
    )

    // Set to an absolute value
    activeConnections.Set(42)

    // Add (can be positive or negative)
    activeConnections.Add(1)   // increment
    activeConnections.Add(-1)  // decrement

    // Read current value
    current := activeConnections.Value()
    fmt.Printf("Active connections: %f\n", current)
}
```

### Histogram

Records distributions of values. Use histograms for request durations, response sizes, etc.

```go
func handler(ctx forge.Context) error {
    metrics := app.Metrics()

    duration := metrics.Histogram("request_duration_seconds",
        forge.WithLabel("handler", "createUser"),
    )

    start := time.Now()
    defer func() {
        elapsed := time.Since(start).Seconds()
        duration.Observe(elapsed)
    }()

    // ... handler logic

    return ctx.JSON(200, result)
}
```

## Labels

Add dimensional labels to metrics for filtering and grouping.

```go
// Single label
counter := metrics.Counter("api_calls",
    forge.WithLabel("service", "user-api"),
)

// Multiple labels
counter := metrics.Counter("api_calls",
    forge.WithLabels(map[string]string{
        "service": "user-api",
        "method":  "POST",
        "status":  "200",
    }),
)
```

## Label Vectors

`forge.WithLabel` works, but it does a registry lookup on every call, and nothing stops two call sites from spelling a label name differently. For anything on a hot path, declare the metric once with its label names and fetch children with `With`.

```go
type Orders struct {
    created *forge.Vec[forge.Counter]
    latency *forge.Vec[forge.Histogram]
}

func NewOrders(m forge.Metrics) *Orders {
    return &Orders{
        created: forge.CounterVec(m, "orders_created_total", "tier", "region"),
        latency: forge.HistogramVec(m, "checkout_duration_seconds",
            forge.HistogramOpts{
                Buckets: []float64{0.05, 0.1, 0.25, 0.5, 1, 2.5},
                Help:    "Time to complete a checkout.",
            },
            "tier",
        ),
    }
}

func (o *Orders) Record(tier, region string, took time.Duration) {
    o.created.With(tier, region).Inc()
    o.latency.With(tier).Observe(took.Seconds())
}
```

`forge.GaugeVec` has the same shape as `CounterVec`. Pass the values to `With` in the order you declared the names. Children are cached, so repeat calls skip the registry.

Get the count wrong and Forge doesn't panic. It logs one error for that vector, drops the sample and hands you a throwaway metric so your code keeps running. That is the right call in production and a bad one in a test, where a dropped sample means a missing number you only notice on a dashboard. Call `StrictMetrics` at the top of the test and the same mistake fails it:

```go
import forgetesting "github.com/xraph/forge/testing"

func TestRecord(t *testing.T) {
    forgetesting.StrictMetrics(t)

    o := NewOrders(forgetesting.NewNoOpMetrics())
    o.Record("pro", "eu", 120*time.Millisecond) // fine
    o.created.With("pro").Inc()                  // test error: got 1 label values, want 2
}
```

Children made through `.WithLabels(...)` on a metric you got from `app.Metrics()` are registered and exported too. Labels still multiply, so keep user IDs, request IDs and raw paths out of them. See [Series cap](#series-cap) for what happens when you don't.

## MetricsConfig

Configure metrics collection behavior.

```go
app := forge.New(
    forge.WithAppMetricsConfig(forge.MetricsConfig{
        Enabled: true,
        Features: forge.MetricsFeatures{
            SystemMetrics:  true,  // OS-level metrics (CPU, memory, disk)
            RuntimeMetrics: true,  // Go runtime metrics (goroutines, GC)
            HTTPMetrics:    true,  // Request duration and active requests
            HTTPBodySizes:  false, // Also record request and response body sizes
        },
        Collection: forge.MetricsCollection{
            Interval:  10 * time.Second,  // Collection interval
            Namespace: "myapp",           // Prefix for your own metrics
            Path:      "/_/metrics",      // Endpoint path
            DefaultTags: map[string]string{
                "environment": "production",
                "service":     "user-api",
            },
        },
        Exporters: map[string]forge.MetricsExporterConfig[map[string]any]{
            "prometheus": {
                Enabled: true,
                Format:  "prometheus",
            },
        },
        Limits: forge.MetricsLimits{
            MaxMetrics:         10000, // Maximum number of unique metrics
            BufferSize:         1000,  // Internal buffer size
            MaxSeriesPerMetric: 2000,  // Label sets one metric name may hold
        },
    }),
)
```

The same settings in a config file:

```yaml
metrics:
  enabled: true
  features:
    http_metrics: true
    http_body_sizes: true
  limits:
    max_series_per_metric: 2000
```

If you don't call `WithAppMetricsConfig`, Forge starts from `DefaultMetricsConfig()` and every key you put in the file replaces its default, so `http_metrics: false` or `namespace: myapp` in the file takes effect. If you do call it, your code wins: the file is read only when it says `enabled: true`, and it can't turn off anything code turned on.

### Default Configuration

```go
config := forge.DefaultMetricsConfig()
// Returns:
// - Enabled: true
// - System, runtime and HTTP metrics: enabled
// - HTTP body sizes: disabled (opt-in)
// - Collection interval: 10s
// - Namespace: "forge"
// - Path: /_/metrics
// - MaxMetrics: 10000
// - BufferSize: 1000
// - MaxSeriesPerMetric: 0, which means 2000
```

## Built-in Metric Types

When enabled in `MetricsFeatures`, Forge automatically collects:

### System Metrics (`SystemMetrics: true`)

- CPU usage
- Memory usage (RSS, heap)
- Disk I/O
- Network I/O

### Runtime Metrics (`RuntimeMetrics: true`)

- `go_goroutines` -- number of goroutines
- `go_gc_duration_seconds` -- GC pause duration
- `go_memstats_alloc_bytes` -- heap allocation
- `go_memstats_heap_objects` -- number of heap objects

### HTTP Metrics (`HTTPMetrics: true`)

Forge records the OpenTelemetry HTTP server metrics for every request, keyed by the route pattern you registered (`/users/:id`), never the raw path. The recorder sits inside tracing and outside your extensions' middleware, so a request that an auth extension rejects with a 401 is still counted.

| Series | Type | Labels |
|--------|------|--------|
| `http_server_request_duration_seconds` | histogram, buckets 0.005 to 10 s | `http_request_method`, `http_route`, `http_response_status_code`, `url_scheme`, `error_type` |
| `http_server_active_requests` | gauge | `http_request_method`, `url_scheme` |
| `http_server_request_body_size_bytes` | histogram, only with `http_body_sizes` | same as duration |
| `http_server_response_body_size_bytes` | histogram, only with `http_body_sizes` | same as duration |

Three queries cover most dashboards.

```promql
# Requests per second, by route
sum by (http_route) (rate(http_server_request_duration_seconds_count[5m]))

# Share of requests that returned a 5xx
sum(rate(http_server_request_duration_seconds_count{http_response_status_code=~"5.."}[5m]))
  / sum(rate(http_server_request_duration_seconds_count[5m]))

# p95 latency, by route
histogram_quantile(0.95,
  sum by (le, http_route) (rate(http_server_request_duration_seconds_bucket[5m])))
```

A few details that change how you read the numbers:

- `http_route` is empty for requests that matched no route, so a scanner hammering `/wp-admin` lands under one empty route instead of making a series per path it tries.
- Methods outside the standard nine (GET, HEAD, POST, PUT, DELETE, CONNECT, OPTIONS, TRACE, PATCH) are recorded as `_OTHER`.
- `error_type` is the status code (`"503"`) for 5xx responses and empty otherwise.
- Paths under the tracing `exclude_paths` (default `/_/`) are not recorded, so scraping `/_/metrics` doesn't count itself.
- The request body size is only observed when the request carries a `Content-Length`.

These names are never prefixed. Your own metrics keep the `forge_` prefix, or whatever you set in `metrics.collection.namespace`, and the `go_` and `process_` runtime series stay unprefixed as before.

Turn on the body size histograms with `metrics.features.http_body_sizes: true`. They're off by default because each one adds a full set of buckets per route and status.

#### Exemplars

The duration histogram carries `trace_id` and `span_id` exemplars for sampled requests, so you can jump from a slow bucket to the trace that landed in it. Exemplars only exist in the OpenMetrics format, which Prometheus asks for on its own. A plain `curl` of `/_/metrics` won't show them unless you send `Accept: application/openmetrics-text`.

Prometheus has to be started with `--enable-feature=exemplar-storage` or it throws them away. In Grafana you switch on the Exemplars toggle per query, on the latency query. The link from `trace_id` to your tracing data source isn't set on the panel. It lives in the Prometheus data source settings, in the Exemplars section. Requests that tracing didn't sample have no exemplar.

#### Series cap

Every distinct label set is a series, and a label fed by user input will eventually find a way to make millions of them. `metrics.limits.max_series_per_metric` (default 2000, and 0 means the default) stops that. Once a metric name holds that many label sets, new ones fold into a single series and Forge logs one warning for that metric.

Here `orders_total` has a `tier` label and a cap of 1. `free` got in first, then `pro` was incremented once and `team` once:

```
forge_orders_total{otel_metric_overflow="",tier="free"} 1
forge_orders_total{otel_metric_overflow="true",tier=""} 2
```

The overflow series has `otel_metric_overflow="true"` and every other label empty, and the series under the cap carry `otel_metric_overflow=""`. The counts are right and the detail is gone. If you see it on a dashboard, find the label that has too many values and fix that. Raising the cap only moves the problem.

`metrics.limits.max_metrics` (default 10000) caps the whole registry, every series of every metric counted. Past it, a new metric or label set still gives you a handle you can call, but nothing it records reaches the scrape, and Forge logs one warning.

#### Moving from the old series

Earlier releases exposed a flat set of `forge_http_*` series, with a gauge per path, status and method. Those are gone, along with the `track_paths`, `group_similar_paths` and path allow and block list settings. Remove them from your config. With the route as a label you don't need them.

| Old | New |
|-----|-----|
| `forge_http_requests_total` | `http_server_request_duration_seconds_count` |
| `forge_http_request_duration_*` | `http_server_request_duration_seconds_*` |
| `forge_http_requests_active` | `http_server_active_requests` |
| `forge_http_request_size_*` | `http_server_request_body_size_bytes_*` (needs `http_body_sizes`) |
| `forge_http_response_size_*` | `http_server_response_body_size_bytes_*` (needs `http_body_sizes`) |
| `forge_http_requests_status_200`, `..._404` and so on | label `http_response_status_code` |
| `forge_http_requests_method_GET`, `..._POST` and so on | label `http_request_method` |
| `forge_http_requests_path_*` | label `http_route` |
| `forge_http_requests_error_rate` | the 5xx ratio query above |
| `forge_http_requests_avg_duration`, `forge_http_response_avg_size` | `rate(..._sum[5m]) / rate(..._count[5m])` |

The old duration histogram used buckets from 5 to 10000 while recording seconds, so nearly every request landed in the first bucket and its quantiles told you nothing. Don't try to carry old panels over by renaming. Rebuild them from the queries above.

## Custom Metrics in Handlers

```go
func createOrder(ctx forge.Context) error {
    metrics := app.Metrics()

    // Track order creation
    orderCounter := metrics.Counter("orders_created_total",
        forge.WithLabel("source", ctx.Header("X-Source")),
    )

    orderValue := metrics.Histogram("order_value_dollars")

    // ... create order
    order, err := orderService.Create(ctx.Request().Context(), req)
    if err != nil {
        metrics.Counter("orders_failed_total").Inc()
        return forge.InternalError(err)
    }

    orderCounter.Inc()
    orderValue.Observe(order.Total)

    return ctx.JSON(201, order)
}
```

## Metrics in Extensions

Extensions can record metrics through the `Metrics` accessor on `BaseExtension`.

```go
type CacheExtension struct {
    *forge.BaseExtension
}

func (e *CacheExtension) Start(ctx context.Context) error {
    e.BaseExtension.Start(ctx)

    // Use extension's metrics
    hits := e.Metrics().Counter("cache_hits_total")
    misses := e.Metrics().Counter("cache_misses_total")
    latency := e.Metrics().Histogram("cache_latency_seconds")

    // ... use in cache operations
    return nil
}
```

## Export Formats

Forge supports multiple export formats:

| Format | Constant | Description |
|--------|----------|-------------|
| Prometheus | `ExportFormatPrometheus` | Standard Prometheus exposition format |
| JSON | `ExportFormatJSON` | JSON format for custom consumers |
| InfluxDB | `ExportFormatInflux` | InfluxDB line protocol |
| StatsD | `ExportFormatStatsD` | StatsD format |

## Complete Example

```go
package main

import (
    "time"

    "github.com/xraph/forge"
)

func main() {
    app := forge.New(
        forge.WithAppName("metrics-demo"),
        forge.WithAppMetricsConfig(forge.MetricsConfig{
            Enabled: true,
            Features: forge.MetricsFeatures{
                RuntimeMetrics: true,
                HTTPMetrics:    true,
            },
            Collection: forge.MetricsCollection{
                Interval:  10 * time.Second,
                Namespace: "demo",
                Path:      "/_/metrics",
                DefaultTags: map[string]string{
                    "environment": "development",
                },
            },
        }),
    )

    r := app.Router()
    m := app.Metrics()

    // Custom application metrics
    activeUsers := m.Gauge("active_users")
    requestLatency := m.Histogram("business_logic_duration_seconds")

    r.GET("/api/dashboard", func(ctx forge.Context) error {
        start := time.Now()
        defer func() {
            requestLatency.Observe(time.Since(start).Seconds())
        }()

        activeUsers.Set(float64(getUserCount()))

        return ctx.JSON(200, map[string]any{
            "activeUsers": activeUsers.Value(),
        })
    },
        forge.WithTags("dashboard"),
    )

    app.Run()
}
```

Access the Prometheus-formatted metrics at `GET /_/metrics` and scrape them with your preferred monitoring stack.
