Forge gives you structured logging, OpenTelemetry tracing and a set of built-in diagnostic endpoints. Tracing is on from the first request and logs pick up its trace and span IDs; sending spans to a collector takes one environment variable. To see all of it in a local Grafana, follow [Grafana in five minutes](/docs/forge/grafana-in-five-minutes).

## Structured Logging

Forge's logging system provides high-performance, structured logging with multiple output formats.

### Log Levels

```go
const (
    forge.LevelDebug // Detailed debugging information
    forge.LevelInfo  // General operational information
    forge.LevelWarn  // Warning conditions
    forge.LevelError // Error conditions
    forge.LevelFatal // Fatal errors (causes shutdown)
)
```

### Structured Fields

Forge provides typed field constructors for structured logging. Fields are type-safe and optimized for zero-allocation logging.

```go
logger.Info("user created",
    forge.String("user_id", "usr_123"),
    forge.String("email", "alice@example.com"),
    forge.Int("age", 30),
    forge.Duration("latency", 15*time.Millisecond),
)

logger.Error("database query failed",
    forge.Error(err),
    forge.String("query", "SELECT * FROM users"),
    forge.Int("retry_count", 3),
    forge.Stack(),
)
```

### Field Types

| Constructor | Type | Example |
|-------------|------|---------|
| `forge.String(key, val)` | string | `forge.String("name", "alice")` |
| `forge.Int(key, val)` | int | `forge.Int("count", 42)` |
| `forge.Int64(key, val)` | int64 | `forge.Int64("bytes", 1048576)` |
| `forge.Float64(key, val)` | float64 | `forge.Float64("ratio", 0.95)` |
| `forge.Bool(key, val)` | bool | `forge.Bool("active", true)` |
| `forge.Time(key, val)` | time.Time | `forge.Time("created", time.Now())` |
| `forge.Duration(key, val)` | time.Duration | `forge.Duration("elapsed", 2*time.Second)` |
| `forge.Error(err)` | error | `forge.Error(err)` |
| `forge.Any(key, val)` | any | `forge.Any("data", myStruct)` |
| `forge.Stack()` | stack trace | `forge.Stack()` |
| `forge.Strings(key, val)` | []string | `forge.Strings("tags", tags)` |

### Performance Tracking

Use `Track` to measure and log function execution time:

```go
func processOrder(ctx context.Context) error {
    defer forge.Track(logger, "processOrder")()

    // ... processing logic

    return nil
}
// Logs: "processOrder completed" duration=145ms

// With additional fields
defer forge.TrackWithFields(logger, "processOrder",
    forge.String("order_id", orderID),
)()
```

### Export logs over OTLP

Set the same endpoint variable you used for spans and restart.

```bash
OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318 ./my-app
```

That alone is enough. Forge appends `/v1/logs` to the value, and every line the app's logger writes now also goes to the collector. That includes the boot lines, from extension registration onwards. Lines written before the app is built, while your own code loads config say, only reach stderr. If your logs live behind a different URL, set `OTEL_EXPORTER_OTLP_LOGS_ENDPOINT` and it's used exactly as written. Headers come from `OTEL_EXPORTER_OTLP_LOGS_HEADERS`, or from `OTEL_EXPORTER_OTLP_HEADERS` when that isn't set, and are percent-encoded the way they are for spans.

The transport is OTLP over HTTP with protobuf bodies, same as tracing, so point it at the collector's HTTP port (4318 by default, never the gRPC one) and give it a full `http` or `https` URL. A bad endpoint logs one error. The app still boots.

#### Configuration

Every key is optional. This is the `logs_export:` block:

```yaml
logs_export:
  enabled: true      # false: no export, even when OTEL_* sets an endpoint
  endpoint: ""       # full OTLP/HTTP logs URL; empty falls back to OTEL_* env
  headers: {}        # sent with every export request
  level: ""          # debug, info, warn, error or fatal; empty exports every line
```

The first of these wins, as it does for tracing and profiling:

1. Code: `forge.WithAppLogsExportConfig`
2. The `logs_export:` block in your Forge config file
3. `OTEL_*` environment variables
4. The defaults

```go
app := forge.New(
    forge.WithAppName("user-api"),
    forge.WithAppLogsExportConfig(forge.LogsExportConfig{
        Endpoint: "https://collector.internal:4318/v1/logs",
        Headers:  map[string]string{"Authorization": "Bearer <token>"},
        Level:    "info",
    }),
)
```

`level` only narrows. It drops lines below it before they are converted, but it can't export a line your logger already decided not to write, so a logger set to `info` never sends debug lines whatever `level` says.

To turn export off, set `OTEL_LOGS_EXPORTER=none` or `enabled: false`. The file or code value wins over the environment, so `enabled: false` stays off even with an endpoint set. `OTEL_SDK_DISABLED=true` stops it too, unless `enabled` says otherwise. A list that leaves out `otlp` counts as off. Setting `enabled: true` with no endpoint anywhere logs a warning and exports nothing.

#### What a record carries

Each log line becomes one OTLP log record. The message is the body, the level becomes the severity (debug 5, info 9, warn 13, error 17, fatal 21), and your fields become attributes. The resource is the one your spans use, so `service.name`, `service.version` and `deployment.environment.name` match across all three signals.

A logger you got from a request carries `trace_id` and `span_id`. On the exported record those become the record's own trace and span IDs rather than ordinary attributes, which is what lets Grafana link a log line to its trace and back. If either ID is missing or isn't valid hex, both stay plain attributes.

The instrumentation scope is the path you built with `Named`, or `forge` for a logger with no name. Each line also gets `code.file.path` and `code.line.number` from its caller.

Forge keeps a scope for at most 256 distinct names. That's plenty for packages and services. A `Named` call with a user ID in it would otherwise grow the cache for as long as the process runs, which is the one thing a log pipeline mustn't do. Past 256, a line from a new name goes out under scope `forge` and carries its name as a `logger.name` attribute instead. Names already cached keep their scope.

#### Before you rely on it

Export doesn't replace anything. Lines still go to stderr in the format they always had, and they go to the collector as well. Scrape stdout into the same Loki already? Then you'll see every line twice until you drop one of the two paths.

Export ships exactly what stderr shows, error text included. The redaction rules that keep values off your spans don't apply to logs, so if an error message can hold something sensitive, scrub it in a collector processor before it reaches storage.

Logging never waits on the collector. Lines go into a queue (2048 records by default) and are sent in batches, and when the queue fills, the oldest lines drop. So the tail of the output can go missing if the process dies. `app.Stop` exports what is queued before it returns, a `Start` that fails flushes first so the lines that explain the failure leave before you exit on the error, and `Fatal` waits up to two seconds for the same reason. An app that never reaches `Stop` loses whatever hadn't been sent yet. Think of a process killed by a signal you don't handle.

Export needs Forge's own logger. If you pass a custom `Logger`, Forge logs a warning at boot and sends nothing.

With `forge dev -O` running, the lines show up in Loki, and the **Logs for this span** link on a trace in Tempo opens the ones from that request. [Grafana in five minutes](/docs/forge/grafana-in-five-minutes) walks through the stack.

## Distributed Tracing

Tracing is on by default. Start an app and send it a request: Forge has already opened a server span for that request, stamped `trace_id` and `span_id` on every log line written through the request's logger, and put a `traceparent` header on the response. Nothing leaves the process until you give it an endpoint.

### Export spans

Point Forge at an OTLP collector and restart.

```bash
OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318 ./my-app
```

Forge appends `/v1/traces` to that value. If you need a different path, set `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` instead, and it's used exactly as written.

Export is OTLP over HTTP with protobuf bodies, and that's the only transport. A gRPC collector on port 4317 won't work, so use the collector's HTTP port (4318 by default). The endpoint also has to be a full `http` or `https` URL. A bare `localhost:4318` is rejected: Forge logs one error, keeps booting, and carries on creating spans without exporting them.

For Grafana Cloud, or any backend that wants an auth header, set the headers variable as well:

| Variable | Example |
|---|---|
| `OTEL_EXPORTER_OTLP_ENDPOINT` | `https://otlp-gateway-prod-us-central-0.grafana.net/otlp` |
| `OTEL_EXPORTER_OTLP_HEADERS` | `Authorization=Basic%20<base64 of instance:token>` |
| `OTEL_SERVICE_NAME` | `user-api` |

Header values are percent-encoded, so the space after `Basic` is written `%20`. Separate several headers with commas. The `headers` key in YAML or code takes plain values and needs no encoding. [Shipping telemetry](/docs/forge/shipping-telemetry) has the variables for Tempo, Jaeger, Honeycomb, Datadog, New Relic and a plain Collector, and how each one gets your metrics.

### Configuration

Every key is optional. This is the `tracing:` block with its defaults:

```yaml
tracing:
  enabled: true                  # false: no spans, but traceparent still passes through
  endpoint: ""                   # full OTLP/HTTP traces URL; empty means no export
  headers: {}                    # sent with every export request
  sample_ratio: 1.0              # 1.0 in dev, test and local; 0.1 anywhere else
  propagators: [tracecontext, baggage]
  exclude_paths: ["/_/"]         # path prefixes that get no span
  response_header: traceparent   # set to "" to stop writing it
  resource: {}                   # extra resource attributes, e.g. service.namespace: payments
  record_raw_path: false         # true: url.path is the raw request path, not the route
  record_user_agent: false       # true: record user_agent.original
  allowed_query_keys: []         # non-empty: record url.query, with other keys' values REDACTED
```

The last three decide how much of each request lands on its span. They're covered in [What stays off your spans](#what-stays-off-your-spans).

With `enabled: false` you get no spans and no `traceparent` response header. An incoming `traceparent` still passes through, though, so calls you make with `forge.HTTPClient()` carry the caller's trace on to the next service.

When the same setting comes from more than one place, the first of these wins:

1. Code: `forge.WithAppTracingConfig`
2. The `tracing:` block in your Forge config file
3. `OTEL_*` environment variables
4. The defaults above

```go
ratio := 0.25

app := forge.New(
    forge.WithAppName("user-api"),
    forge.WithAppEnvironment("production"),
    forge.WithAppTracingConfig(forge.TracingConfig{
        Endpoint:    "https://collector.internal:4318/v1/traces",
        SampleRatio: &ratio,
    }),
)
```

These environment variables are read when the matching key isn't set above them:

| Variable | Sets |
|---|---|
| `OTEL_SDK_DISABLED=true` | `enabled: false` |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | `endpoint`, with `/v1/traces` appended |
| `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` | `endpoint`, used as is |
| `OTEL_EXPORTER_OTLP_HEADERS` | `headers` (also `OTEL_EXPORTER_OTLP_TRACES_HEADERS`) |
| `OTEL_TRACES_SAMPLER`, `OTEL_TRACES_SAMPLER_ARG` | the sampler and its ratio |
| `OTEL_PROPAGATORS` | `propagators` |
| `OTEL_SERVICE_NAME`, `OTEL_RESOURCE_ATTRIBUTES` | the resource |

The resource always carries `service.name` (the app's name), `service.version` and `deployment.environment.name`, plus host and process details. `OTEL_SERVICE_NAME` and `OTEL_RESOURCE_ATTRIBUTES` override those, and the `resource` key overrides both.

### When a value doesn't parse

A scalar value (a number, bool, duration or string) that can't be read as its field's type is ignored, the field keeps its default, and Forge logs a warning. A list, mapping or block given a value of the wrong shape, like `hosts: "a,b"` for a list, is still ignored without a warning in this release. Here's a scalar that fails:

```yaml
tracing:
  sample_ratio: "lots"
  endpoint: https://collector.internal:4318/v1/traces
```

You get a warning like this one. Your logger decides the exact layout:

```text
WARN config: ignoring invalid value, using the default key=tracing.sample_ratio value=lots expected=float64
```

The `endpoint` still applies. Only the key that failed falls back, and each bad key warns once per boot.

For `sample_ratio`, "the default" means the same thing it does when the key is missing. A ratio set in code still wins. Otherwise `OTEL_TRACES_SAMPLER` and `OTEL_TRACES_SAMPLER_ARG` are read next (the ratio argument is only read for a `traceidratio` sampler), and if neither is set you get 1.0 in an empty, `development`, `dev`, `local` or `test` environment and 0.1 anywhere else.

The `metrics` and `health` blocks work the same way, and so does every extension's block. The warning names the full key, such as `metrics.collection.interval` or `extensions.cache.max_size`, and that field keeps its default while the rest of the block loads.

`enabled` is the exception, because it decides whether Forge reads the file block at all. Forge only reads the `health` block when it says `enabled: true`, so a bad `health.enabled` skips the whole block, and health runs on your code config or Forge's defaults. `metrics` does the same when you also pass a metrics config in code. Without one, a bad `metrics.enabled` keeps its default like any other key.

When you pass a metrics config in code and the file block loads, the code value stays for any key the file got wrong. A key that's wrong in the file and not set in code is treated as if the file never mentioned it.

Before this release, Forge bound a value like `"lots"` as 0. For `sample_ratio` that meant no traces at all, and nothing in the log said why. If you're upgrading and traces or limits start behaving differently, search your boot logs for `ignoring invalid value`.

### What a request produces

Each request gets one server span, named `METHOD /route/pattern` once the router has matched, such as `GET /users/:id`. The name uses the pattern and not the URL, so traffic to a thousand different user IDs lands on one span name. A request that matches nothing keeps the bare method as its name.

The span carries these attributes: `http.request.method`, `url.scheme`, `url.path`, `network.protocol.version`, `server.address`, `http.route` and `http.response.status_code`. `url.path` holds the route pattern, the same value as `http.route`, and a request that matched no route has no `url.path` at all. A method outside the standard nine is recorded as `_OTHER`, with the original in `http.request.method_original`.

A response with a 5xx status marks the span as an error and sets `error.type`. When a handler returns a 5xx error or panics and the router recovers, the span also gets an `exception` event whose `exception.type` names the error's class (`panic` for a panic), with a stack trace for panics. 4xx responses are normal traffic, so they don't mark the span.

Requests whose path starts with anything in `exclude_paths` get no span. The default, `/_/`, keeps Forge's own endpoints (health, metrics, info) out of your traces.

Incoming `traceparent` and `baggage` headers are honoured, so your spans join the caller's trace.

A WebSocket, SSE or WebTransport route is the exception to "one span for the request". Its server span ends at the handshake: after the upgrade for a WebSocket (status 101), once the stream is writable for `EventStream`, right before your handler runs for `SSE()`, and after the upgrade for WebTransport. It carries `forge.stream.kind` (`sse`, `websocket` or `webtransport`) as well as the usual attributes, so a trace of a connection that stays open all day is still a few milliseconds long. Spans you start for each message with `forge.StartSpan` are children of that span. For how long the connection lived and how many messages crossed it, use the [stream metrics](/docs/forge/metrics#stream-connections). A rejected upgrade, a 403 for a bad `Origin` say, is an ordinary request with an ordinary span and no `forge.stream.kind`.

WebTransport sessions run on the router's own HTTP/3 server. Call `EnableWebTransport` and then `StartHTTP3`, and each upgrade gets its span the same way a WebSocket does.

### What stays off your spans

Out of the box, a span never holds:

- the raw request path. `url.path` is the route pattern, so `/v1/sessions/:id` and not the session ID, and the span name is `METHOD /route/pattern` or the bare method.
- the query string. There's no `url.query` and no `url.full`.
- the user agent. There's no `user_agent.original`.
- error text. A status description or `exception.type` names the error's class: `context.Canceled`, `context.DeadlineExceeded`, or the Go type of the innermost error in the chain, so a wrapped driver error reads as the driver's type. A panic reads `panic`, and its value stays off. The call still hands you the full error, and Forge's default error handler and panic recovery still log it.

Paths carry session IDs, passkey credential IDs and the occasional push secret, query strings carry tickets and tokens, a user agent is personal data, and error text quotes DSNs and bound query values. Your tracing backend probably keeps all of it for weeks, readable by more people than your database is.

If you want any of the first three back, turn them on in the `tracing` block or in code:

```yaml
tracing:
  record_raw_path: true          # url.path is the raw path, for matched and unmatched requests
  record_user_agent: true        # user_agent.original is recorded
  allowed_query_keys: [page, sort]
```

```go
on := true

app := forge.New(
    forge.WithAppTracingConfig(forge.TracingConfig{
        RecordRawPath:    &on,
        RecordUserAgent:  &on,
        AllowedQueryKeys: []string{"page", "sort"},
    }),
)
```

`allowed_query_keys` turns `url.query` on. Every key is recorded, the listed keys keep their values and every other value reads `REDACTED`, so `?page=2&t=abc` becomes `page=2&t=REDACTED`. A key sent without a value is recorded only if you list it, since `?<token>` puts the secret where the key goes. Keys are matched after decoding. With the list empty there's no `url.query`, and there's no setting that records every value as sent. The span name stays `METHOD /route/pattern` whatever you set.

Error text has no switch. When you know an error is safe to keep, record it on the span yourself:

```go
func charge(c forge.Context) error {
    if err := billing.Charge(c.Context(), order); err != nil {
        forge.SpanFromContext(c.Context()).RecordError(err) // message and all
        return err
    }

    return c.JSON(http.StatusOK, order)
}
```

Before Forge 1.12.10, `url.path` was the raw path, `user_agent.original` was always recorded, and errors went on spans with their message, as the status description and as `exception.message`. If a dashboard, an alert or a span processor of yours reads any of those, set the matching key above, or switch it to `http.route` and `exception.type`.

### Add your own spans

`forge.StartSpan` starts a child of whatever span the context carries. Pass it the request's context and end the span when the work is done.

```go
func charge(ctx forge.Context) error {
    spanCtx, span := forge.StartSpan(ctx.Context(), "charge-card")
    defer span.End()

    span.SetAttributes(attribute.String("payment.provider", "stripe"))

    return provider.Charge(spanCtx, order)
}
```

`forge.SpanFromContext(ctx)` returns the current span, or a no-op span when there isn't one, so you can add attributes without checking.

### Boot and shutdown traces

Slow boot? Open the `forge.start` trace. Every `Start` produces one, with a `register <ext>` and a `start <ext>` child for each extension, so the long bar is the extension that held things up. Every `Stop` does the same under `forge.stop`, with a `stop <ext>` child per extension. Each extension span carries `forge.extension.name` and `forge.extension.version`, and a failed or panicking call is recorded on its span by class, never by message: an extension that fails to parse a DSN shows the error's Go type, and `Start` hands you the full error.

These two root spans are sampled whatever `sample_ratio` says, because a boot happens once per process and the slow one is the one you want to see. The exception is sampling that is off (`sample_ratio: 0`, `always_off` or `parentbased_always_off`), where you get nothing. Under the default parent-based sampler the children follow their root, so the whole trace ships. A plain `traceidratio` sampler isn't parent-based and rolls again for each child, so you'd see only some of them.

Spans you start with the context your extension's `Start` receives nest under `start <ext>`:

```go
func (e *Extension) Start(ctx context.Context) error {
	ctx, span := forge.StartSpan(ctx, "warm-cache")
	defer span.End()

	return e.cache.Warm(ctx)
}
```

Don't hand that context to a goroutine that outlives `Start`. It belongs to the caller, so every span the goroutine starts later would land in the boot trace. Start it from `context.Background()` instead. `context.WithoutCancel(ctx)` won't do, because it keeps the span.

The boot trace starts at the top of `Start`, before the before-start hooks, but only the extension calls get its context. Hooks, the container and health checks don't, so nothing long-lived they start ends up in it. `Stop` ends the `forge.stop` span before it flushes the exporter, so shutdown spans are exported rather than lost.

### Trace outgoing calls

`forge.HTTPClient()` returns an `*http.Client` whose requests get a client span and carry the trace headers to the next service. Build it once and reuse it.

```go
var client = forge.HTTPClient()

func fetchUser(ctx context.Context, id string) (*http.Response, error) {
    req, err := http.NewRequestWithContext(ctx, http.MethodGet, "http://users/"+id, nil)
    if err != nil {
        return nil, err
    }

    return client.Do(req)
}
```

Already have a client with its own transport? Wrap the transport with `forge.InstrumentTransport(rt)`. A nil transport means `http.DefaultTransport`.

The client span's `url.full` keeps the scheme, host and path. It drops any username and password and the fragment, and every query value reads `REDACTED`, so a call to `https://api.example.com/v1/items?token=abc&page=2` shows up as `https://api.example.com/v1/items?token=REDACTED&page=REDACTED`. The request that goes out is untouched. A transport error, or one from reading the response body, sets the span's status and `error.type` to the error's class, and you get the original error back. The path isn't scrubbed, so if your URLs carry a secret in the path, a webhook URL say, put a transport of your own in front that hides it.

A client captures the tracer provider and propagators that are current when you build it. One built before `forge.New` still traces, because OpenTelemetry's global hands its spans on to the first provider anyone sets. In a process with several apps, though, a client stays with whichever provider was current when you built it, so build it after the app you want it to follow.

### gRPC calls

The [gRPC extension](/docs/extensions/grpc) gives every served call a server span named like the method (`billing.Invoices/Get`), with the `rpc.system.name`, `rpc.method` and `rpc.response.status_code` attributes, and records its duration in `rpc_server_call_duration_seconds` with the same three labels. Health and reflection calls are left out of both. For calls going out, add `grpcext.ClientDialOptions()` to your `grpc.NewClient`, or use conduit's `Services.GRPC`, which does it for you. Both read the OpenTelemetry globals when you call them, so call them after `forge.New`.

### Messaging

A message you publish in one service and handle in another shows up as one trace. The publisher records a producer span, the handler runs inside a consumer span that is its child, and the trace context travels in the message's own headers: `traceparent`, `tracestate` when there is one, and `baggage` when the context has any (the default propagators are `tracecontext` and `baggage`). The queue, events, conduit and kafka extensions do this for you. You don't add a hook or copy a header by hand.

| Extension | Spans you'll see | `messaging_system` |
|---|---|---|
| [queue](/docs/extensions/queue) | `publish {queue}`, then `process {queue}` | the driver: `memory`, `redis`, `nats` or `rabbitmq` |
| [events](/docs/extensions/events) | `publish {event type}` for each broker the event reaches, then `process {event type}` for each handler | the broker's name |
| [conduit](/docs/extensions/conduit) | `create {stream}`, `send {stream}` and `process {stream}`; for typed RPC, `call {service}.{method}` and `serve {service}.{method}` | the provider's name, such as `memory`, `redis-streams`, `nats-jetstream`, `postgres` or `kafka` |
| [kafka](/docs/extensions/kafka) | `send {topic}`, then `process {topic}`; a `SendMessages` batch adds a `create {topic}` per record | `kafka` |

The create, send and publish spans are producer spans and the process spans are consumer spans. The RPC pair is the exception: `call` is a client span and `serve` is a server span, and the server span is the call's child.

Every span carries `messaging.system`, `messaging.destination.name` (the queue, event type, stream or topic), `messaging.operation.name` and `messaging.operation.type`. A batch send adds `messaging.batch.message_count`. A failed publish or handler marks its span as an error, sets `error.type` and adds an `exception` event, and the status description and `exception.type` carry that same type and never the error's message; in the queue, events and kafka extensions a handler that panics does the same with `error.type` set to `*messaging.PanicError`, and the panic carries on up unchanged. Conduit recovers a handler or RPC panic into an ordinary error (`conduit: callback panic: ...`), so its span gets that error's Go type and the panic doesn't propagate.

Conduit records two producer spans per message. `Prepare` writes the `create` span's context into the envelope before your publish hooks run, so an envelope that waits in the transactional outbox, gets backfilled or comes back through dead letter replay still joins the trace that made it. The `send` span carries a link to `create`. When an outbox relay sends the envelope later there's no caller span to be a child of, so `send` is a root span with that link, and the trace still connects through `create`. Each retry gets its own `process` span. A publish hook that replaces `Headers` wholesale throws `traceparent` away with the rest, so add to the map.

Kafka's `SendMessageAsync` span covers the hand-off to the producer only. Delivery errors come back on the producer's own error channel, so they don't reach that span. Pass your request's context to the `*Context` methods (`SendMessageContext`, `SendMessagesContext` and so on) to make the send a child of the request. `Consume` and `ConsumePartition` still trace a handler that takes no context, but only a `ContextMessageHandler` gets the consumer span's context to start children from.

A few cases you can count on:

- A message from a publisher that sends no `traceparent`, or a garbled one, gives a root consumer span and no error.
- A publisher whose trace wasn't sampled stays unsampled downstream. Nothing is exported, but the trace ID still reaches your logs.
- The headers or metadata you pass to a publish call are never modified. The extension copies them first, so reusing one map across publishes or goroutines is safe.
- Messages now carry trace context (`traceparent`, and `tracestate` or `baggage` when there are any), so a test that asserts the exact set of headers or metadata needs to allow for it.
- The context you publish with decides the trace. With tracing on, a publish from a context that has no span starts a new root and replaces a `traceparent` you put in the headers yourself. To forward a message you received, call `forge.ExtractTraceContext` (or `messaging.Extract`) on its headers first and publish with the context that returns.

`enable_tracing: false` on the queue, events or kafka extension turns the spans off and leaves propagation on. A hop that doesn't trace still hands the trace on, so a service with tracing off doesn't break the trace of the services around it. Conduit has no flag and follows the app's `tracing.enabled`. Events used to default to `false` (and never read it); it's `true` now.

#### Your own maps

If you run your own broker client and just want the trace to survive the hop, copy it into whatever string map your messages carry.

```go
func publish(ctx context.Context, body []byte) error {
    headers := map[string]string{}
    forge.InjectTraceContext(ctx, headers)

    return broker.Send(ctx, body, headers)
}

func handle(ctx context.Context, body []byte, headers map[string]string) error {
    ctx = forge.ExtractTraceContext(ctx, headers)

    ctx, span := forge.StartSpan(ctx, "handle-order")
    defer span.End()

    return process(ctx, body)
}
```

Both work with tracing turned off, which is what makes them right for a service that only passes messages along. A nil map is ignored. `ExtractTraceContext` hands the context back unchanged when the map holds no trace.

#### Your own producers and consumers

The extensions all run on the `github.com/xraph/forge/messaging` package, and you can use it too. It gives you the spans in the table above and the two duration histograms in the [metrics reference](/docs/forge/metrics#messaging), with the same labels the extensions use, so your hand-written consumer lands on the same dashboards.

Build one `Telemetry` per messaging system and reuse it. `Process` wraps a handler: it extracts the trace from a carrier, starts the consumer span, runs your function with the span's context and ends the span with the function's error.

```go
mt := messaging.New("kafka", messaging.WithMetrics(app.Metrics()))

func (h handler) ConsumeClaim(sess sarama.ConsumerGroupSession, claim sarama.ConsumerGroupClaim) error {
    for msg := range claim.Messages() {
        err := mt.Process(sess.Context(), kafka.ConsumerHeaderCarrier(msg), msg.Topic, "process",
            func(ctx context.Context) error { return h.handle(ctx, msg) })
        if err == nil {
            sess.MarkMessage(msg, "")
        }
    }

    return nil
}
```

Kafka consumer groups are your own `ConsumerGroupHandler`, so the extension can't wrap them. That's why `kafka.ConsumerHeaderCarrier` exists: it lets `Process` read the record's headers. `kafka.ProducerHeaderCarrier` does the same for an outgoing `*sarama.ProducerMessage`.

For a producer, start the send, add the trace context to a copy of your headers and end the operation with the result:

```go
ctx, op := mt.StartSend(ctx, "orders", "publish")
headers := messaging.WithTraceContext(ctx, baseHeaders)
err := broker.Send(ctx, body, headers)
op.End(err)
```

`WithTraceContext` never touches `baseHeaders`. It returns a copy with the trace added, or the same map when there's nothing to add. `End` is safe on a nil operation and safe to call twice. With `messaging.WithTracing(false)` no spans start, and `Inject` and `Extract` still pass the trace through.

#### MQTT

The mqtt extension can't carry trace context. Its client (paho v1.5.1) speaks MQTT 3.1.1, which has no user properties, so a message has nowhere to hold a `traceparent`. `enable_tracing` on the mqtt extension is deprecated and does nothing. If you need a trace across an MQTT hop today, put the `traceparent` in your payload yourself with `forge.InjectTraceContext` and `forge.ExtractTraceContext`. Real support has to wait for an MQTT v5 client.

The timing side is in the [messaging metrics](/docs/forge/metrics#messaging).

### Send spans somewhere else too

`forge.RegisterSpanProcessor` adds an OpenTelemetry span processor to an app's tracer provider, so you can copy spans into your own store or log.

Read a server span's attributes in `OnEnd`. The HTTP request attributes (`http.request.method`, `url.path` and the rest) are set when the span ends, so in `OnStart` the span only has its name and kind.

```go
app := forge.New(forge.WithAppName("user-api"))

if err := forge.RegisterSpanProcessor(app, myProcessor); err != nil {
    if errors.Is(err, forge.ErrTracingDisabled) {
        // tracing is off, so there is nothing to attach to
    }
}
```

The provider is also in the container as `trace.TracerProvider` (from `go.opentelemetry.io/otel/trace`) if you'd rather start spans from your own tracer.

A processor can ask for more than the sampled spans. Implement `forge.UnsampledSpanProcessor`, which is `sdktrace.SpanProcessor` plus `WantsUnsampled() bool`, and while that returns true the app also records the spans the sampler dropped. They're never exported, and downstream services still see "not sampled", so your OTLP backend gets the same sample as before. `WantsUnsampled` runs for every dropped span, so keep it to something like an atomic load.

```go
type watcher struct {
	sdktrace.SpanProcessor // your real processor; a nil one panics on the first span
	active atomic.Bool
}

func newWatcher(inner sdktrace.SpanProcessor) *watcher {
	return &watcher{SpanProcessor: inner}
}

func (w *watcher) WantsUnsampled() bool { return w.active.Load() }
```

Register it with `forge.RegisterSpanProcessor(app, newWatcher(myProcessor))`. The dashboard does exactly this to show every request while somebody is looking at it.

Those extra spans reach every processor you've registered, including ones that never asked for them, because the SDK hands each recording span to all of them. So while the dashboard is open (or all the time, if its `trace_idle_ttl` is zero or less), your own processor gets unsampled spans too, and `span.IsRecording()` is true for them. If you only want what gets exported, check the sampled flag in `OnEnd`:

```go
func (p *myProcessor) OnEnd(s sdktrace.ReadOnlySpan) {
	if !s.SpanContext().IsSampled() {
		return // recorded for a processor that asked, never exported
	}

	p.store(s)
}
```

### Sampling

Without any configuration the ratio is 1.0 (every trace) when the app's environment is empty, `development`, `dev`, `local` or `test`, and 0.1 for every other environment. By default sampling is parent-based: if a caller sent a sampled trace, you keep it, and if they sent an unsampled one, you drop it. The ratio only decides for requests that start a new trace. One exception: the `forge.start` and `forge.stop` roots are always sampled unless sampling is off (see [Boot and shutdown traces](#boot-and-shutdown-traces)). A sampler you name without the `parentbased_` prefix, below, ignores the caller's choice too.

To change it, set `sample_ratio` in code or config. A value outside 0 to 1 is clamped and logged as a warning. To pick a sampler by name, use `OTEL_TRACES_SAMPLER` with `OTEL_TRACES_SAMPLER_ARG` for the ratio:

```bash
OTEL_TRACES_SAMPLER=parentbased_traceidratio OTEL_TRACES_SAMPLER_ARG=0.25 ./my-app
```

The names Forge accepts are `always_on`, `always_off`, `traceidratio`, `parentbased_always_on`, `parentbased_always_off` and `parentbased_traceidratio`. Anything else logs a warning and falls back to `parentbased_traceidratio`. A `sample_ratio` in code or config beats these variables entirely.

### Shutdown

Spans are batched, and the batch is flushed when the app stops, after the extensions and the container have shut down so their last spans are included. The flush waits at most five seconds.

<Callout type="warn">
`forge.New` takes over the OpenTelemetry globals: the tracer provider, the propagator and the error handler. If your app set up its own tracer provider in code before `forge.New`, Forge replaces it, and spans you start with `otel.Tracer(...)` go to Forge's provider from then on. That provider only exports when you've configured an endpoint. With `enabled: false` the global becomes a no-op provider, so if you want to keep your own, set it up after `forge.New`.

Already running your own `otelhttp` server middleware? You'll now get two server spans per request. Remove yours, or turn Forge's off with `tracing.enabled: false`.

With more than one Forge app in a process, the last app built sets all three: the tracer provider, the `propagators` setting and the error handler (that one only from an app with tracing on). `forge.StartSpan` reads the globals on every call, so it follows the last app. Each app's own request spans still go to its own provider. Build the app you want the helpers to follow last.
</Callout>

## Profiling

Forge can push continuous profiles to Pyroscope and link each sampled trace to the CPU its request burned. Give it a server address and restart.

```bash
PYROSCOPE_SERVER_ADDRESS=http://localhost:4040 ./my-app
```

Your app now pushes CPU and memory profiles every 15 seconds under its own name, and when you open a sampled request's span in Grafana, you can jump from it to the part of the CPU profile that request produced. Set neither an address nor `span_labels` and nothing runs: the request path pays for one bool check.

### Push to Pyroscope

Every key is optional. This is the `profiling:` block:

```yaml
profiling:
  server_address: http://pyroscope:4040   # empty means no push
  application_name: user-api              # defaults to the app's name
  basic_auth_user: "123456"               # Grafana Cloud wants the instance ID here
  basic_auth_password: ""                 # keep it in PYROSCOPE_BASIC_AUTH_PASSWORD instead
  tenant_id: ""                           # sent as X-Scope-OrgID to a multi-tenant Pyroscope
  tags:
    region: eu-west-1
  profile_types: [cpu, alloc_objects, alloc_space, inuse_objects, inuse_space]
  span_labels: true                       # follows push when you leave it out
```

When the same setting comes from more than one place, the first of these wins:

1. Code: `forge.WithAppProfilingConfig`
2. The `profiling:` block in your Forge config file
3. `PYROSCOPE_*` environment variables
4. The defaults

```go
labels := true

app := forge.New(
    forge.WithAppName("user-api"),
    forge.WithAppVersion("2.1.0"),
    forge.WithAppEnvironment("production"),
    forge.WithAppProfilingConfig(forge.ProfilingConfig{
        ServerAddress: "http://pyroscope:4040",
        Tags:          map[string]string{"region": "eu-west-1"},
        SpanLabels:    &labels,
    }),
)
```

These environment variables are read when the matching key isn't set above them:

| Variable | Sets |
|---|---|
| `PYROSCOPE_SERVER_ADDRESS` | `server_address` |
| `PYROSCOPE_APPLICATION_NAME` | `application_name` |
| `PYROSCOPE_BASIC_AUTH_USER` | `basic_auth_user` |
| `PYROSCOPE_BASIC_AUTH_PASSWORD` | `basic_auth_password` |
| `PYROSCOPE_TENANT_ID` | `tenant_id` |

Setting `PYROSCOPE_SERVER_ADDRESS` on its own turns push on, with nothing in your code or config file. If your app already calls `pyroscope.Start` itself, drop that call when you move to Forge's profiler. Otherwise you run two sessions in one process, and they fight over Go's single CPU profiler.

`tags`, `profile_types` and `span_labels` have no variable. Tags and profile types don't merge between sources: a map or list you set in code replaces the file's entirely, the same way `headers` and `resource` work for tracing, so if your code sets one tag, every tag in your config file is ignored.

Forge adds two tags of its own, `service_version` from the app's version and `environment` from its environment, each only when the app has one. If you set a tag with the same key, yours wins.

Pyroscope only accepts letters, digits, `_`, `.`, `/` and `-` in an application name. Forge turns any other character into `_` and logs a warning, so an app named `My App` profiles as `My_App`. Tag keys are stricter and take letters, digits, `_` and `.` only. A key outside that set, or the reserved `__name__`, is dropped with a warning.

Tag values can hold anything except `,`, `{`, `}` and `=`. The SDK sends tags in the upload's query as `name=app{key=value,...}`, so one of those characters breaks the query and Pyroscope refuses every upload. Forge turns each of them into `_` and logs a warning naming the key and the value you gave. That covers its own `service_version` and `environment` too, so a version of `1.0,rc1` profiles as `1.0_rc1`.

### Profile types

You get `cpu`, `alloc_objects`, `alloc_space`, `inuse_objects` and `inuse_space` by default. Five more are on offer: `goroutines`, `mutex_count`, `mutex_duration`, `block_count` and `block_duration`. A name Forge doesn't know is dropped with a warning, and a list with nothing valid left in it falls back to the defaults.

```yaml
profiling:
  server_address: http://pyroscope:4040
  profile_types: [cpu, inuse_space, goroutines, mutex_duration, block_duration]
```

<Callout type="warn">
Asking for `mutex_count` or `mutex_duration` calls `runtime.SetMutexProfileFraction(5)`, and `block_count` or `block_duration` calls `runtime.SetBlockProfileRate(5)`. Those are runtime settings for the whole process, not for Forge. They replace any rate you set before `app.Start`, they cost a little on every contended lock or blocking call, and they stay in place after the app stops.
</Callout>

### From a trace to its profile

With span labels on, every sampled server span gets a `pyroscope.profile.id` attribute set to its span ID, and the CPU samples taken while its handler ran carry two pprof labels: `span_id`, and `span_name` holding the span's final name, such as `GET /users/:id`. Grafana puts "Profiles for this span" on a span that has the `pyroscope.profile.id` attribute, and finds its samples through the `span_id` label. `span_name` is for per-route flame graphs: filter on it in Pyroscope and you see what one route costs across every sampled request.

To turn the link on in Grafana:

1. Open your Tempo data source's settings and find **Traces to profiles**.
2. Pick your Pyroscope data source.
3. Add a tag that maps `service.name` to `service_name`.
4. Choose a CPU profile type, and save.

The join only works when the two names agree. Pyroscope's `service_name` defaults to the app's name, the same value traces send as `service.name`, so out of the box they match. If you override one (`OTEL_SERVICE_NAME`, say, or `application_name`), set the other to the same value. A name Forge had to rewrite won't match either: traces keep `My App` while profiles say `My_App`, so give the app a name without spaces.

You need tracing on. Labels hang off the server span, so with `tracing.enabled: false` your `span_labels` stays off and Forge logs `profiling: span labels need tracing, which is off, so they stay off`. Only sampled spans get labels, because only a sampled span reaches Tempo.

### Pull with Alloy

You can let Grafana Alloy scrape instead of pushing. Leave `server_address` empty, keep the pprof endpoints on behind a `PprofGuard`, and set `span_labels: true` yourself, since without push it defaults to off.

```go
labels := true

app := forge.New(
    forge.WithAppName("user-api"),
    forge.WithPprofGuard(func(r *http.Request) bool {
        return subtle.ConstantTimeCompare(
            []byte(r.Header.Get("Authorization")), []byte("Bearer "+token)) == 1
    }),
    forge.WithAppProfilingConfig(forge.ProfilingConfig{SpanLabels: &labels}),
)
```

Then point `pyroscope.scrape` at the app. The endpoints live under `/_/debug/pprof`, so the path prefix is `/_`:

```hcl
pyroscope.scrape "user_api" {
  targets           = [{"__address__" = "user-api:8080", "service_name" = "user-api"}]
  forward_to        = [pyroscope.write.default.receiver]
  bearer_token_file = "/etc/alloy/pprof-token"

  profiling_config {
    path_prefix = "/_"
  }
}

pyroscope.write "default" {
  endpoint {
    url = "http://pyroscope:4040"
  }
}
```

Set `service_name` on the target to the app's `service.name`, for the same reason as above.

Pull reads `span_labels` and nothing else from the `profiling:` block. `profile_types`, `tags` and `application_name` only shape what push sends, and the mutex and block rates only get set when push asks for a `mutex_*` or `block_*` type. Go records neither by default, so if you want mutex or block profiles from the pprof endpoints, call `runtime.SetMutexProfileFraction` and `runtime.SetBlockProfileRate` yourself before `app.Start`.

### Limits

Before you trust a flame graph filtered to one span or one route, know where the link between a span and its samples breaks down.

- Labels reach CPU profiles (and goroutine profiles) only. Heap and allocation profiles carry none.
- Go's CPU profiler samples at 100 Hz, so a span shorter than about 10ms usually has no samples at all.
- Goroutines a handler starts inherit its labels. Work handed to a goroutine that already exists, such as a worker pool, loses the link.
- A per-route flame graph filtered by `span_name` only covers the requests tracing sampled. At a ratio of 0.1, that is about one in ten.
- A WebSocket, SSE or WebTransport span ends at the handshake, so its profile link covers the handshake too. Once the stream is up, the goroutine drops `span_id` and keeps `span_name`, which keeps hours of stream CPU off a span that lasted a few milliseconds. The request context still carries `span_id`, though. A stream handler that calls `pprof.Do(r.Context(), ...)` brings `span_id` back, and it stays on the goroutine for the rest of the stream after that `Do` returns.
- `span_name` lives on the goroutine and not on the request context. If a handler or middleware adds labels of its own with `pprof.Do(r.Context(), ...)`, it loses `span_name` inside that `Do` and for the rest of the request after it returns. `span_id`, which is what links the trace, survives.

### Start, stop and failures

The profiler starts in `app.Start`, right after the "starting application" log line and before the before-start hooks, so extension startup shows up in the first profiles. If `app.Start` fails, it stops the profiler again. `app.Stop` stops it last, after the tracing flush, and uploads what is left. That upload gets at most 5 seconds, the same cap as the tracing flush, or less when your stop context ends sooner. When time runs out, Forge logs `profiling: final upload did not finish` and returns. A failed `app.Start` gets the same capped attempt, even with a cancelled context, so a Pyroscope that takes the connection and never answers can't hold your boot error for 30 seconds.

An unreachable Pyroscope never fails `app.Start`. Uploads happen in the background, so a Pyroscope that's down shows up in your logs as `profiling: pyroscope client error` at warn, at most once a minute. The `error` field holds the SDK's own message, and `suppressed` counts the errors in between. The same line covers the SDK's other complaints, such as a full upload queue. If the Pyroscope client can't start at all, Forge logs `profiling: push disabled` at error and keeps booting.

<Callout type="warn">
Go has one CPU profiler per process, and push holds it. While push includes `cpu`, the pprof endpoint `/_/debug/pprof/profile` answers "cpu profiling already in use". Forge logs a warning saying so at start when the pprof endpoints are on. The heap, goroutine and other pprof endpoints still work.
</Callout>

## Metrics

With `metrics.features.http_metrics` on (the default), Forge records the OpenTelemetry HTTP server metrics for every request and serves them at `/_/metrics`. The latency series is `http_server_request_duration_seconds`, labelled by method, route pattern, status code, scheme and error type. Requests that tracing samples carry a `trace_id` exemplar on it, so Grafana can take you from a slow bucket to the trace.

```promql
histogram_quantile(0.95,
  sum by (le, http_route) (rate(http_server_request_duration_seconds_bucket[5m])))
```

Prometheus needs `--enable-feature=exemplar-storage` to keep the exemplars. The label vectors for your own metrics and the series cap are on the [Metrics](/docs/forge/metrics) page. Every series with its labels and buckets is on the [metric reference](/docs/forge/metric-reference), and [Migrating dashboards](/docs/forge/migrating-dashboards) maps the old `forge_http_*` and `forge_grpc_*` names to the new ones.

Metrics can also be pushed. Set `OTEL_EXPORTER_OTLP_ENDPOINT` and Forge sends traces to `/v1/traces` and, from `app.Start` to `app.Stop`, metrics to `/v1/metrics` under that base URL, every 60 seconds. A traces endpoint set in the `tracing:` block, in code or in `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` doesn't turn metrics push on, so use `metrics_export.endpoint` or `OTEL_EXPORTER_OTLP_METRICS_ENDPOINT` for those. `OTEL_METRICS_EXPORTER=none` keeps the metrics on the scrape endpoint alone while traces still go out. Pick one route per backend, scrape or push, or each series counts twice. The environment variables, `metrics_export:` keys, temporality and naming rules are under [Pushing over OTLP](/docs/forge/metrics#pushing-over-otlp).

## Complete Example

```go
package main

import (
    "github.com/xraph/forge"
)

func main() {
    // Use beautiful logger in dev, production logger in prod
    var logger forge.Logger
    if env := os.Getenv("ENV"); env == "production" {
        logger = forge.NewProductionLogger()
    } else {
        logger = forge.NewBeautifulLogger()
    }

    app := forge.New(
        forge.WithAppName("observable-api"),
        forge.WithAppVersion("1.0.0"),
        forge.WithAppLogger(logger),
        forge.WithAppMetricsConfig(forge.MetricsConfig{
            Enabled: true,
            Features: forge.MetricsFeatures{
                RuntimeMetrics: true,
                HTTPMetrics:    true,
            },
        }),
        forge.WithAppHealthConfig(forge.HealthConfig{
            Enabled: true,
            Features: forge.HealthFeatures{
                AutoDiscovery: true,
            },
        }),
    )

    r := app.Router()

    r.GET("/api/users", func(ctx forge.Context) error {
        defer forge.Track(app.Logger(), "listUsers")()

        app.Logger().Info("listing users",
            forge.String("source", ctx.Header("X-Source")),
        )

        return ctx.JSON(200, users)
    })

    // All endpoints available:
    // GET /_/info      - App info
    // GET /_/health    - Health checks
    // GET /_/metrics   - Prometheus metrics
    // GET /_/openapi   - OpenAPI spec
    // GET /_/asyncapi  - AsyncAPI spec

    app.Run()
}
```
