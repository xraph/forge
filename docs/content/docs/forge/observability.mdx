Forge gives you structured logging, OpenTelemetry tracing and a set of built-in diagnostic endpoints. Tracing is on from the first request and logs pick up its trace and span IDs; sending spans to a collector takes one environment variable. To see all of it in a local Grafana, follow [Grafana in five minutes](/docs/forge/grafana-in-five-minutes).

## Structured Logging

Forge's logging system provides high-performance, structured logging with multiple output formats.

### Logger Types

<Tabs items={["Beautiful (Dev)", "Production", "Noop"]}>

### Log Levels

```go
const (
    forge.LevelDebug // Detailed debugging information
    forge.LevelInfo  // General operational information
    forge.LevelWarn  // Warning conditions
    forge.LevelError // Error conditions
    forge.LevelFatal // Fatal errors (causes shutdown)
)
```

### Structured Fields

Forge provides typed field constructors for structured logging. Fields are type-safe and optimized for zero-allocation logging.

```go
logger.Info("user created",
    forge.String("user_id", "usr_123"),
    forge.String("email", "alice@example.com"),
    forge.Int("age", 30),
    forge.Duration("latency", 15*time.Millisecond),
)

logger.Error("database query failed",
    forge.Error(err),
    forge.String("query", "SELECT * FROM users"),
    forge.Int("retry_count", 3),
    forge.Stack(),
)
```

### Field Types

| Constructor | Type | Example |
|-------------|------|---------|
| `forge.String(key, val)` | string | `forge.String("name", "alice")` |
| `forge.Int(key, val)` | int | `forge.Int("count", 42)` |
| `forge.Int64(key, val)` | int64 | `forge.Int64("bytes", 1048576)` |
| `forge.Float64(key, val)` | float64 | `forge.Float64("ratio", 0.95)` |
| `forge.Bool(key, val)` | bool | `forge.Bool("active", true)` |
| `forge.Time(key, val)` | time.Time | `forge.Time("created", time.Now())` |
| `forge.Duration(key, val)` | time.Duration | `forge.Duration("elapsed", 2*time.Second)` |
| `forge.Error(err)` | error | `forge.Error(err)` |
| `forge.Any(key, val)` | any | `forge.Any("data", myStruct)` |
| `forge.Stack()` | stack trace | `forge.Stack()` |
| `forge.Strings(key, val)` | []string | `forge.Strings("tags", tags)` |

Pre-built field constructors for common domains:

```go
// HTTP fields
logger.Info("request",

    forge.UserID("usr_456"),

```

### The F() Helper

`F()` is a shorthand for `forge.Any()` for quick key-value pairs:

```go

    forge.F("key", "value"),
    forge.F("count", 42),
    forge.F("data", myStruct),
)
```

### Performance Tracking

Use `Track` to measure and log function execution time:

```go
func processOrder(ctx context.Context) error {
    defer forge.Track(logger, "processOrder")()

    // ... processing logic

    return nil
}
// Logs: "processOrder completed" duration=145ms

// With additional fields
defer forge.TrackWithFields(logger, "processOrder",
    forge.String("order_id", orderID),
)()
```

## Distributed Tracing

Tracing is on by default. Start an app and send it a request: Forge has already opened a server span for that request, stamped `trace_id` and `span_id` on every log line written through the request's logger, and put a `traceparent` header on the response. Nothing leaves the process until you give it an endpoint.

### Export spans

Point Forge at an OTLP collector and restart.

```bash
OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318 ./my-app
```

Forge appends `/v1/traces` to that value. If you need a different path, set `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` instead, and it's used exactly as written.

Export is OTLP over HTTP with protobuf bodies, and that's the only transport. A gRPC collector on port 4317 won't work, so use the collector's HTTP port (4318 by default). The endpoint also has to be a full `http` or `https` URL. A bare `localhost:4318` is rejected: Forge logs one error, keeps booting, and carries on creating spans without exporting them.

For Grafana Cloud, or any backend that wants an auth header, set the headers variable as well:

| Variable | Example |
|---|---|
| `OTEL_EXPORTER_OTLP_ENDPOINT` | `https://otlp-gateway-prod-us-central-0.grafana.net/otlp` |
| `OTEL_EXPORTER_OTLP_HEADERS` | `Authorization=Basic%20<base64 of instance:token>` |
| `OTEL_SERVICE_NAME` | `user-api` |

Header values are percent-encoded, so the space after `Basic` is written `%20`. Separate several headers with commas. The `headers` key in YAML or code takes plain values and needs no encoding. [Shipping telemetry](/docs/forge/shipping-telemetry) has the variables for Tempo, Jaeger, Honeycomb, Datadog, New Relic and a plain Collector, and how each one gets your metrics.

### Configuration

Every key is optional. This is the `tracing:` block with its defaults:

```yaml
tracing:
  enabled: true                  # false: no spans, but traceparent still passes through
  endpoint: ""                   # full OTLP/HTTP traces URL; empty means no export
  headers: {}                    # sent with every export request
  sample_ratio: 1.0              # 1.0 in dev, test and local; 0.1 anywhere else
  propagators: [tracecontext, baggage]
  exclude_paths: ["/_/"]         # path prefixes that get no span
  response_header: traceparent   # set to "" to stop writing it
  resource: {}                   # extra resource attributes, e.g. service.namespace: payments
```

With `enabled: false` you get no spans and no `traceparent` response header. An incoming `traceparent` still passes through, though, so calls you make with `forge.HTTPClient()` carry the caller's trace on to the next service.

When the same setting comes from more than one place, the first of these wins:

1. Code: `forge.WithAppTracingConfig`
2. The `tracing:` block in your Forge config file
3. `OTEL_*` environment variables
4. The defaults above

```go
ratio := 0.25

app := forge.New(
    forge.WithAppName("user-api"),
    forge.WithAppEnvironment("production"),
    forge.WithAppTracingConfig(forge.TracingConfig{
        Endpoint:    "https://collector.internal:4318/v1/traces",
        SampleRatio: &ratio,
    }),
)
```

These environment variables are read when the matching key isn't set above them:

| Variable | Sets |
|---|---|
| `OTEL_SDK_DISABLED=true` | `enabled: false` |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | `endpoint`, with `/v1/traces` appended |
| `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` | `endpoint`, used as is |
| `OTEL_EXPORTER_OTLP_HEADERS` | `headers` (also `OTEL_EXPORTER_OTLP_TRACES_HEADERS`) |
| `OTEL_TRACES_SAMPLER`, `OTEL_TRACES_SAMPLER_ARG` | the sampler and its ratio |
| `OTEL_PROPAGATORS` | `propagators` |
| `OTEL_SERVICE_NAME`, `OTEL_RESOURCE_ATTRIBUTES` | the resource |

The resource always carries `service.name` (the app's name), `service.version` and `deployment.environment.name`, plus host and process details. `OTEL_SERVICE_NAME` and `OTEL_RESOURCE_ATTRIBUTES` override those, and the `resource` key overrides both.

### What a request produces

Each request gets one server span, named `METHOD /route/pattern` once the router has matched, such as `GET /users/:id`. The name uses the pattern and not the URL, so traffic to a thousand different user IDs lands on one span name. A request that matches nothing keeps the bare method as its name.

The span carries these attributes: `http.request.method`, `url.scheme`, `url.path`, `network.protocol.version`, `server.address`, `user_agent.original`, `http.route` and `http.response.status_code`. A method outside the standard nine is recorded as `_OTHER`, with the original in `http.request.method_original`.

A response with a 5xx status marks the span as an error and sets `error.type`. When a handler returns a 5xx error or panics and the router recovers, the error is recorded on the span as well, with a stack trace for panics. 4xx responses are normal traffic, so they don't mark the span.

Requests whose path starts with anything in `exclude_paths` get no span. The default, `/_/`, keeps Forge's own endpoints (health, metrics, info) out of your traces.

Incoming `traceparent` and `baggage` headers are honoured, so your spans join the caller's trace.

A WebSocket, SSE or WebTransport route is the exception to "one span for the request". Its server span ends at the handshake: after the upgrade for a WebSocket (status 101), once the stream is writable for `EventStream`, right before your handler runs for `SSE()`, and after the upgrade for WebTransport. It carries `forge.stream.kind` (`sse`, `websocket` or `webtransport`) as well as the usual attributes, so a trace of a connection that stays open all day is still a few milliseconds long. Spans you start for each message with `forge.StartSpan` are children of that span. For how long the connection lived and how many messages crossed it, use the [stream metrics](/docs/forge/metrics#stream-connections). A rejected upgrade, a 403 for a bad `Origin` say, is an ordinary request with an ordinary span and no `forge.stream.kind`.

WebTransport sessions run on the router's own HTTP/3 server. Call `EnableWebTransport` and then `StartHTTP3`, and each upgrade gets its span the same way a WebSocket does.

### Add your own spans

`forge.StartSpan` starts a child of whatever span the context carries. Pass it the request's context and end the span when the work is done.

```go
func charge(ctx forge.Context) error {
    spanCtx, span := forge.StartSpan(ctx.Context(), "charge-card")
    defer span.End()

    span.SetAttributes(attribute.String("payment.provider", "stripe"))

    return provider.Charge(spanCtx, order)
}
```

`forge.SpanFromContext(ctx)` returns the current span, or a no-op span when there isn't one, so you can add attributes without checking.

### Trace outgoing calls

`forge.HTTPClient()` returns an `*http.Client` whose requests get a client span and carry the trace headers to the next service. Build it once and reuse it.

```go
var client = forge.HTTPClient()

func fetchUser(ctx context.Context, id string) (*http.Response, error) {
    req, err := http.NewRequestWithContext(ctx, http.MethodGet, "http://users/"+id, nil)
    if err != nil {
        return nil, err
    }

    return client.Do(req)
}
```

Already have a client with its own transport? Wrap the transport with `forge.InstrumentTransport(rt)`. A nil transport means `http.DefaultTransport`.

A client captures the tracer provider and propagators that are current when you build it. One built before `forge.New` still traces, because OpenTelemetry's global hands its spans on to the first provider anyone sets. In a process with several apps, though, a client stays with whichever provider was current when you built it, so build it after the app you want it to follow.

### gRPC calls

The [gRPC extension](/docs/extensions/grpc) gives every served call a server span named like the method (`billing.Invoices/Get`), with the `rpc.system.name`, `rpc.method` and `rpc.response.status_code` attributes, and records its duration in `rpc_server_call_duration_seconds` with the same three labels. Health and reflection calls are left out of both. For calls going out, add `grpcext.ClientDialOptions()` to your `grpc.NewClient`, or use conduit's `Services.GRPC`, which does it for you. Both read the OpenTelemetry globals when you call them, so call them after `forge.New`.

### Send spans somewhere else too

`forge.RegisterSpanProcessor` adds an OpenTelemetry span processor to an app's tracer provider, so you can copy spans into your own store or log.

Read a server span's attributes in `OnEnd`. The HTTP request attributes (`http.request.method`, `url.path` and the rest) are set when the span ends, so in `OnStart` the span only has its name and kind.

```go
app := forge.New(forge.WithAppName("user-api"))

if err := forge.RegisterSpanProcessor(app, myProcessor); err != nil {
    if errors.Is(err, forge.ErrTracingDisabled) {
        // tracing is off, so there is nothing to attach to
    }
}
```

The provider is also in the container as `trace.TracerProvider` (from `go.opentelemetry.io/otel/trace`) if you'd rather start spans from your own tracer.

### Sampling

Without any configuration the ratio is 1.0 (every trace) when the app's environment is empty, `development`, `dev`, `local` or `test`, and 0.1 for every other environment. Sampling is always parent-based: if a caller sent a sampled trace, you keep it, and if they sent an unsampled one, you drop it. The ratio only decides for requests that start a new trace.

To change it, set `sample_ratio` in code or config. A value outside 0 to 1 is clamped and logged as a warning. To pick a sampler by name, use `OTEL_TRACES_SAMPLER` with `OTEL_TRACES_SAMPLER_ARG` for the ratio:

```bash
OTEL_TRACES_SAMPLER=parentbased_traceidratio OTEL_TRACES_SAMPLER_ARG=0.25 ./my-app
```

The names Forge accepts are `always_on`, `always_off`, `traceidratio`, `parentbased_always_on`, `parentbased_always_off` and `parentbased_traceidratio`. Anything else logs a warning and falls back to `parentbased_traceidratio`. A `sample_ratio` in code or config beats these variables entirely.

### Shutdown

Spans are batched, and the batch is flushed when the app stops, after the extensions and the container have shut down so their last spans are included. The flush waits at most five seconds.

<Callout type="warn">
`forge.New` takes over the OpenTelemetry globals: the tracer provider, the propagator and the error handler. If your app set up its own tracer provider in code before `forge.New`, Forge replaces it, and spans you start with `otel.Tracer(...)` go to Forge's provider from then on. That provider only exports when you've configured an endpoint. With `enabled: false` the global becomes a no-op provider, so if you want to keep your own, set it up after `forge.New`.

Already running your own `otelhttp` server middleware? You'll now get two server spans per request. Remove yours, or turn Forge's off with `tracing.enabled: false`.

With more than one Forge app in a process, the last app built sets all three: the tracer provider, the `propagators` setting and the error handler (that one only from an app with tracing on). `forge.StartSpan` reads the globals on every call, so it follows the last app. Each app's own request spans still go to its own provider. Build the app you want the helpers to follow last.
</Callout>

## Profiling

Forge can push continuous profiles to Pyroscope and link each sampled trace to the CPU its request burned. Give it a server address and restart.

```bash
PYROSCOPE_SERVER_ADDRESS=http://localhost:4040 ./my-app
```

Your app now pushes CPU and memory profiles every 15 seconds under its own name, and when you open a sampled request's span in Grafana, you can jump from it to the part of the CPU profile that request produced. Set neither an address nor `span_labels` and nothing runs: the request path pays for one bool check.

### Push to Pyroscope

Every key is optional. This is the `profiling:` block:

```yaml
profiling:
  server_address: http://pyroscope:4040   # empty means no push
  application_name: user-api              # defaults to the app's name
  basic_auth_user: "123456"               # Grafana Cloud wants the instance ID here
  basic_auth_password: ""                 # keep it in PYROSCOPE_BASIC_AUTH_PASSWORD instead
  tenant_id: ""                           # sent as X-Scope-OrgID to a multi-tenant Pyroscope
  tags:
    region: eu-west-1
  profile_types: [cpu, alloc_objects, alloc_space, inuse_objects, inuse_space]
  span_labels: true                       # follows push when you leave it out
```

When the same setting comes from more than one place, the first of these wins:

1. Code: `forge.WithAppProfilingConfig`
2. The `profiling:` block in your Forge config file
3. `PYROSCOPE_*` environment variables
4. The defaults

```go
labels := true

app := forge.New(
    forge.WithAppName("user-api"),
    forge.WithAppVersion("2.1.0"),
    forge.WithAppEnvironment("production"),
    forge.WithAppProfilingConfig(forge.ProfilingConfig{
        ServerAddress: "http://pyroscope:4040",
        Tags:          map[string]string{"region": "eu-west-1"},
        SpanLabels:    &labels,
    }),
)
```

These environment variables are read when the matching key isn't set above them:

| Variable | Sets |
|---|---|
| `PYROSCOPE_SERVER_ADDRESS` | `server_address` |
| `PYROSCOPE_APPLICATION_NAME` | `application_name` |
| `PYROSCOPE_BASIC_AUTH_USER` | `basic_auth_user` |
| `PYROSCOPE_BASIC_AUTH_PASSWORD` | `basic_auth_password` |
| `PYROSCOPE_TENANT_ID` | `tenant_id` |

Setting `PYROSCOPE_SERVER_ADDRESS` on its own turns push on, with nothing in your code or config file. If your app already calls `pyroscope.Start` itself, drop that call when you move to Forge's profiler. Otherwise you run two sessions in one process, and they fight over Go's single CPU profiler.

`tags`, `profile_types` and `span_labels` have no variable. Tags and profile types don't merge between sources: a map or list you set in code replaces the file's entirely, the same way `headers` and `resource` work for tracing, so if your code sets one tag, every tag in your config file is ignored.

Forge adds two tags of its own, `service_version` from the app's version and `environment` from its environment, each only when the app has one. If you set a tag with the same key, yours wins.

Pyroscope only accepts letters, digits, `_`, `.`, `/` and `-` in an application name. Forge turns any other character into `_` and logs a warning, so an app named `My App` profiles as `My_App`. Tag keys are stricter and take letters, digits, `_` and `.` only. A key outside that set, or the reserved `__name__`, is dropped with a warning.

Tag values can hold anything except `,`, `{`, `}` and `=`. The SDK sends tags in the upload's query as `name=app{key=value,...}`, so one of those characters breaks the query and Pyroscope refuses every upload. Forge turns each of them into `_` and logs a warning naming the key and the value you gave. That covers its own `service_version` and `environment` too, so a version of `1.0,rc1` profiles as `1.0_rc1`.

### Profile types

You get `cpu`, `alloc_objects`, `alloc_space`, `inuse_objects` and `inuse_space` by default. Five more are on offer: `goroutines`, `mutex_count`, `mutex_duration`, `block_count` and `block_duration`. A name Forge doesn't know is dropped with a warning, and a list with nothing valid left in it falls back to the defaults.

```yaml
profiling:
  server_address: http://pyroscope:4040
  profile_types: [cpu, inuse_space, goroutines, mutex_duration, block_duration]
```

<Callout type="warn">
Asking for `mutex_count` or `mutex_duration` calls `runtime.SetMutexProfileFraction(5)`, and `block_count` or `block_duration` calls `runtime.SetBlockProfileRate(5)`. Those are runtime settings for the whole process, not for Forge. They replace any rate you set before `app.Start`, they cost a little on every contended lock or blocking call, and they stay in place after the app stops.
</Callout>

### From a trace to its profile

With span labels on, every sampled server span gets a `pyroscope.profile.id` attribute set to its span ID, and the CPU samples taken while its handler ran carry two pprof labels: `span_id`, and `span_name` holding the span's final name, such as `GET /users/:id`. Grafana puts "Profiles for this span" on a span that has the `pyroscope.profile.id` attribute, and finds its samples through the `span_id` label. `span_name` is for per-route flame graphs: filter on it in Pyroscope and you see what one route costs across every sampled request.

To turn the link on in Grafana:

1. Open your Tempo data source's settings and find **Traces to profiles**.
2. Pick your Pyroscope data source.
3. Add a tag that maps `service.name` to `service_name`.
4. Choose a CPU profile type, and save.

The join only works when the two names agree. Pyroscope's `service_name` defaults to the app's name, the same value traces send as `service.name`, so out of the box they match. If you override one (`OTEL_SERVICE_NAME`, say, or `application_name`), set the other to the same value. A name Forge had to rewrite won't match either: traces keep `My App` while profiles say `My_App`, so give the app a name without spaces.

You need tracing on. Labels hang off the server span, so with `tracing.enabled: false` your `span_labels` stays off and Forge logs `profiling: span labels need tracing, which is off, so they stay off`. Only sampled spans get labels, because only a sampled span reaches Tempo.

### Pull with Alloy

You can let Grafana Alloy scrape instead of pushing. Leave `server_address` empty, keep the pprof endpoints on behind a `PprofGuard`, and set `span_labels: true` yourself, since without push it defaults to off.

```go
labels := true

app := forge.New(
    forge.WithAppName("user-api"),
    forge.WithPprofGuard(func(r *http.Request) bool {
        return subtle.ConstantTimeCompare(
            []byte(r.Header.Get("Authorization")), []byte("Bearer "+token)) == 1
    }),
    forge.WithAppProfilingConfig(forge.ProfilingConfig{SpanLabels: &labels}),
)
```

Then point `pyroscope.scrape` at the app. The endpoints live under `/_/debug/pprof`, so the path prefix is `/_`:

```hcl
pyroscope.scrape "user_api" {
  targets           = [{"__address__" = "user-api:8080", "service_name" = "user-api"}]
  forward_to        = [pyroscope.write.default.receiver]
  bearer_token_file = "/etc/alloy/pprof-token"

  profiling_config {
    path_prefix = "/_"
  }
}

pyroscope.write "default" {
  endpoint {
    url = "http://pyroscope:4040"
  }
}
```

Set `service_name` on the target to the app's `service.name`, for the same reason as above.

Pull reads `span_labels` and nothing else from the `profiling:` block. `profile_types`, `tags` and `application_name` only shape what push sends, and the mutex and block rates only get set when push asks for a `mutex_*` or `block_*` type. Go records neither by default, so if you want mutex or block profiles from the pprof endpoints, call `runtime.SetMutexProfileFraction` and `runtime.SetBlockProfileRate` yourself before `app.Start`.

### Limits

Before you trust a flame graph filtered to one span or one route, know where the link between a span and its samples breaks down.

- Labels reach CPU profiles (and goroutine profiles) only. Heap and allocation profiles carry none.
- Go's CPU profiler samples at 100 Hz, so a span shorter than about 10ms usually has no samples at all.
- Goroutines a handler starts inherit its labels. Work handed to a goroutine that already exists, such as a worker pool, loses the link.
- A per-route flame graph filtered by `span_name` only covers the requests tracing sampled. At a ratio of 0.1, that is about one in ten.
- A WebSocket, SSE or WebTransport span ends at the handshake, so its profile link covers the handshake too. Once the stream is up, the goroutine drops `span_id` and keeps `span_name`, which keeps hours of stream CPU off a span that lasted a few milliseconds. The request context still carries `span_id`, though. A stream handler that calls `pprof.Do(r.Context(), ...)` brings `span_id` back, and it stays on the goroutine for the rest of the stream after that `Do` returns.
- `span_name` lives on the goroutine and not on the request context. If a handler or middleware adds labels of its own with `pprof.Do(r.Context(), ...)`, it loses `span_name` inside that `Do` and for the rest of the request after it returns. `span_id`, which is what links the trace, survives.

### Start, stop and failures

The profiler starts in `app.Start`, right after the "starting application" log line and before the before-start hooks, so extension startup shows up in the first profiles. If `app.Start` fails, it stops the profiler again. `app.Stop` stops it last, after the tracing flush, and uploads what is left. That upload gets at most 5 seconds, the same cap as the tracing flush, or less when your stop context ends sooner. When time runs out, Forge logs `profiling: final upload did not finish` and returns. A failed `app.Start` gets the same capped attempt, even with a cancelled context, so a Pyroscope that takes the connection and never answers can't hold your boot error for 30 seconds.

An unreachable Pyroscope never fails `app.Start`. Uploads happen in the background, so a Pyroscope that's down shows up in your logs as `profiling: pyroscope client error` at warn, at most once a minute. The `error` field holds the SDK's own message, and `suppressed` counts the errors in between. The same line covers the SDK's other complaints, such as a full upload queue. If the Pyroscope client can't start at all, Forge logs `profiling: push disabled` at error and keeps booting.

<Callout type="warn">
Go has one CPU profiler per process, and push holds it. While push includes `cpu`, the pprof endpoint `/_/debug/pprof/profile` answers "cpu profiling already in use". Forge logs a warning saying so at start when the pprof endpoints are on. The heap, goroutine and other pprof endpoints still work.
</Callout>

## Metrics

With `metrics.features.http_metrics` on (the default), Forge records the OpenTelemetry HTTP server metrics for every request and serves them at `/_/metrics`. The latency series is `http_server_request_duration_seconds`, labelled by method, route pattern, status code, scheme and error type. Requests that tracing samples carry a `trace_id` exemplar on it, so Grafana can take you from a slow bucket to the trace.

```promql
histogram_quantile(0.95,
  sum by (le, http_route) (rate(http_server_request_duration_seconds_bucket[5m])))
```

Prometheus needs `--enable-feature=exemplar-storage` to keep the exemplars. The label vectors for your own metrics and the series cap are on the [Metrics](/docs/forge/metrics) page. Every series with its labels and buckets is on the [metric reference](/docs/forge/metric-reference), and [Migrating dashboards](/docs/forge/migrating-dashboards) maps the old `forge_http_*` and `forge_grpc_*` names to the new ones.

Metrics can also be pushed. Set `OTEL_EXPORTER_OTLP_ENDPOINT` and Forge sends traces to `/v1/traces` and metrics to `/v1/metrics` under that base URL, every 60 seconds. A traces endpoint set in the `tracing:` block, in code or in `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` doesn't turn metrics push on, so use `metrics_export.endpoint` or `OTEL_EXPORTER_OTLP_METRICS_ENDPOINT` for those. `OTEL_METRICS_EXPORTER=none` keeps the metrics on the scrape endpoint alone while traces still go out. Pick one route per backend, scrape or push, or each series counts twice. The environment variables, `metrics_export:` keys, temporality and naming rules are under [Pushing over OTLP](/docs/forge/metrics#pushing-over-otlp).

## Logger from DI Container

Access the logger from the DI container in services and handlers:

```go
// From handler via container
func handler(ctx forge.Context) error {
    logger, err := forge.GetLogger(ctx.Container())
    if err != nil {
        return forge.InternalError(err)
    }

    logger.Info("processing request")
    return ctx.JSON(200, result)
}

// From application
logger := app.Logger()
```

## Context-Aware Logging

Enrich logs with context information (request ID, user ID, trace ID):

```go
// Set context values in middleware
func requestIDMiddleware(next forge.Handler) forge.Handler {
    return func(ctx forge.Context) error {
        reqID := generateRequestID()
        reqCtx := forge.WithRequestID(ctx.Request().Context(), reqID)
        // ... propagate context
        return next(ctx)
    }
}

// Read context values in handler
func handler(ctx forge.Context) error {
    reqCtx := ctx.Request().Context()

    logger.Info("handling request",
        forge.ContextFields(reqCtx)..., // Automatically includes requestID, traceID, userID
    )

    return ctx.JSON(200, result)
}
```

## Complete Example

```go
package main

import (
    "github.com/xraph/forge"
)

func main() {
    // Use beautiful logger in dev, production logger in prod
    var logger forge.Logger
    if env := os.Getenv("ENV"); env == "production" {
        logger = forge.NewProductionLogger()
    } else {
        logger = forge.NewBeautifulLogger()
    }

    app := forge.New(
        forge.WithAppName("observable-api"),
        forge.WithAppVersion("1.0.0"),
        forge.WithAppLogger(logger),
        forge.WithAppMetricsConfig(forge.MetricsConfig{
            Enabled: true,
            Features: forge.MetricsFeatures{
                RuntimeMetrics: true,
                HTTPMetrics:    true,
            },
        }),
        forge.WithAppHealthConfig(forge.HealthConfig{
            Enabled: true,
            Features: forge.HealthFeatures{
                AutoDiscovery: true,
            },
        }),
    )

    r := app.Router()

    r.GET("/api/users", func(ctx forge.Context) error {
        defer forge.Track(app.Logger(), "listUsers")()

        app.Logger().Info("listing users",
            forge.String("source", ctx.Header("X-Source")),
        )

        return ctx.JSON(200, users)
    })

    // All endpoints available:
    // GET /_/info      - App info
    // GET /_/health    - Health checks
    // GET /_/metrics   - Prometheus metrics
    // GET /_/openapi   - OpenAPI spec
    // GET /_/asyncapi  - AsyncAPI spec

    app.Run()
}
```
