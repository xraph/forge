Forge sends traces over OTLP, and it can push metrics over OTLP too. It also serves metrics at `/_/metrics` for scraping. For each backend below you pick one route for metrics: push them with the same endpoint your traces use, or point a scraper at `/_/metrics`. Traces take a couple of environment variables. Metrics take one more setting, or a scraper.

## Traces

Every backend here accepts OTLP over HTTP, so the setup is the same shape each time: an endpoint, sometimes a header, and a restart.

A few things hold for all of them, because they're about Forge and not the backend:

- `OTEL_EXPORTER_OTLP_ENDPOINT` is a base URL. Forge appends `/v1/traces`. If you set `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` instead, it's used exactly as written, so it has to include `/v1/traces` itself.
- The endpoint must be a full `http://` or `https://` URL. A bare `host:4318` is rejected with one logged error, and the app runs on without exporting.
- OTLP over HTTP with protobuf bodies is the only transport. Forge doesn't read `OTEL_EXPORTER_OTLP_PROTOCOL`, so setting it does nothing, and a gRPC port such as 4317 won't work.
- Header values are percent-encoded. A space is `%20`, so `Basic abc` is written `Basic%20abc`. Separate several headers with commas.
- `OTEL_EXPORTER_OTLP_COMPRESSION=gzip` compresses the export. The OpenTelemetry exporter Forge uses reads it directly.
- `service.name` comes from your app's name. `OTEL_SERVICE_NAME` overrides it.

The [Observability](/docs/forge/observability#configuration) page has the full list of variables and the `tracing:` config block, which takes the same values without the encoding.

### Grafana Cloud

| Variable | Value |
|---|---|
| `OTEL_EXPORTER_OTLP_ENDPOINT` | `https://otlp-gateway-<zone>.grafana.net/otlp`, for example `https://otlp-gateway-prod-us-east-0.grafana.net/otlp` |
| `OTEL_EXPORTER_OTLP_HEADERS` | `Authorization=Basic%20<base64 value from the portal>` |

The zone depends on your stack's region and when it was created, so copy it rather than guessing. Your stack's OpenTelemetry connection page in the Grafana Cloud portal generates both values. Copy them, and check the space after `Basic` is written `%20`.

### Grafana Tempo

| Variable | Value |
|---|---|
| `OTEL_EXPORTER_OTLP_ENDPOINT` | `http://<tempo-host>:4318` |

No header is needed unless you've put auth in front of Tempo. Since Tempo 2.7 the OTLP receiver listens on `localhost:4318` by default, so a Tempo in another container never hears from your app. Set the receiver's endpoint in Tempo's config:

```yaml
distributor:
  receivers:
    otlp:
      protocols:
        http:
          endpoint: "tempo:4318"
```

`0.0.0.0:4318` also works. Tempo's docs warn it exposes the receiver on every interface.

### Jaeger

| Variable | Value |
|---|---|
| `OTEL_EXPORTER_OTLP_ENDPOINT` | `http://<jaeger-host>:4318` |

Jaeger v2's all-in-one image takes OTLP over HTTP on 4318 and serves its UI on 16686:

```bash
docker run --rm --name jaeger -p 16686:16686 -p 4318:4318 \
  cr.jaegertracing.io/jaegertracing/jaeger:2.22.0
```

### Honeycomb

| Variable | Value |
|---|---|
| `OTEL_EXPORTER_OTLP_ENDPOINT` | `https://api.honeycomb.io`, or `https://api.eu1.honeycomb.io` for the EU |
| `OTEL_EXPORTER_OTLP_HEADERS` | `x-honeycomb-team=<api key>` |

A Honeycomb Classic team also needs `x-honeycomb-dataset=<name>` in the headers, comma separated after the key.

### Datadog Agent

| Variable | Value |
|---|---|
| `OTEL_EXPORTER_OTLP_ENDPOINT` | `http://localhost:4318`, or `http://<agent-host>:4318` when the Agent runs in another container |

The Agent doesn't accept OTLP until you turn it on. You need Agent 7.32 or later, with this in `datadog.yaml`:

```yaml
otlp_config:
  receiver:
    protocols:
      http:
        endpoint: 0.0.0.0:4318
```

Or set `DD_OTLP_CONFIG_RECEIVER_PROTOCOLS_HTTP_ENDPOINT=0.0.0.0:4318` on both the core Agent and the trace Agent. Datadog's docs use `localhost:4318` for an Agent installed on the host and `0.0.0.0:4318` for one in a container.

Datadog also takes OTLP traces with no Agent at all:

| Variable | Value |
|---|---|
| `OTEL_EXPORTER_OTLP_ENDPOINT` | `https://otlp.<your Datadog site>`, for example `https://otlp.datadoghq.com` |
| `OTEL_EXPORTER_OTLP_HEADERS` | `dd-api-key=<api key>,compute_stats=true` |

Without `compute_stats=true`, Datadog doesn't compute trace metrics from your spans. A 403 usually means the site in the URL doesn't match your account's. Datadog recommends sending production traffic through an Agent or a Collector.

### New Relic

| Variable | Value |
|---|---|
| `OTEL_EXPORTER_OTLP_ENDPOINT` | `https://otlp.nr-data.net` (US), `https://otlp.eu01.nr-data.net` (EU), `https://otlp.jp.nr-data.net` (JP) or `https://gov-otlp.nr-data.net` (US FedRAMP) |
| `OTEL_EXPORTER_OTLP_HEADERS` | `api-key=<license key>` |
| `OTEL_EXPORTER_OTLP_COMPRESSION` | `gzip` |

New Relic caps a payload at 1 MB and asks you to compress to stay under it. Leaving the port off is fine, since 443 takes OTLP over HTTP.

### OpenTelemetry Collector

| Variable | Value |
|---|---|
| `OTEL_EXPORTER_OTLP_ENDPOINT` | `http://<collector-host>:4318` |

The Collector binds its receivers to `localhost` by default. Give the OTLP receiver an address your app can reach:

```yaml
receivers:
  otlp:
    protocols:
      http:
        endpoint: 0.0.0.0:4318
```

## Metrics

Forge serves metrics at `/_/metrics`, in the Prometheus text format or in OpenMetrics when the scraper asks for it. If the backend takes OTLP, you can skip the scraper and let Forge push. Either way, use one route per backend. Do both into the same place and every series counts twice.

<Callout type="info">
The HTTP latency histogram carries `trace_id` exemplars only in the OpenMetrics format. Prometheus asks for that format on its own. With any other scraper, check its docs before you count on seeing exemplars.
</Callout>

### Pushing metrics

Pushing needs an endpoint. If your traces use `OTEL_EXPORTER_OTLP_ENDPOINT`, metrics follow it. It's a base URL, so Forge sends metrics to `/v1/metrics` under it, every 60 seconds, and `/_/metrics` keeps serving. `OTEL_EXPORTER_OTLP_HEADERS` applies to metrics as well. An endpoint set in the `tracing:` block, in code, or in `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` doesn't carry over, so set `metrics_export.endpoint` or `OTEL_EXPORTER_OTLP_METRICS_ENDPOINT` for those. Set `OTEL_EXPORTER_OTLP_METRICS_ENDPOINT` or `OTEL_EXPORTER_OTLP_METRICS_HEADERS` when metrics need something different from traces. The [metrics page](/docs/forge/metrics#pushing-over-otlp) has the rest: the `metrics_export:` keys, the interval, and how names come out.

If you want traces pushed and metrics left to a scraper, set `OTEL_METRICS_EXPORTER=none`.

| Backend | What to set for metrics |
|---|---|
| Grafana Cloud | Nothing new. The OTLP gateway endpoint and `Authorization` header from the Traces section carry metrics too. Cumulative, the default, is what you want |
| Datadog Agent | Nothing new on the endpoint. The Agent's OTLP receiver on 4318 takes metrics as well as traces. Add `OTEL_EXPORTER_OTLP_METRICS_TEMPORALITY_PREFERENCE=delta` |
| Honeycomb | `OTEL_EXPORTER_OTLP_METRICS_HEADERS=x-honeycomb-team=<api key>,x-honeycomb-dataset=<metrics dataset>`. Metrics need a dataset header, so use the metrics variable and leave the traces header alone |
| New Relic | Same endpoint and `api-key` header as traces. Add `OTEL_EXPORTER_OTLP_METRICS_TEMPORALITY_PREFERENCE=delta`, which New Relic's docs recommend. Cumulative is accepted, but their pages say it can raise SDK memory use and data ingest |
| OpenTelemetry Collector | Nothing extra. The Collector needs a `metrics` pipeline that uses its `otlp` receiver, next to the traces one |

Datadog is stricter about metrics than traces. It wants delta, so set the preference even though the traces side needed nothing. Datadog documents an Agent-free route in [OTLP metrics intake](https://docs.datadoghq.com/opentelemetry/setup/otlp_ingest/metrics/). We haven't verified its endpoint against Forge, so we don't list one here. Going through an Agent or a Collector sidesteps it.

If you send traces to Datadog with no Agent, as in the second table above, metrics push is already on. `https://otlp.<your Datadog site>` is a base endpoint, so Forge now pushes metrics to `/v1/metrics` under it, cumulative, with the same `dd-api-key` header. Datadog's intake wants delta and we haven't verified that URL, so expect the push to fail, with Forge logging an export error about once a minute. Pick one fix. Set `OTEL_METRICS_EXPORTER=none` to keep traces flowing and drop the metrics push. Or set `OTEL_EXPORTER_OTLP_METRICS_ENDPOINT` to the URL on Datadog's metrics intake page together with `OTEL_EXPORTER_OTLP_METRICS_TEMPORALITY_PREFERENCE=delta`.

### Scraping instead

Each backend below has its own scraper. Use these when you'd rather not push.

### Prometheus

```yaml
scrape_configs:
  - job_name: forge
    metrics_path: /_/metrics
    static_configs:
      - targets: ["shop-api:8080"]
```

Start Prometheus with `--enable-feature=exemplar-storage` if you want the exemplars kept. [Grafana in five minutes](/docs/forge/grafana-in-five-minutes) walks through it with a local Grafana.

### Grafana Cloud, through Grafana Alloy

Alloy scrapes the endpoint and remote-writes to your stack's Prometheus:

```hcl
prometheus.scrape "forge" {
  targets = [{
    __address__      = "shop-api:8080",
    __metrics_path__ = "/_/metrics",
  }]
  scrape_interval = "15s"
  forward_to      = [prometheus.remote_write.default.receiver]
}

prometheus.remote_write "default" {
  endpoint {
    url = "https://prometheus-<zone>.grafana.net/api/prom/push"

    basic_auth {
      username = sys.env("REMOTE_WRITE_USERNAME")
      password = sys.env("REMOTE_WRITE_PASSWORD")
    }
  }
}
```

The remote-write URL, username and token come from your stack's Prometheus details in the portal. Without `__metrics_path__` Alloy scrapes `/metrics`, and without `scrape_interval` it scrapes once a minute.

### Datadog Agent

The Agent's OpenMetrics check reads the endpoint. Put this in `conf.d/openmetrics.d/conf.yaml`:

```yaml
instances:
  - openmetrics_endpoint: http://shop-api:8080/_/metrics
    namespace: shop_api
    metrics:
      - http_server_.*
      - forge_.*
      - rpc_server_.*
```

`metrics` takes names or regular expressions, and only what matches is collected. From Agent 7.32 on, write counter names without their `_total` suffix. Running in Docker, you can put the same instance in a `com.datadoghq.ad.instances` label on your app's container instead.

### New Relic

Run Prometheus as above and add a remote write to New Relic:

```yaml
remote_write:
  - url: https://metric-api.newrelic.com/prometheus/v1/write?prometheus_server=shop-api
    authorization:
      credentials: <license key>
```

The EU host is `metric-api.eu.newrelic.com` and the JP host is `metric-api.jp.nr-data.net`. New Relic also documents a Prometheus agent for Kubernetes and an OpenMetrics integration for Docker, if you'd rather not run Prometheus yourself.

### Honeycomb, or anything else through a Collector

The Collector's `prometheus` receiver scrapes the endpoint, and an OTLP exporter sends the result on. For Honeycomb, give metrics their own dataset:

```yaml
receivers:
  prometheus:
    config:
      scrape_configs:
        - job_name: shop-api
          metrics_path: /_/metrics
          scrape_interval: 15s
          static_configs:
            - targets: ["shop-api:8080"]

processors:
  batch: {}

exporters:
  otlp/metrics:
    endpoint: api.honeycomb.io:443
    headers:
      x-honeycomb-team: <api key>
      x-honeycomb-dataset: shop-api-metrics

service:
  pipelines:
    metrics:
      receivers: [prometheus]
      processors: [batch]
      exporters: [otlp/metrics]
```

The same receiver works in front of any backend that takes OTLP metrics. Swap the exporter. A `$` anywhere in the receiver's config has to be written `$$`.

This config scrapes `/_/metrics`. If Forge also pushes to this Collector, as it does when `OTEL_EXPORTER_OTLP_ENDPOINT` points here, the same series arrive twice. Remove the `prometheus` receiver and let Forge push, or set `OTEL_METRICS_EXPORTER=none` on the app and keep the scrape.
