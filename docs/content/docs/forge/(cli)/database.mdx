# Database Commands

The `forge db` command provides comprehensive database migration tools. It supports SQL and Go migrations, app-scoped migration isolation, multiple database connections, and safe rollback operations. Migrations are powered by [grove](https://github.com/xraph/grove) under the hood.

<Callout type="warn">
Every `forge db` command that touches a database generates a small Go program, runs `go mod tidy` and `go build` against it, and executes the result. Your project has to compile for any of that to work. If `go build ./...` fails on its own, `forge db migrate` and its siblings will fail too, with the same error.
</Callout>

## Main Command

### `forge db` (alias: `database`)

Database management tools.

```bash
forge db migrate
forge db status
forge db rollback
forge database migrate    # Full alias
```

**Note:** The main command requires a subcommand. Use `forge db --help` to see all available subcommands.

## Common Flags

Most `forge db` subcommands accept these flags for database connection and scoping:

| Flag | Alias | Default | Description |
|---|---|---|---|
| `--database` | `-d` | `"default"` | Database name from project config |
| `--dsn` | | `""` | Override database DSN/connection string |
| `--app` | `-a` | `""` | App name for app-scoped migrations |
| `--verbose` | `-v` | `false` | Show debug output (paths, table names, etc.) |

There is no flag for picking a database type. Forge reads it straight off your DSN's scheme, `postgres://`, `mysql://`, and so on. See [Supported databases](#supported-databases) for the full list.

## Subcommands

### `forge db init`

Initialize migration tables in the database and create the migrations directory.

```bash
forge db init
forge db init --database=analytics
forge db init --app=api-gateway
forge db init --dsn="postgres://user:pass@localhost/mydb"
forge db init --force                     # Rewrite an existing migrations.go
```

**Flags:**
- `--force` / `-f` -- Rewrite `migrations.go` with the current scaffold even if it already looks current

**Behavior:**

`init` runs in two stages, and only the second one needs a database:

1. It scaffolds first. It ensures the migrations directory exists and writes `migrations.go` if it is missing. This step is pure filesystem work, so it always succeeds, even against a project with no database running yet.
2. It creates grove's tracking tables (`grove_migrations` and `grove_migration_locks`) second. If the database is unreachable at this point, `init` says exactly that: your migrations package was scaffolded, but the tables were not created, and it exits non-zero so scripts notice.

When `--app` is provided, the scaffolded `migrations.go` names its migration group after that app. There are no per-app tables to create; see [App-scoped migrations](#app-scoped-migrations) for how grove isolates apps instead.

**Upgrading a project from before grove:** older Forge wrote a `migrations.go` that re-exported `database.Migrations` from the database extension. That extension is gone, and nothing can build against the file it left behind, so every `forge db` command would fail inside `go build`. `init` recognizes that file and rewrites it against grove's registry, then tells you it did. Your migration files are not touched. Run `forge db adopt` next if the database already has migrations applied.

### `forge db migrate`

Run all pending migrations.

```bash
forge db migrate                          # Run all pending migrations
forge db migrate --database=analytics     # Use a named database connection
forge db migrate --app=api-gateway        # Run app-scoped migrations only
forge db migrate --dsn="postgres://..."   # Override connection string
forge db migrate --verbose                # Show debug information
```

**Behavior:**
- Discovers and runs all pending migrations in order
- Auto-initializes migration tables if they do not exist
- Builds a runner binary from your migrations package and executes it
- When `--app` is provided, runs only the migrations registered to that app's group
- Shows a spinner with progress information

<Callout type="info">
Every migration, whether you wrote it in SQL with `create-sql` or in Go with `create-go`, ends up as a registered Go value in your migrations package. `forge db migrate` always builds and runs a binary, not just when it happens to see a `.go` file lying around.
</Callout>

---

### `forge db rollback`

Rollback the last group of applied migrations.

```bash
forge db rollback                      # Rollback last migration group
forge db rollback --app=api-gateway    # Rollback app-scoped migrations
forge db rollback --database=analytics # Use a named database connection
```

**Behavior:**
- Prompts for confirmation before rolling back
- Rolls back the last migration group (all migrations applied in the same batch)
- Supports both SQL and Go migrations
- When `--app` is provided, rolls back only that app's migrations

### `forge db reset`

Reset the database by rolling back all migrations and re-running them.

```bash
forge db reset                   # Interactive confirmation
forge db reset --force           # Skip confirmation
forge db reset --app=api-gateway # Reset app-scoped migrations only
```

**Flags:**
- `--force` / `-f` -- Skip the confirmation prompt

<Callout type="warn">
This is a destructive operation. It rolls back **all** applied migrations and then re-runs them from scratch. Always back up your database before running this in production.
</Callout>

### `forge db create-sql`

Create a new SQL migration.

```bash
forge db create-sql add_users_table
forge db create-sql add_orders_table --tx
forge db create-sql add_user_roles --app=auth-service
```

**Flags:**
- `--tx` -- Create transactional migration files (`.tx.up.sql` / `.tx.down.sql`)
- `--app` / `-a` -- Create migration in an app-scoped directory

**Behavior:**

This writes three files, not two. Grove has no filesystem discovery at all, so the SQL on its own would never run; the third file is what registers it.

- `{timestamp}_{name}.up.sql` -- the up migration, an empty template for you to fill in
- `{timestamp}_{name}.down.sql` -- the down migration, same
- `{timestamp}_{name}.go` -- embeds both files and registers them with grove

<Callout type="warn">
Commit the `.go` file alongside the two `.sql` files. Without it, grove never sees the migration, and `forge db migrate` behaves as if it does not exist.
</Callout>

**Example:**
```bash
forge db create-sql create_users_table
# Created: database/migrations/20240115100000_create_users_table.up.sql
# Created: database/migrations/20240115100000_create_users_table.down.sql
# Created: database/migrations/20240115100000_create_users_table.go
```

<Tabs items={["Up migration", "Down migration", "Go wrapper"]}>
<Tab value="Up migration">
```sql
-- database/migrations/20240115100000_create_users_table.up.sql
CREATE TABLE users (
    id SERIAL PRIMARY KEY,
    name VARCHAR(255) NOT NULL,
    email VARCHAR(255) UNIQUE NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```
</Tab>
<Tab value="Down migration">
```sql
-- database/migrations/20240115100000_create_users_table.down.sql
DROP TABLE IF EXISTS users;
```
</Tab>
<Tab value="Go wrapper">
```go
// database/migrations/20240115100000_create_users_table.go
package migrations

import (
    "context"
    _ "embed"

    "github.com/xraph/grove/migrate"
)

//go:embed 20240115100000_create_users_table.up.sql
var upm20240115100000 string

//go:embed 20240115100000_create_users_table.down.sql
var downm20240115100000 string

func init() {
    App.MustRegister(&migrate.Migration{
        Name:    "create_users_table",
        Version: "20240115100000",
        Up: func(ctx context.Context, exec migrate.Executor) error {
            _, err := exec.Exec(ctx, upm20240115100000)
            return err
        },
        Down: func(ctx context.Context, exec migrate.Executor) error {
            _, err := exec.Exec(ctx, downm20240115100000)
            return err
        },
    })
}
```
</Tab>
</Tabs>

You never need to write this file by hand for a migration `create-sql` generates. You do need to write one by hand if you are carrying over `.sql` files from before this change; see [Migrating existing SQL files](#migrating-existing-sql-files) below.

### Migrating existing SQL files

If you have `.up.sql` / `.down.sql` pairs on disk from before Forge moved to grove, they stopped running the moment this shipped. Grove was never told about a filesystem convention for SQL; it only knows about migrations registered in Go, and a loose pair has no such registration.

You need a `migrations.go` in the directory first, the one `forge db init` writes, since the wrapper below registers against the `App` value it defines. Run `forge db init` once if you don't already have one.

**Write the wrapper by hand.** This is the path to use, and for anything already applied to a live database it is the only safe one. Add a `.go` file next to the existing pair. It keeps the original filenames and the original timestamp, so the migration holds its place in the ordering and, more importantly, keeps the version that `forge db adopt` recorded for it:

```go
package migrations

import (
    "context"
    _ "embed"

    "github.com/xraph/grove/migrate"
)

//go:embed 20240115100000_create_users.up.sql
var upCreateUsers string

//go:embed 20240115100000_create_users.down.sql
var downCreateUsers string

func init() {
    App.MustRegister(&migrate.Migration{
        Name:    "create_users",
        Version: "20240115100000",
        Up: func(ctx context.Context, exec migrate.Executor) error {
            _, err := exec.Exec(ctx, upCreateUsers)
            return err
        },
        Down: func(ctx context.Context, exec migrate.Executor) error {
            _, err := exec.Exec(ctx, downCreateUsers)
            return err
        },
    })
}
```

Point the `//go:embed` directives at your actual filenames, and set `Version` to the same timestamp prefix the files already use. Do this for every loose pair; there is no batch tool for it, because grove has no way to enumerate what used to be there.

<Callout type="warn">
Do not re-run `forge db create-sql` for a migration that has already been applied to a live database. `create-sql` stamps the current time as the version, so you get a *new* version that will never match the one `adopt` recorded from your bun history. Grove sees an unknown migration, and `forge db migrate` runs it again against a schema that already has it. That is the exact failure `adopt` exists to prevent.

Re-running `create-sql` and pasting your SQL into the fresh files is fine for a migration that has never been applied anywhere. For anything else, write the wrapper.
</Callout>

Create a new Go migration file.

```bash
forge db create-go add_seed_data
forge db create-go populate_defaults --app=api-gateway
```

**Flags:**
- `--app` / `-a` -- Create migration in an app-scoped directory

**Behavior:**
- Creates a single `.go` migration file with `init()` function boilerplate
- Go migrations can execute arbitrary Go code during migration (useful for data transformations, seeding, etc.)

<Callout type="info">
Go migrations require a `migrations.go` file in the migrations directory. Run `forge db init` to generate it if missing.

### `forge db lock`

Manually acquire the migration lock. Prevents other processes from running migrations concurrently.

```bash
forge db lock
forge db lock --app=api-gateway
```

---

### `forge db unlock`

Manually release the migration lock.

```bash
forge db unlock
forge db unlock --app=api-gateway
```

<Callout type="info">
You typically do not need to use `lock`/`unlock` manually. Forge acquires and releases the lock automatically when running `migrate`, `rollback`, or `reset`. Use these commands only to recover from a stuck lock (e.g., after a crash).
</Callout>

### `forge db mark-applied`

Mark all pending migrations as applied without actually running them.

```bash
forge db mark-applied
forge db mark-applied --app=api-gateway
```

**Behavior:**
- Prompts for confirmation
- Marks all pending migrations as applied in the tracking table using no-op execution
- Useful when migrations were applied manually or outside of Forge

### `forge db adopt`

Record a database's existing migration history into grove, without running anything.

```bash
forge db adopt
forge db adopt --dry-run
forge db adopt --app=api-gateway
```

**Flags:**
- `--dry-run` -- Report what would be adopted, and record nothing
- `--app` / `-a` -- Adopt into a specific app's migration group

**Why you need this:** grove starts out knowing nothing about your database. If you are upgrading a project that already has migrations applied through the old bun-based runner, grove has no record of them, so the next plain `forge db migrate` would try to run every one of those historical migrations again, against a schema that already has them. `adopt` closes that gap once, up front.

**Behavior:**
- Reads the legacy migration table (`bun_migrations`, or the app-scoped equivalent under `--app`) and grove's own tables side by side
- Records every legacy row grove does not already know about, so a subsequent `forge db migrate` sees them as already applied and moves straight to what is actually pending
- Refuses to run if it cannot find the legacy table, rather than silently doing nothing. If you are adopting a database that genuinely has no prior migration history, there is nothing to adopt and no reason to run this command
- Is idempotent: running it twice adopts nothing the second time
- Is app-aware: pass `--app` to adopt one app's legacy table into that app's migration group, the same way `migrate` and the rest scope by app

Run this once, right after you upgrade a project with an existing, already-migrated database, and before you run `forge db migrate` against it for the first time. A brand new database with no prior migrations does not need it; `forge db init` is enough there.

**If your project still has the old `migrations.go`:** the one that re-exported `database.Migrations` from the removed database extension. Run `forge db init` first. It detects that file, rewrites it against grove, and leaves your migration files alone. Until you do, no `forge db` command can build its runner, `adopt` included.

**What adopt records:** the old bun migration table stores only the timestamp of each applied migration. The descriptive half of the filename was never a column in it, so there is nothing to recover. Adopted rows therefore show up in `forge db status` as `adopted_<timestamp>`. Grove matches an applied migration on its group and version, not its name, so the display name has no effect on what runs.

#### Rollback and reset after adopt

An adopted row records that a migration ran. It does not record *how*, because the code for it is not registered anywhere in your project. So if the most recently applied migration is an adopted one, both of these fail:

```bash
forge db rollback
# Error: migrate: applied migration app/20240115120000 not found in registered groups
```

`forge db reset` fails the same way, since it is a loop of rollbacks.

This is not a bug you can clear by re-running the command. What to do:

- **Rolling forward is unaffected.** `forge db migrate` and `forge db status` work normally. Anything you create after adopting rolls back normally too, right up until the rollback reaches an adopted row.
- **If you need rollback for a historical migration,** write the wrapper for it: a `.go` file with the original `Version` and a real `Down`, as shown under [Migrating existing SQL files](#migrating-existing-sql-files). Once grove can find a definition for that version, rollback works.
- **Do not "fix" it by re-running `create-sql`.** A fresh timestamp will not match the adopted version, and `forge db migrate` will then apply that migration again to a schema that already has it.

## App-Scoped Migrations

App-scoped migrations allow you to isolate migrations for individual applications within a monorepo. Each app gets its own migration directory, and its own migration group inside grove.

### How It Works

When you pass the `--app` flag, Forge:

1. **Resolves a separate migration directory** for that app
2. **Scopes the run to that app's grove group**, so migrations don't interfere with other apps

```bash
# Create a migration for the api-gateway app
forge db create-sql create_routes --app=api-gateway

# Run only api-gateway migrations
forge db migrate --app=api-gateway

# Check status for api-gateway only
forge db status --app=api-gateway
```

### Migration Directory Resolution

Forge resolves app-scoped migration paths using a two-step process:

1. **App config override:** If the app has its own `.forge.yaml` with `database.migrations_path`, that path is used (relative to the app directory).
2. **Centralized convention:** Otherwise, Forge creates a subdirectory under the global migrations path: `<global_migrations_path>/<app-name>/`.

```
# Default centralized layout
database/
  migrations/
    20240115_create_shared_table.up.sql      # Global migrations
    20240115_create_shared_table.down.sql
    api-gateway/                              # App-scoped
      20240120_create_routes.up.sql
      20240120_create_routes.down.sql
    auth-service/                             # App-scoped
      20240120_create_sessions.up.sql
      20240120_create_sessions.down.sql
```

### App Config Override

To use a custom migration path for an app, add a `database` section to the app's `.forge.yaml`:

```yaml
# apps/api-gateway/.forge.yaml
app:
  name: api-gateway

database:
  migrations_path: db/migrations   # Relative to this app's directory
  seeds_path: db/seeds
```

This results in migrations stored at `apps/api-gateway/db/migrations/` instead of the centralized location.

### Group scoping, not table namespacing

Before grove, app isolation worked through separate tables: `bun_migrations_api_gateway` sat next to `bun_migrations_auth_service`, each with its own lock table. That is gone. Grove hardcodes two table names, `grove_migrations` and `grove_migration_locks`, and there is no way to tell it to use different ones per app.

Instead, isolation happens through grove's own concept of a group. Every migration belongs to one, and `App` in your scaffolded `migrations.go` is that group, named after the app by default:

```go
// database/migrations/api-gateway/migrations.go
var App = migrate.NewGroup("api-gateway")
```

`--app=api-gateway` tells the runner to operate on the `api-gateway` group specifically. Rows for every app still land in the same two tables, `grove_migrations` and `grove_migration_locks`, distinguished by a `group` column rather than by which table they are in. Practically, this changes nothing about how you use `--app` day to day; it changes what to expect if you go looking at the database directly.

## Go Migrations

Go migrations allow you to write migrations in Go for complex data transformations, seeding, or operations that are difficult to express in pure SQL.

### Setup

1. Initialize the migrations directory:

```bash
forge db init
```

This creates a `migrations.go` file with two package-level values: `Registry`, which holds every migration group your application owns, and `App`, the group your generated migrations register into.

2. Create a Go migration:

```bash
forge db create-go seed_default_roles
```

3. Edit the generated file:

```go
package migrations

import (
    "context"

    "github.com/xraph/grove/migrate"
)

func init() {
    App.MustRegister(&migrate.Migration{
        Name:    "seed_default_roles",
        Version: "20240120090000",
        Up: func(ctx context.Context, exec migrate.Executor) error {
            // Up migration
            _, err := exec.Exec(ctx, "INSERT INTO roles (name) VALUES ($1)", "admin")
            return err
        },
        Down: func(ctx context.Context, exec migrate.Executor) error {
            // Down migration
            _, err := exec.Exec(ctx, "DELETE FROM roles WHERE name = $1", "admin")
            return err
        },
    })
}
```

`exec` is grove's `migrate.Executor`. It gives you `Exec` and `Query` for raw SQL, so anything you would otherwise script by hand, an insert loop, a data backfill, a bulk transformation, runs here as ordinary Go rather than a wall of SQL.

### How Go migrations run

Every `forge db` command that touches migrations, not just when it spots a `.go` file, does the same thing:

1. Generates a `main.go` for a runner in a temporary directory
2. Runs `go mod tidy` and `go build` against it, importing your migrations package
3. Executes the built binary with the requested command (`migrate`, `rollback`, `status`, and so on)
4. Cleans up the temporary directory

Because SQL migrations are also Go files under the hood (see [`create-sql`](#forge-db-create-sql)), this build step happens on every run, whether your migrations directory has hand-written Go in it or not. It also means the runner will not build, and the command will fail, if your project itself does not compile. Fix `go build ./...` first.

You can freely mix SQL and Go migrations in the same directory; both register into the same group and run in timestamp order.

### Mixing SQL and Go Migrations

A migrations directory built entirely with `create-sql` and `create-go` looks like this:

```
database/migrations/
  migrations.go                              # Registry and App
  20240115100000_create_users.up.sql         # SQL migration
  20240115100000_create_users.down.sql
  20240115100000_create_users.go             # Registers the pair above
  20240120090000_seed_default_data.go        # Go migration, self-contained
  20240125140000_add_indexes.tx.up.sql       # Transactional SQL migration
  20240125140000_add_indexes.tx.down.sql
  20240125140000_add_indexes.go              # Registers the pair above
```

## Database Connection

### Connecting via Config

Define database connections in your project's `.forge.yaml` or `config.yaml`:

```yaml
# .forge.yaml
database:
  connections:
    default:
      dsn: "postgres://user:pass@localhost:5432/myapp?sslmode=disable"
    analytics:
      dsn: "postgres://user:pass@localhost:5432/analytics?sslmode=disable"
```

Use the `--database` flag to select a named connection:

```bash
forge db migrate --database=analytics
```

### Connecting via DSN

Override the connection string directly:

```bash
forge db migrate --dsn="postgres://user:pass@localhost:5432/mydb?sslmode=disable"
```

### Supported databases

Forge reads the scheme off your DSN and picks a grove driver from it. These schemes are recognized:

| Scheme | Database |
|---|---|
| `postgres`, `pg` | PostgreSQL |
| `mysql` | MySQL |
| `sqlite` | SQLite |
| `mongodb`, `mongo` | MongoDB |
| `clickhouse` | ClickHouse |
| `turso` | Turso |

`postgresql://` is accepted too; Forge normalizes it to `postgres` before resolving a driver, so either prefix works.

Anything outside that list fails with an error naming the scheme it did not recognize and listing what is supported, so you do not have to go digging through source to fix a typo'd DSN. `elasticsearch://` is a special case: grove ships an Elasticsearch driver, but no migration executor for it, so `forge db` rejects it explicitly rather than letting it fail somewhere deeper in the run.

### Environment Variables

Database connections support environment variable expansion. Forge loads `.env` files in this priority order:

1. `.env` -- Base environment
2. `.env.local` -- Local overrides (gitignored)
3. `.env.{environment}` -- Environment-specific (e.g., `.env.production`)
4. `.env.{environment}.local` -- Environment-specific local overrides

The environment is determined by `FORGE_ENV` or `GO_ENV` (defaults to `development`).

```bash
# .env
DATABASE_URL=postgres://user:pass@localhost:5432/myapp?sslmode=disable
```

```yaml
# .forge.yaml (references the env variable)
database:
  connections:
    default:
      dsn: "${DATABASE_URL}"
```

## Migration File Conventions

### SQL Migrations

SQL migration files use this naming pattern:

| Pattern | Description |
|---|---|
| `{timestamp}_{name}.up.sql` | Standard up migration |
| `{timestamp}_{name}.down.sql` | Standard down migration |
| `{timestamp}_{name}.tx.up.sql` | Transactional up migration |
| `{timestamp}_{name}.tx.down.sql` | Transactional down migration |
| `{timestamp}_{name}.go` | Registers the pair above with grove. `create-sql` always writes this alongside the SQL; commit all three together |

Transactional migrations (created with `--tx`) wrap the entire migration in a database transaction, ensuring atomicity.

### Go Migrations

Go migration files use the pattern `{timestamp}_{name}.go` and must be in the same package as `migrations.go`.

## Best Practices

1. **Version control migrations** -- Always commit migration files, including the `.go` file `create-sql` generates alongside your SQL. Without it, grove never sees the migration.
2. **Write reversible migrations** -- Always include a down migration for safe rollback.
3. **Keep migrations small and focused** -- One logical change per migration is easier to review and rollback.
4. **Use transactional migrations** -- Use `--tx` for DDL changes that should be atomic.
5. **Use Go migrations for data transformations** -- Complex data seeding or transformation logic is better expressed in Go than SQL.
6. **Use app-scoped migrations in monorepos** -- Isolate each app's schema changes to avoid conflicts and enable independent deployments.
7. **Run `adopt` once when upgrading an existing database** -- Skipping it means the next `forge db migrate` re-runs your entire migration history against a schema that already has it.
8. **Back up before production migrations** -- Always have a backup before running migrations in production.
9. **Test in development first** -- Run `forge db migrate` locally, verify with `forge db status`, then promote to staging and production.

## Troubleshooting

### No Migrations Found

```bash
forge db migrate
# No migrations found
```

**Solution:** Create your first migration:

```bash
forge db create-sql initial_schema
# or for app-scoped:
forge db create-sql initial_schema --app=my-app
```

### A `.sql` file exists but never runs

If `forge db status` doesn't list a migration you know is on disk, check for a matching `.go` file next to the `.up.sql` / `.down.sql` pair. Grove has no filesystem discovery; a loose SQL pair with no registration is invisible to it. See [Migrating existing SQL files](#migrating-existing-sql-files).

### The migration runner will not build

```bash
forge db migrate
# Error: .../migrations/migrations.go still registers migrations with the
# removed database extension, so the migration runner cannot be built.
```

Your project predates the move to grove. Run `forge db init` (add `--app` if the migrations are app-scoped). It rewrites `migrations.go` against grove's registry and leaves your migration files where they are. Then run `forge db adopt` before `forge db migrate`, so grove does not re-run history the database already has.

### `forge db rollback` says a migration is not in a registered group

```bash
forge db rollback
# Error: migrate: applied migration app/20240115120000 not found in registered groups
```

The most recently applied migration was recorded by `adopt`, which means grove knows it ran but has no code for it, so there is no `Down` to execute. `forge db reset` fails the same way. See [Rollback and reset after adopt](#rollback-and-reset-after-adopt) for what to do.

### `--type` is not accepted

```bash
forge db migrate --type=postgres
# Error: --type was removed
```

The driver now comes from the DSN scheme and nothing else. Write `postgres://`, `mysql://`, `sqlite://`, `mongodb://`, `clickhouse://` or `turso://` in the DSN itself, whether it comes from `--dsn`, `.forge.yaml`, `config.yaml`, or `DATABASE_URL`.

### Database Connection Error

```bash
forge db migrate
# Error: database connection failed
```

**Solution:**

```bash
# Check your database is running
pg_isready -h localhost -p 5432

# Verify your DSN
forge db migrate --dsn="postgres://user:pass@localhost:5432/mydb" --verbose

# Check your .forge.yaml or config.yaml
cat .forge.yaml
```

### Migration Lock Stuck

If a previous migration run crashed and left the lock acquired:

```bash
forge db unlock
# or for app-scoped:
forge db unlock --app=api-gateway
```

### Missing `migrations.go`

If you see a warning about a missing `migrations.go` file:

```bash
forge db init
# or for app-scoped:
forge db init --app=api-gateway
```

This generates the required package registration file for Go migrations.
