# Deployment Workbench Proposal

You describe your services and the databases, buckets and caches they need in
one `deploy:` block, and Forge renders and applies that to Compose, Kubernetes
or a managed platform. The local page, the terminal and an AI agent all go
through the same planner, so the choice you make in one place is the choice the
others see.

<Callout type="info">
  The versioned config editor, migration, catalog, service discovery and
  `inspect`, `init`, and offline `doctor` commands are implemented. The local
  page and provider lifecycle are being connected to that engine. The mock
  remains a browser preview and performs no deployments.
</Callout>

## Inspect and configure your project

```bash
forge deploy inspect --output json
forge deploy init --non-interactive --yes \
  --answer deploy.services.worker.health=none \
  --answer deploy.resources.cache.features=json,search
forge deploy doctor --offline --output json
forge deploy schema
```

Initialization reads your build apps, runtime config and extension descriptors.
Every suggestion has a source and confidence. Imports alone need an explicit
answer before a resource is added. Invalid config blocks the write. Existing
versioned blocks are preserved. Use `forge deploy init --force` to propose
missing keys while keeping your saved choices, or `forge deploy migrate --dry-run`
to review an older block, then `forge deploy migrate --yes` to save it with a
backup. Saving checks the source hashes again and writes the exact proposal
you reviewed. If those files changed, review a new proposal first.

Offline inspection checks local secret references and leaves cluster references
unverified. It does not contact Kubernetes. Use online `doctor` to check those
references before you apply.

An environment can select services with `services: [api, worker]`. A call to an
excluded service needs an `external_services` endpoint. Resource generation
follows the selected bindings, and deselection never schedules data deletion.

Grove's default connection uses `extensions.grove.dsn`; named connections use
`databases` entries. Grove KV follows the same default versus named-store
rule. Each named Trove store receives its own `storage_driver`, bucket and
`grove_database`. Secrets are references, and malformed secret-file errors do
not print their contents.

## Try the mock

[Open the workbench mock](/mock/workbench.html).

The page reads a sample project with a public gateway, a private API and a
worker. The API and worker use a named Grove PostgreSQL database, a Trove
store with its metadata in that database, and Redis through Grove KV. It is
laid out in the order the CLI runs, and the margin names the command each
section mirrors.

You start with no deploy block. One click suggests it from the files Forge
read, with the source file and line beside every value, and leaves two
decisions open: how the worker's health is observed, and whether the app uses
Redis JSON or search. Deploy stays off until you answer. Switch the
environment to production and the lifecycle of each resource becomes a
question too, with a secret reference that has to resolve before preflight
passes.

Save shows the exact change to `.forge.yml` and marks the page saved. Run
checks fills the preflight list for the chosen target. Build plan writes the
operations into the ledger with a hash, and approving it turns the ledger into
the journal, row by row, with a healthy rollout, a failed migration or a
readiness timeout as the simulated outcome. The files section shows what you
own and what Forge renders, and the last section shows the same steps as
commands and the JSON an agent would read. Everything is simulated and nothing
leaves your browser.

The [deployment dashboard mock](/mock/deploy.html) starts with large target
cards before opening the sidebar. Choose several targets and switch between
their saved profiles. The service list lets you deploy a subset, with an
existing API binding required when you select the gateway and exclude API.
The plan, connection graph and generated overlays follow that selection.

Data and messaging settings let you propose an existing broker, a target
container or a separate Docker host. Images & registry offers local builds,
remote builders, CI, immutable existing images and provider Git builds. Render
Git settings include the repository, branch and manual, CI-check or commit
trigger; Kubernetes has a separate manifest delivery option for an existing
GitOps controller. Registry authentication and access checks are simulated.
No token is collected.

Environment & storage includes environment creation and Files, SQLite or
PostgreSQL persistence settings. Files are the proposed default. The mock
always stores drafts in this browser, and downloaded files are schema
proposals. It does not create an environment, connect a database, write to your
repository, push Git commits or deploy services.

Light, Dark and System themes, a collapsible desktop sidebar, a mobile drawer,
keyboard tabs and compact icon actions are available. Theme, target profiles
and configuration choices survive reload. The newer workflow and schema
proposals are described in the
[target and delivery design](https://github.com/xraph/forge/blob/main/docs/deployment/WORKBENCH_WORKFLOWS.md).

## The flow

From nothing, on a laptop with Docker:

```bash
# Planned commands. Not available in the current CLI.
forge deploy init        # suggests the deploy block, asks the open questions
forge deploy up          # plan and apply the default environment
forge deploy status
forge deploy logs api -f
forge deploy destroy --env dev
```

In CI:

```bash
forge deploy doctor --target k8s-prod --env production --output json
forge deploy plan   --target k8s-prod --env production --out plan.json
forge deploy apply  --plan plan.json --approve-plan "$PLAN_HASH" --non-interactive
```

For an agent, the same four commands with `--output json`: `inspect` returns
the resolved model and the open decisions, `doctor` returns diagnostics with a
file, line, field and fix, `plan` prints a hash, and `apply` takes that hash and
refuses anything else. Exit codes are stable: 2 invalid input, 3 unresolved
decisions, 4 unsupported, 5 access, 6 stale plan, 7 apply failed, 8 timeout.

## Files you own

| File                                                | Purpose                                                                                                                        |
| --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `.forge.yml` or `.forge.yaml`                       | Project and build settings plus the `deploy:` block with `version: 2`: services, resources, environments, targets and secrets. |
| `deploy/stack.yml`, `deploy/environments/<env>.yml` | Optional splits of the same keys for large stacks, named from `deploy.spec` and `deploy.environment_files`.                    |
| `config/<service>.yaml`                             | Your runtime configuration as it is today. The compiler reads it for suggestions and never edits it.                           |
| `deploy/lock.yml`                                   | Descriptor versions, recipe ids and image digests per environment. Committed.                                                  |
| `deployments/<target>/<env>/`                       | Generated artifacts with a manifest of file hashes. Your edits go in `patches/` beside them and survive regeneration.          |
| `.forge/plans/`, `.forge/state/`                    | Plans, the apply journal, locks and releases. Gitignored, restrictive permissions, no secret values in plans.                  |

The page saves through the CLI's file editor. Comments, anchors and keys the
CLI does not know survive, and a write that finds the file changed by someone
else returns a conflict with a diff instead of overwriting.

## Resources, Grove, Trove and Redis

Grove and Trove run inside your app. Forge provisions or binds their backends
and writes the real extension settings: named Grove databases with their
driver and DSN, Trove's storage DSN, bucket and metadata database, Grove KV's
driver and DSN. Each resource has a lifecycle per environment: `container`
(a pinned recipe with a volume, the Compose default), `external` (an existing
service through a secret reference) or `managed` (the platform provisions it).

Bindings reach the app through an overlay file the compiler renders per
service and mounts at `/etc/forge/overlay.yaml`. The overlay holds no secret
value; it references `${ATLAS_PRIMARY_DSN}` and the target injects that from
its secret store. A small framework change, `FORGE_CONFIG_OVERLAY`, loads the
file between `config.local.yaml` and environment variables, so a real
environment variable still wins. Where a platform cannot mount files, the
same content goes through `FORGE_CONFIG_OVERLAY_YAML`.

How does the CLI know what Grove or Trove needs? A catalog of descriptors
ships in the CLI for Grove, Grove KV, Trove, the Forge cache, queue, events,
search, Kafka and MQTT extensions, and the forgery extensions that take a
`grove_database`. Extension modules can ship a `forge-deploy.yaml` the CLI
reads from the module cache, and you can add descriptors for in-house
extensions under `deploy/descriptors/`. Static discovery only ever produces
suggestions; the `deploy:` block you confirm is what gets deployed.

Redis requirements include the features your app uses. A managed Redis that
speaks the protocol but rejects `JSON.SET` fails the plan before any app rolls
out.

## Service communication

The service name is the app name. On Compose that resolves on the shared
network, on Kubernetes it is the Service DNS name in the namespace, and on
Render or DigitalOcean it is the platform's private reference. For each
`calls` edge the compiler writes `services.<name>.url` into the caller's
overlay and `<NAME>_URL` into its environment, and the generated Forge client
gains a resolver that reads them. Only `exposure: public` ports get a route.
Receiving services still run their auth middleware; discovery and private
networking do not grant authorization.

## Targets and order

| Target                                      | First path                                                                         | Plan |
| ------------------------------------------- | ---------------------------------------------------------------------------------- | ---- |
| Docker Compose                              | render, apply, observe, logs, rollback, destroy                                    | 03   |
| Kubernetes                                  | Kustomize base and overlays, migration Job, apply with rollout observation         | 04   |
| Local page                                  | `forge deploy start` on loopback with a token, file save and one-click apply       | 05   |
| Render, DigitalOcean                        | export verified against the provider schema, then apply after a live run           | 06   |
| Module descriptors, gateways, hosted target | `forge-deploy.yaml` in grove and trove, `kind: gateway`, a ctrlplane-backed target | 07   |

Each adapter publishes a level: renderable, validated, apply, or live
qualified. Nothing claims a level it has not earned.

## Where the design lives

The design spec, the shared contracts and the implementation plans are
working documents under `docs/superpowers/` in the forge checkout. That
directory is gitignored, so you will find them next to the code and not on
GitHub.

- `docs/superpowers/specs/2026-10-09-forge-deploy-design.md`: decisions, the
  `deploy:` schema, the architecture, the CLI contract and the slice order.
- `docs/superpowers/plans/2026-10-09-forge-deploy-00-contracts.md`: package
  names, signatures, diagnostic codes and fixtures the plans share.
- `docs/superpowers/plans/2026-10-09-forge-deploy-01-honest-cli-and-spec.md`,
  `02-discover-catalog-resolve.md` and `03-compose.md`: the first three
  slices as small test-first tasks. Plans 04 to 07 are written when 03 ships.
- [Source review](https://github.com/xraph/forge/blob/main/docs/deployment/PLAN.md):
  what the current commands do, with file references, and the acceptance
  gates for live providers.
