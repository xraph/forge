# Build and Deployment

You can deploy a Forge project to Docker Compose from its `.forge.yml` or
`.forge.yaml`. The planner selects services, resolves their database and storage
bindings, generates files and records each operation during apply.

```bash
forge deploy inspect
forge deploy init
forge deploy doctor --env dev
forge deploy up --env dev
forge deploy status --env dev
forge deploy logs api --env dev --tail 200
forge deploy destroy --env dev
```

`destroy` keeps persistent data. Add `--delete-data` only when you intend to
remove the selected backend volumes.

<Callout type="info">
  Compose has an implemented lifecycle adapter. The real integration test covers
  PostgreSQL through Grove, Redis JSON and search, Trove object writes, service
  communication and persistence across restart. The local workbench and other
  adapters are being implemented. You can preview the [workbench
  design](/docs/forge/deployment-workbench).
</Callout>

## Configure a target

```yaml
project:
  name: atlas
  module: example.com/atlas
build:
  apps:
    - name: api
      cmd: ./cmd/api

deploy:
  version: 2
  defaults:
    environment: dev
    target: local
  services:
    api:
      app: api
      kind: web
      ports:
        http: { port: 8080, exposure: public }
      bindings:
        - { resource: primary, extension: grove, database: primary }
      migrate: auto
  resources:
    primary: { type: postgres, version: "17" }
  targets:
    local: { provider: compose }
  environments:
    dev:
      target: local
      resources:
        primary: { lifecycle: container }
```

`init` reads your build apps, runtime config and extension descriptors. You review
its suggestions and answer unresolved decisions before saving. `init --force`
adds missing keys while preserving saved values and comments. For an older
block, run `migrate --dry-run`, then `migrate --yes` to save a backup and version 2.

You can keep several named targets. Pass `--target <name>` and `--env <name>` to
select one. An environment can restrict services with `services: [api, worker]`;
`plan`, `export` and `up` also accept `--services api,worker` within that scope.
A selected service that calls an excluded service needs an `external_services`
address. Deselection does not remove existing containers or data.

## Resources and runtime config

| Backend        | Container recipe                                            |
| -------------- | ----------------------------------------------------------- |
| PostgreSQL     | PostgreSQL 17 with persistent data and readiness            |
| MySQL          | MySQL 8.4 with persistent data                              |
| MongoDB        | MongoDB 7 with persistent data                              |
| Redis          | Redis 7, or Redis Stack when you require `json` or `search` |
| Object storage | RustFS with a persistent volume and bucket initialization   |
| Messaging      | NATS JetStream or RabbitMQ with retained data               |
| SMTP           | Mailpit for local development                               |

Container credentials are generated once and saved privately under
`.forge/state/<target>/<env>/generated.env`. Exported files contain references.
You can bind an existing backend with `lifecycle: external` and a named secret;
use the environment, file or Kubernetes secret resolver. A compatible endpoint
still needs the features your app declares. Managed provisioning is unsupported
by the Compose adapter.

Your effective runtime config is preserved in an overlay with the binding values
replaced by secret references. Named Grove databases, Grove KV stores and Trove
stores keep their own settings. Trove also receives its metadata database
binding. New Forge versions read `FORGE_CONFIG_OVERLAY`; older versions use the
mounted `config.local.yaml` fallback. Both are generated from the same model.

Declare real migration entry points. `migrate: auto` runs the app's `migrate up`
command before rollout. Import the migration executor for your Grove driver,
including `github.com/xraph/grove/drivers/pgdriver/pgmigrate` for PostgreSQL.
A failed migration stops rollout and leaves the journal and data available for
recovery. Completed migrations are skipped when you retry the same saved plan.

## Review, export and apply

```bash
forge deploy plan --env dev --output json
forge deploy export --plan .forge/plans/dev-local-HASH.json
forge deploy apply --plan .forge/plans/dev-local-HASH.json \
  --approve-plan FULL_HASH --non-interactive --output json
```

The JSON response includes `data.hash` and the saved plan path. Approve the full
hash, not its filename prefix. Apply checks the plan's integrity, expiry and
source files again. A changed source, configuration or generated artifact blocks
apply until you review a fresh plan. Only one apply can hold an environment lock.

Generated artifacts live in `deployments/<target>/<env>`. The ownership manifest
tracks their hashes. Regeneration preserves user files and edited generated
files; `export --force` explicitly replaces edited generated files. Apply refuses
skipped files. Keep custom configuration in the source deploy block while you
review the generated output. Arbitrary patch files are preserved but are not
merged into Compose artifacts.

Compose builds in Docker by default. Set `build: { builder: host }` on a target
to cross-compile Go on your machine and package the binary in a runtime image.
Host builds need complete module sums and a Linux platform; they do not support
CGO or custom Dockerfiles. Remote Buildx builders use `source: remote` and a named
`builder`. `source: existing` and `source: ci` require immutable `build.images`
references for every selected service. Registry delivery uses your Docker
credential configuration; dedicated connection management is being added to the
workbench.

## Commands

Every command accepts `--config`, `--target`, `--env`, `--timeout`,
`--output text|json`, `--non-interactive` and `--no-color`.

| Command                                     | Additional options                                                       |
| ------------------------------------------- | ------------------------------------------------------------------------ |
| `init`                                      | `--force`, `--yes`, repeated `--answer path=value`                       |
| `migrate`                                   | `--dry-run`, `--yes`                                                     |
| `schema`, `inspect`, `providers`, `catalog` | No additional options                                                    |
| `doctor`                                    | `--offline`                                                              |
| `plan`                                      | `--services`, `--out`                                                    |
| `export`                                    | `--services`, `--plan`, `--output-dir`, `--force`                        |
| `apply`                                     | `--plan`, `--approve-plan`, `--allow-destructive`                        |
| `up`                                        | `--services`, `--plan`, `--approve-plan`, `--yes`, `--allow-destructive` |
| `status`                                    | No additional options                                                    |
| `logs SERVICE`                              | `--tail`, `--follow`                                                     |
| `rollback`                                  | `--release`, `--yes`                                                     |
| `destroy`                                   | `--delete-data`, `--yes`                                                 |

Rollback uses recorded image IDs. It refuses a release with irreversible or
unqualified migrations; use a forward migration in that case. Status counts all
replicas. Disabled readiness or an unprobed external resource produces
`accepted`, not `healthy`.

JSON output uses the `forge.deploy/v1` envelope with `ok`, `data` and structured
`diagnostics`. Exit codes are 0 for success, 2 for invalid input, 3 for unresolved
decisions, 4 for unsupported operations, 5 for access failures, 6 for conflicts,
7 for apply failures and 8 for timeout or cancellation. Offline inspection does
not contact Kubernetes and reports remote secret references as unverified.

## Other platforms and legacy commands

The shared typed engine currently applies Compose targets. Kubernetes and managed
platform adapters are being added. Until they land, you can export draft files
with `forge infra k8s export`, `forge infra render export` or
`forge infra do export`, then validate and deploy through the provider's tools.
Those legacy exports do not generate the complete version 2 resource graph.
`forge infra docker export` forwards version 2 projects to the shared engine.

For legacy Kubernetes exports, render your selected Kustomize overlay, verify
the context and namespace, and use server-side dry-run before apply. Legacy
`infra k8s deploy` validates Kustomize and rejects service filtering. It does not
claim application readiness. Plain Service DNS does not require discovery RBAC;
only enable the discovery extension when your app needs Kubernetes API watches.

## Build without deploying

```bash
forge build
forge build --app api --platform linux/amd64 --production
forge build --output ./dist
```

Build contexts must contain the modules and workspace files your app uses. For
native libraries or CGO, supply your own Dockerfile and build configuration.
