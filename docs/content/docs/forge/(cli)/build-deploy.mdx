# Build and Deployment

You can build Go applications and export Docker Compose, Kubernetes, DigitalOcean and Render configuration with the current CLI. Review the generated files before you use them.

<Callout type="warn">
  `forge deploy` and `forge cloud` currently contain simulated operations. The
  DigitalOcean and Render `forge infra ... deploy` handlers also report success
  without submitting a deployment. Their success messages do not establish a
  running application. Docker Compose and Kubernetes infra handlers invoke real
  tools, but do not verify application readiness.
</Callout>

For the proposed file-backed local page, service communication model and resource provisioning workflow, see the [Deployment Workbench Proposal](/docs/forge/deployment-workbench). Its commands are planned, not available in the current CLI.

## Current support

| Command family                                                                   | Current behavior                                                                                       |
| -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `forge build`                                                                    | Runs Go builds for selected or discovered applications.                                                |
| `forge infra docker export`                                                      | Writes Compose files, Dockerfiles and an environment example.                                          |
| `forge infra k8s export`                                                         | Writes application Deployments, Services and Kustomize overlays.                                       |
| `forge infra do export`                                                          | Writes an App Platform app spec and supporting files.                                                  |
| `forge infra render export`                                                      | Writes a Render Blueprint and supporting files.                                                        |
| `forge infra docker deploy`                                                      | Invokes Docker Compose to build/start the stack. Review build paths, ports and runtime settings first. |
| `forge infra k8s deploy`                                                         | Invokes kubectl apply. The current fallback/filtering behavior needs review before use.                |
| `forge deploy`, `forge deploy docker`, `forge deploy k8s`, `forge deploy status` | Simulated build/push/deployment or fixed status data.                                                  |
| `forge infra do deploy`, `forge infra render deploy`, `forge cloud`              | Simulated remote operations. Export and use the provider's own deployment workflow.                    |
| `forge deploy start`, `plan`, `export`, `apply`                                  | Proposed workbench commands. Not implemented.                                                          |

## Build applications

```bash
forge build
forge build --app api-gateway
forge build --platform linux/amd64
forge build --production
forge build --output ./dist
```

| Flag             | Purpose                         | Default                        |
| ---------------- | ------------------------------- | ------------------------------ |
| `-a, --app`      | Build one application           | All discovered/configured apps |
| `-p, --platform` | Set target OS and architecture  | Host platform                  |
| `--production`   | Enable production build options | Disabled                       |
| `-o, --output`   | Binary output directory         | `./bin`                        |

Both `.forge.yml` and `.forge.yaml` are accepted. You can keep the spelling already in your project.

```yaml
project:
  name: atlas
  module: example.com/atlas
  layout: single-module
build:
  output_dir: ./bin
  auto_discover: true
  ldflags: "-s -w"
  apps:
    - name: api-gateway
      cmd: ./cmd/api-gateway
      output: api-gateway
```

Multi-module applications need a build context that includes the modules and workspace inputs they use. Do not assume the current generated single-module Dockerfile handles your workspace, CGO dependencies or native libraries.

## Export infrastructure

```bash
forge infra docker export
forge infra k8s export
forge infra do export
forge infra render export
```

`kubernetes` is an alias for `k8s`; `digitalocean` is an alias for `do`. Each export accepts `--output` (`-o`) and `--force` (`-f`). Use a fresh output directory when you want to compare regenerated files without overwriting your edits.

```bash
forge infra k8s export --output ./deployment-review/k8s
forge infra docker export --output ./deployment-review/docker
```

Default outputs:

```text
deployments/
  docker/
    docker-compose.yml
    docker-compose.dev.yml
    docker-compose.prod.yml
    .env.example
    Dockerfile.<app>
  k8s/
    base/
      deployment.yaml
      service.yaml
      kustomization.yaml
    overlays/
      dev/kustomization.yaml
      prod/kustomization.yaml
  do/
    app.yaml
    .env.example
    README.md
  render/
    render.yaml
    .env.example
    README.md
```

The generated overlays are `dev` and `prod`. They are not automatically created for every environment name in your project configuration.

### Review the generated runtime contract

The current generator uses defaults that may not match your application: port 8080, a Go 1.22 builder image, mutable application tags, `/health` for liveness and `/ready` for readiness. Configure the correct Go toolchain, build path, container port, image reference and probe routes before deployment. Check the routes your app actually registers; Forge system routes and custom health handlers can use different paths.

For Compose, also review the build context and Dockerfile location. Exported Dockerfiles live in the export directory, and the generated relative paths need to match where you run the build. Multiple default host-port mappings can collide.

The `.env.example` file is a starting point. It does not provision a database, create a bucket, install Redis features or connect an extension to its backend. Do not commit populated credentials.

### Kubernetes

The export creates application Deployments and ClusterIP Services. It does not create the full infrastructure your application may need, including data services, persistent storage, migration jobs, secrets, ingress/TLS, network policies or required controllers.

After reviewing and fixing the generated files, you can render and validate the selected overlay explicitly:

```bash
kubectl kustomize deployments/k8s/overlays/dev
kubectl --context YOUR_CONTEXT apply --dry-run=server -k deployments/k8s/overlays/dev -n YOUR_NAMESPACE
```

Create the intended namespace through your normal infrastructure process. Verify the context before a real apply. Server-side dry-run validates the cluster-facing resources without establishing that the application or its data connections work.

The current `forge infra k8s deploy` supports `--env`, `--namespace`, `--service` and `--dry-run`. Its dry-run uses client-side validation. Its Kustomize availability check uses an obsolete kubectl flag, and the exported Kustomize apply helper does not enforce the requested service filter. Until those are fixed, render and apply your reviewed overlay with kubectl directly and do not rely on `--service` to limit the resource set.

### Docker Compose

`forge infra docker deploy` supports `--service`, `--env` and `--build`. It uses exported files when present and otherwise generates a temporary stack. This starts containers; it does not establish durable storage, successful migrations or healthy service communication.

Validate your edited Compose file with `docker compose config`, then use your normal Compose workflow to start and inspect the stack. For production on one host, you still need explicit volume retention, secret handling, backup/restore and operational ownership.

### DigitalOcean and Render

Use the export commands to get draft provider files. Validate them against the provider's current schema and deploy through the provider console or CLI. The Forge deploy handlers for these providers are placeholders.

Render has distinct public web, private service and worker types. DigitalOcean supports internal service ports while its workers and jobs cannot receive inbound traffic. Review the type assigned to each application and use the provider's connection-property bindings. See the [Render Blueprint reference](https://render.com/docs/blueprint-spec), [DigitalOcean app spec](https://docs.digitalocean.com/products/app-platform/reference/app-spec/) and [internal routing guide](https://docs.digitalocean.com/products/app-platform/how-to/manage-internal-routing/).

## Grove, Trove and Redis

Grove and Trove run inside your application. Deploy their database and storage backends, then configure the extensions with the connection names and store names your application uses.

You need to account for:

- Every named Grove connection, its driver, credentials and migrations.
- Trove's object backend, bucket, credentials and Grove metadata database.
- Shared Trove dashboard content signing secrets when multiple instances verify tickets.
- The Redis features your application uses, persistence requirements and ACLs.
- Runtime configuration paths and verified environment-variable overrides.

The current infrastructure introspector does not fully recognize Grove/Trove requirements, named connections or dependencies configured outside `main.go`. Declare and provision them explicitly. A Redis-compatible endpoint does not by itself prove Redis JSON or search compatibility.

The [workbench proposal](/docs/forge/deployment-workbench) describes a deployment catalog that can bind these requirements to local containers, Kubernetes recipes or managed resources.

## Service communication

Use private service addresses for internal calls and expose only the intended public entry points. On Kubernetes you can use Service DNS. On Compose you can use the service name on the shared network. Managed platforms have their own private networking and connection references.

The existing discovery extension has a Kubernetes backend that lists and watches namespace-scoped Services. Use it when your application needs dynamic discovery; ordinary DNS calls do not need Kubernetes API access. FARP can carry service contract metadata, but discovery does not authorize a request or automatically establish a secure gateway route.

Receiving services must still validate identity, audience and grants. Verify a real service call, a denied call, backend outage recovery and trace propagation before you call the deployment healthy.

## Automation today

In CI, you can build and export draft infrastructure with the current CLI. Use your existing provider deployment tool after you have validated the artifacts and configured credentials. Do not use simulated `forge deploy` or `forge cloud` success as a release gate.

```bash
forge build --production
forge infra k8s export --output ./deployment-review/k8s
```

The proposed `inspect`, `doctor`, `plan`, `export` and `apply` commands will provide structured errors, reproducible artifacts and an immutable plan hash for non-interactive deployment. Read the [proposed workflow](/docs/forge/deployment-workbench) before adopting those command names in scripts.
