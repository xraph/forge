WebTransport is a modern protocol that provides low-latency, bidirectional communication over QUIC (HTTP/3). It supports multiple concurrent streams, datagrams, and offers significantly lower latency than WebSocket for performance-critical applications.

<Callout type="warn">
WebTransport requires HTTP/3 (QUIC) support. Currently supported in Chrome 97+, Edge 97+, and Opera 83+. Firefox and Safari support is in development. Your server must be configured with TLS certificates for HTTP/3.
</Callout>

## Enabling WebTransport

WebTransport is off until you call `EnableWebTransport` on the router, and your WebTransport routes are only served by the router's own HTTP/3 server, which you start with `StartHTTP3`. It listens on UDP next to your regular HTTP server.

```go
app := forge.New(forge.WithAppName("wt-server"))
r := app.Router()

if err := r.EnableWebTransport(forge.DefaultWebTransportConfig()); err != nil {
    log.Fatal(err)
}

// Register WebTransport routes with r.WebTransport, before or after StartHTTP3.

cert, err := tls.LoadX509KeyPair("cert.pem", "key.pem")
if err != nil {
    log.Fatal(err)
}

if err := r.StartHTTP3(":443", &tls.Config{Certificates: []tls.Certificate{cert}}); err != nil {
    log.Fatal(err)
}
defer r.StopHTTP3()
```

`StartHTTP3` binds the UDP socket before it returns, so a port that's already taken comes back as its error, and then serves in the background. Call it again while it's running and you get an error. `StopHTTP3` closes every open session, then the socket.

## WebTransportHandler Signature

```go
type WebTransportHandler func(ctx forge.Context, session forge.WebTransportSession) error
```

## WebTransportSession Interface

A session represents a single WebTransport connection and can host multiple streams.

```go
type WebTransportSession interface {
    // AcceptStream accepts an incoming bidirectional stream
    AcceptStream(ctx context.Context) (WebTransportStream, error)

    // OpenStream opens a new bidirectional stream
    OpenStream() (WebTransportStream, error)

    // AcceptUniStream accepts an incoming unidirectional stream
    AcceptUniStream(ctx context.Context) (WebTransportStream, error)

    // OpenUniStream opens a new unidirectional stream
    OpenUniStream() (WebTransportStream, error)

    // SendDatagram sends an unreliable datagram
    SendDatagram(data []byte) error

    // ReceiveDatagram receives a datagram
    ReceiveDatagram(ctx context.Context) ([]byte, error)

    // Close closes the session
    Close() error

    // Context returns the session context
    Context() context.Context
}
```

## WebTransportStream Interface

A stream provides ordered, reliable, bidirectional byte transfer within a session.

```go
type WebTransportStream interface {
    // Read, Write and Close move raw bytes
    io.ReadWriteCloser

    // ReadJSON decodes the next JSON value from the stream
    ReadJSON(v any) error

    // WriteJSON writes v as JSON, followed by a newline
    WriteJSON(v any) error
}
```

`WriteJSON` ends every value with a newline, so a stream you write with it is newline-delimited JSON. That's what the generated TypeScript client's `receiveIterator` expects, and a JSON decoder on the other end reads one value per call.

`ReadJSON` doesn't need the newlines. It reads values back to back however the client sent them, two in one packet or one split across several, and you can switch between it and `Read` on the same stream without losing bytes. Read a stream from one goroutine at a time.

## Basic Usage

```go
r := app.Router()

r.WebTransport("/wt/echo", func(ctx forge.Context, session forge.WebTransportSession) error {
    // Accept a bidirectional stream from the client
    stream, err := session.AcceptStream(ctx.Request().Context())
    if err != nil {
        return err
    }
    defer stream.Close()

    buf := make([]byte, 4096)
    for {
        n, err := stream.Read(buf)
        if err != nil {
            return nil // Stream closed
        }

        if _, err := stream.Write(buf[:n]); err != nil {
            return err
        }
    }
})
```

## Multiple Streams

WebTransport's key advantage over WebSocket is multiplexing -- multiple independent streams over a single connection.

```go
r.WebTransport("/wt/multiplex", func(ctx forge.Context, session forge.WebTransportSession) error {
    // Handle multiple streams concurrently
    for {
        stream, err := session.AcceptStream(session.Context())
        if err != nil {
            return nil // Session closed
        }

        go handleStream(stream)
    }
})

func handleStream(stream forge.WebTransportStream) {
    defer stream.Close()

    buf := make([]byte, 4096)
    for {
        n, err := stream.Read(buf)
        if err != nil {
            return
        }
        stream.Write(buf[:n])
    }
}
```

## Datagrams

Datagrams provide unreliable, unordered delivery -- ideal for data where occasional loss is acceptable (game state, sensor readings, video frames).

```go
r.WebTransport("/wt/game", func(ctx forge.Context, session forge.WebTransportSession) error {
    // Send datagrams (fire-and-forget, low latency)
    go func() {
        ticker := time.NewTicker(16 * time.Millisecond) // ~60fps
        defer ticker.Stop()

        for {
            select {
            case <-session.Context().Done():
                return
            case <-ticker.C:
                gameState := getGameState()
                data, _ := json.Marshal(gameState)
                session.SendDatagram(data)
            }
        }
    }()

    // Receive datagrams from client
    for {
        data, err := session.ReceiveDatagram(session.Context())
        if err != nil {
            return nil
        }
        processClientInput(data)
    }
})
```

## Unidirectional Streams

Use unidirectional streams when data flows in only one direction.

```go
r.WebTransport("/wt/logs", func(ctx forge.Context, session forge.WebTransportSession) error {
    // Server opens a unidirectional stream to push logs
    stream, err := session.OpenUniStream()
    if err != nil {
        return err
    }
    defer stream.Close()

    for logEntry := range logChannel {
        data, _ := json.Marshal(logEntry)
        data = append(data, '\n')
        if _, err := stream.Write(data); err != nil {
            return err
        }
    }

    return nil
})
```

## WebTransportConfig

Start from the defaults and change what you need before you pass it to `EnableWebTransport`.

```go
config := forge.DefaultWebTransportConfig()
config.MaxBidiStreams = 200
config.MaxUniStreams = 50
config.AllowedOrigins = []string{"https://app.example.com"}
```

| Setting | Default | Description |
|---------|---------|-------------|
| `MaxBidiStreams` | 100 | Bidirectional streams a client may have open in a session at once. Zero means 100 and a negative value allows none |
| `MaxUniStreams` | 100 | Unidirectional streams a client may have open in a session at once. Zero means 100 and a negative value allows none |
| `StreamReceiveWindow` | 6MB | Per-stream flow control window |
| `ConnectionReceiveWindow` | 15MB | Per-connection flow control window |
| `KeepAliveInterval` | 30000 | Keep-alive interval, in milliseconds |
| `MaxIdleTimeout` | 60000 | How long a connection may sit idle before it's closed, in milliseconds |
| `AllowedOrigins` | empty | Origins a browser may connect from. Empty means same-origin only, and `"*"` allows any origin. A request with no `Origin` header, from a non-browser client, is always allowed |
| `EnableDatagrams` | true | Has no effect. Every WebTransport session needs datagrams, so they're always on |
| `MaxDatagramFrameSize` | 65536 | Largest datagram payload you can send or receive, in bytes. Zero or less means no limit beyond QUIC's |

The stream limits are QUIC's. The server lets a connection carry one session, so a limit on the connection is a limit on the session. HTTP/3 takes a few streams of its own: the CONNECT request that opened the session holds a bidirectional one, and the client's control stream and QPACK encoder and decoder streams hold three unidirectional ones. Forge adds those on top of what you set, so a browser gets exactly `MaxBidiStreams` and `MaxUniStreams`. A quic-go client doesn't open the QPACK streams, so it gets two unidirectional streams more than you set. Any other HTTP/3 request the client sends on the same connection uses a bidirectional stream while it runs.

When a webtransport-go client is at a limit, its `OpenStream` and `OpenUniStream` fail with a stream limit error and the `Sync` variants wait. A stream stops counting against the limit once both sides are done with it.

A datagram has to fit in one QUIC packet, so QUIC caps its payload at about 1200 bytes until the connection learns it can send bigger packets. The 65536 default never gets a say, then. Set `MaxDatagramFrameSize` lower when you want a smaller cap of your own. A `SendDatagram` over it fails with `*quic.DatagramTooLargeError`, the same error QUIC returns over its own cap, and `MaxDatagramPayloadSize` on the error tells you the limit you hit. An incoming datagram over it is dropped and `ReceiveDatagram` waits for the next one, so a client can't end your receive loop by sending one big datagram, and dropped datagrams don't count in `forge_stream_messages_total`. Clients aren't told your limit: quic-go always advertises its own.

## When to Use WebTransport

WebTransport excels in specific scenarios:

- **Real-time gaming** -- Datagrams provide the lowest latency for game state updates
- **Media streaming** -- Multiple streams for audio, video, and control channels
- **IoT telemetry** -- High-frequency sensor data with optional reliability
- **File transfer** -- Multiple concurrent file transfers over one connection
- **Low-latency APIs** -- When WebSocket latency is too high

For most web applications, WebSocket or SSE will be simpler and more broadly supported. Use WebTransport when you need the performance benefits of QUIC.
