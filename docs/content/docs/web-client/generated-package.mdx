Generating the orders API with `--hooks` produces this:

```
src/generated/
├── src/
│   ├── types.ts        your Go types, as TypeScript
│   ├── ops.ts          the operation manifest: cache contract per endpoint
│   ├── hooks.ts        one typed binding per operation
│   ├── rest.ts         typed method per REST endpoint
│   ├── codecs.ts       wire-name to client-name mapping
│   ├── capabilities.ts declared scopes, as types plus a can() helper
│   ├── client.ts       base client: auth, request assembly
│   ├── fetch.ts        HTTP transport
│   ├── errors.ts       typed error classes
│   ├── pagination.ts   pagination helpers
│   └── index.ts        re-exports everything above
├── tests/
├── package.json
├── tsconfig.json
└── README.md
```

`websocket.ts` and `sse.ts` join them when the source specification declares channels; a document with no streaming endpoints produces neither.

Add `--client-only` to get `src/` alone, without `package.json`, `tsconfig.json` or the test and CI scaffolding — the right choice when the client lives inside an existing application rather than as its own package.

## `types.ts`

Your response and request types, named as they are in Go.

```ts title="src/types.ts"
export interface Customer {
  id: string;
  name: string;
}

export interface Order {
  customer: Customer;
  id: string;
  status: string;
  total: number;
}

export interface OrderPage {
  items: Order[];
  total: number;
}
```

It also carries transport-level types — `ConnectionState`, `AuthConfig`, `ClientConfig` — and the discriminated error union.

## `ops.ts`

The manifest. This is the file that carries everything the server knew and a hand-written client would have had to rediscover: which endpoint returns which entity, what identifies it, and what each write makes stale.

```ts title="src/ops.ts"
export const ops = {
  listOrders: {
    method: 'GET',
    path: '/orders',
    entity: 'Order',
    rootType: 'OrderPage',
    provides: ['Order:{id}', 'Order[]'],
    invalidates: [],
    responseCodec: 'OrderPage',
  },
  createOrder: {
    method: 'POST',
    path: '/orders',
    entity: 'Order',
    rootType: 'Order',
    provides: ['Order:{id}'],
    invalidates: ['Order[]'],
    responseCodec: 'Order',
  },
} as const satisfies Record<string, OperationMeta>;

export const entities = {
  Customer: { idField: 'id' },
  Order: { idField: 'id', fields: { customer: 'Customer' } },
  OrderPage: { fields: { items: 'Order' } },
} as const satisfies Record<string, EntityMeta>;

export const streams = [
] as const;
```

Three exports:

- **`ops`** — one row per operation. `entity` is what the cache contract is about; `rootType` is the typename of the response document itself, which is what indexes the entities table. They differ on a paginated read, and the distinction is load-bearing: normalizing an `OrderPage` against `Order` would read `Order`'s field edges against an envelope's properties and descend into nothing.
- **`entities`** — identity and field edges per typename. A row with no `idField` is a signpost, not a record: it is walked for its fields and never stored.
- **`streams`** — channel-to-entity bindings, populated from an AsyncAPI document.

<Callout type="info">
`ops.ts` is worth reading in code review. It is the diff that shows a colleague changed what a mutation invalidates, and it is what `forge client diff` classifies. A change here with no change to any request or response shape is exactly the cache-breaking category.
</Callout>

## `hooks.ts`

One line per operation. No bodies, no per-endpoint logic, nothing to regenerate when the runtime changes.

```ts title="src/hooks.ts"
/**
 * Typed hooks over the operation manifest.
 *
 * Generated. Each line is a binding, not an implementation.
 *
 * The bodies live in @forge-go/client-core, so a runtime defect is fixed by
 * upgrading that package rather than by regenerating this one.
 */

import { query, mutation } from '@forge-go/client-core';
import { ops } from './ops';

export const useGetCustomer = query(ops.getCustomer);
export const useListOrders = query(ops.listOrders);
export const useCreateOrder = mutation(ops.createOrder);
export const useGetOrder = query(ops.getOrder);
export const useUpdateOrder = mutation(ops.updateOrder);
export const useDeleteOrder = mutation(ops.deleteOrder);
```

`query(...)` and `mutation(...)` come from `@forge-go/client-core` and return module-level constants, not React hooks. They are framework-agnostic bindings; the framework adapter is what turns one into something a component can call.

That indirection is the whole "no bloat" claim. A runtime defect is fixed by publishing `@forge-go/client-core`, not by regenerating every repository consuming your API, and a new framework is a new adapter rather than a second generator.

<Callout type="warn">
`GET` becomes `query`, everything else becomes `mutation`. An endpoint that reads but is modelled as `POST` — a search with a large body, say — is bound as a mutation and will not be cached as a read.
</Callout>

## `rest.ts`

A typed method per endpoint, on a class. This is the plain client, and it has **no dependency on the runtime**.

```ts title="src/rest.ts"
export class RESTClient extends Client {
  public readonly listOrders = async (options?: { signal?: AbortSignal; retry?: { maxAttempts?: number } }): Promise<types.OrderPage> => {
    let __path = `/orders`;
    const config: RequestConfig = {
      method: 'GET',
      url: __path,
      signal: options?.signal,
      retry: options?.retry,
      responseCodec: "OrderPage",
    };

    return this.request<types.OrderPage>(config);
  };
}
```

Adoption is per-component: one screen may use `useListOrders()` from the runtime while the next calls `client.listOrders()` directly, from the same generated package. The runtime drives this client rather than replacing it.

## `codecs.ts`

A table describing, per schema, how a wire payload maps onto its TypeScript shape.

```ts title="src/codecs.ts"
// Generated codec table
//
// Describes, per schema, how a wire payload maps onto its TypeScript
// shape. `ts` is the client-side field name derived from the wire name by
// the configured FieldNaming strategy (or a FieldOverrides entry); encode
// and decode below walk this table to rename between the two.

export type Codec =
  | { kind: 'object'; fields: Record<string, { ts: string; codec?: string | undefined }>; required?: string[]; values?: string }
  | { kind: 'array'; items?: string }
  | { kind: 'record'; values?: string }
  | { kind: 'union'; discriminator?: { wire: string; map: Record<string, string> }; members: string[] }
  | { kind: 'passthrough' };
```

This is why `--field-naming camel` can rename `invoice_number` to `invoiceNumber` without the cache losing track: the manifest's `idField` is renamed through the same function that builds this table, so the two cannot drift. A second implementation of the naming rule would silently produce a normalizer looking for a field the payload does not have — no error, nothing stored.

## `capabilities.ts`

Generated when any route declares scopes through `forge.WithRequiredAuth`. A specification with no scopes produces no file — the capability union would have no members.

```go title="server"
api.POST("/orders", createOrder,
    forge.WithRequiredAuth("jwt", "orders.write"),
)
```

```ts title="src/capabilities.ts"
export type Capability =
  | 'orders.read'
  | 'orders.write';

export function setCapabilities(scopes?: Iterable<string>): void;
export function capabilitiesKnown(): boolean;
export function can(capability: Capability): boolean;
export function canCall(operation: OperationName): boolean;
export function missingCapabilities(operation: OperationName): readonly Capability[];
```

<Callout type="warn">
This is a **UX affordance and never a security boundary**. Every answer is computed from client-held state, so anyone can call `setCapabilities` from a console and flip all of them to `true`. Authorization stays server-side and unconditional. Hiding a button is not access control, and nothing in the generated request path consults these predicates.
</Callout>

Tell it what the current principal holds, then ask:

```ts
setCapabilities(session.scopes);   // on sign-in and after a refresh
setCapabilities();                 // on sign-out

if (can('orders.write')) {
  // render the button
}
```

`Capability` is a union rather than `string`, so `can('orders.wirte')` is a compile error. A typo that merely returned `false` would hide the action forever and look exactly like a permission the user lacks.

**Before anything is known, `can()` returns `false`.** That is deliberate — the alternative, a tri-state, makes `if (can(x))` truthy during load and shows the button to everyone. Where the resulting flicker matters, ask first:

```tsx
if (!capabilitiesKnown()) return <Skeleton />;

return can('orders.write') ? <CreateOrderButton /> : null;
```

`canCall` answers the same question per operation, and returns `true` for operations that declare no scope. `missingCapabilities` names what is outstanding — the smallest set, where a route can be reached more than one way — which is what turns a hidden control into an explicable one:

```ts
const missing = missingCapabilities('createOrder');

if (missing.length > 0) {
  showRequestAccess(missing);  // ['orders.write']
}
```

Neither blocks a request. Call them where you want to skip a round trip you expect to fail; a request issued regardless is still sent, and still authorized by the server.

The module imports nothing, so it is emitted in every mode — with `--hooks` off, and for specifications whose only scopes sit on WebSocket or SSE routes. It also holds no identity of its own: a client that switches principal without calling `setCapabilities` again keeps answering for the previous one.

<Callout type="warn">
The granted set is module state, which is per-process. **This is for the browser.** Calling `setCapabilities` while server-rendering shares one principal's scopes with every request that process is handling concurrently. Server-side authorization is unaffected — it never reads this — so the result is a wrong interface rather than a breach, but it is wrong for everybody at once. Derive what to render from the request's own session there.
</Callout>

If a type in your API is already called `Capability` or `OperationName`, the module is still generated but is not re-exported from the package index — your type keeps the name, and `forge client generate` says so. Import from `./capabilities` directly in that case.

## `websocket.ts` and `sse.ts`

Generated when the specification declares channels. They are `EventEmitter`-style clients with reconnection, heartbeat and connection-state management, and their public surface is unchanged by the cache runtime — `@forge-go/client-core` drives them rather than replacing them.

For a Forge server, channels reach the specification through `forge.WithWebSocketMessages(...)` (or `WithSSEMessages`), which is what puts message schemas in the AsyncAPI document. A channel with no declared messages produces no client.

<Callout type="info">
Forge emits REST operations to `openapi.json` and stream bindings to `asyncapi.json`, so pass both to get both:

```bash
forge client generate --from-spec openapi.json --from-spec asyncapi.json
```

One document on its own still works and still gives you what it describes. Generate from `openapi.json` alone and the `streams` table is empty, which means `{ live: true }` has nothing to subscribe to. See [the CLI reference](/docs/web-client/cli) for the config-file form.
</Callout>

## `package.json`

```json
{
  "dependencies": {
    "@forge-go/client-core": ">=1",
    "eventsource": "^2.0.2",
    "ws": "^8.16.0"
  }
}
```

The `@forge-go/client-core` dependency appears only when `--hooks` is set — the hooks call into it, so it is a regular dependency rather than a peer. Generate without `--hooks` and the package has no runtime dependency at all.

## Auth

An `AuthConfig` field is generated per security scheme your document declares, not per credential type. A scheme keyed `bearerAuth` in `components.securitySchemes` becomes a `BearerAuth` field; a scheme keyed `tenantKey` becomes `TenantKey`. The field name comes straight from the scheme key, so renaming a scheme in your OpenAPI document renames the generated field too.

```go title="src/client.go"
type BasicCredentials struct{ Username, Password string }

type AuthConfig struct {
	BearerAuth  string           // http bearer -> Authorization: Bearer <v>
	TenantKey   string           // apiKey header -> X-Tenant-Key
	SessionAuth string           // apiKey cookie -> session_id
	Login       BasicCredentials // http basic -> Authorization: Basic <v>
	CustomHeaders map[string]string
}
```

An `oauth2` or `openIdConnect` scheme gets one token field of its own, applied the same way a bearer scheme is: `Authorization: Bearer <token>`. Neither specification mandates that transmission, but it is what both flows produce in practice, and the field is named the same way as everything else, from the scheme key.

Every field is applied to the request in its own declared location by a single generated function, `AuthConfig.apply`. A header scheme calls `header.Set`, a cookie scheme calls `header.Add("Cookie", ...)`, a query scheme re-encodes the URL's `RawQuery`, and REST, SSE, WebSocket and WebTransport all route through that one function. Before this, WebSocket carried its own bearer-only check, hand-rolled separately from REST, so a cookie- or query-located scheme never reached the handshake even when REST sent it correctly.

### Breaking change: `BearerToken` and `APIKey` are gone

Earlier generated clients had two fixed fields, `BearerToken` and `APIKey`, regardless of what your document declared. A document with three schemes had nowhere to put the third credential, and a document with one apiKey header scheme still got a client that hardcoded `X-API-Key` no matter what wire name you actually configured.

```go
// before
client.WithAuth(api.AuthConfig{BearerToken: tok, APIKey: key})

// after: one field per declared scheme
client.WithAuth(api.AuthConfig{BearerAuth: tok, TenantKey: key, SessionAuth: sid})
```

Regenerate against your current document and the compiler will point at every call site that needs updating. There is no config flag to keep the old shape.

### `WithCookieJar` and `WithSessionJar`

Two client options are emitted unconditionally, whether or not your document declares a cookie scheme at all:

```go
func WithCookieJar(jar http.CookieJar) ClientOption
func WithSessionJar() ClientOption
```

`WithSessionJar` installs an in-memory `cookiejar.New(nil)`, so a login response's `Set-Cookie` is stored and replayed on every later request from the same client. `WithCookieJar` takes a jar you already have, for when you want to control its lifetime or its storage yourself.

Both exist unconditionally rather than only when a cookie scheme is declared, because the endpoint that actually sets the session cookie, your login route, is frequently absent from `securitySchemes` itself. Gating the option on a detected scheme would withhold it from exactly the case that needs it.

<Callout type="warn">
A client holding a jar carries session state and must not be shared between users. One caller's session cookie rides along on every other caller's requests from that same client. Construct a client per user, or use `WithCookieJar` with a jar you scope yourself, in anything that serves more than one principal, a server process handling concurrent requests, for instance.
</Callout>

### TypeScript: `securitySchemes` and per-operation `security`

The manifest carries the same information as a table, so an `AuthProvider` in `@forge-go/client-core` can look up exactly what an operation needs instead of guessing:

```ts title="src/ops.ts"
export const securitySchemes = {
  bearerAuth: { type: 'http', scheme: 'bearer' },
  tenantKey: { type: 'apiKey', in: 'header', name: 'X-Tenant-Key' },
  sessionAuth: { type: 'apiKey', in: 'cookie', name: 'session_id' },
} as const;

export const ops = {
  listOrders: {
    method: 'GET',
    path: '/orders',
    security: ['bearerAuth', 'tenantKey'],
    // ...
  },
} as const satisfies Record<string, OperationMeta>;
```

`security` on each operation holds keys into `securitySchemes`, not the credentials themselves, so an `AuthProvider.credentials(meta)` implementation can attach a bearer token for one endpoint, an API key header for another, and nothing at all for a public one, from the same table. `securitySchemes` is omitted entirely, not emitted as `{}`, when the document declares no schemes.

### Cross-origin sessions: `credentials`

`RestTransportOptions` in `@forge-go/client-core` takes a `credentials` option, forwarded through to every request the transport builds:

```ts
import { RestTransport } from '@forge-go/client-core';

const transport = new RestTransport({
  client,
  credentials: 'include',
});
```

It is unset by default, which matches a browser's own default `fetch` behaviour: same-origin cookies are already attached without it. Set it to `'include'` when the API lives on a different origin from the page and you want a `sessionAuth`-style cookie to actually reach it. Nothing else in the runtime sets this for you.
