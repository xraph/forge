Documentation that promises unshipped things is worse than none. This page is the full list, so nothing on the other pages has to be read hopefully. It has two kinds of entry. Some are limits we chose and will keep, and each says what to do about it today. The rest are things that aren't built or released yet, and each says what it waits on.

## Limits by design

There are seven. Each one is a decision about how the runtime behaves, and each says what to do about it.

### WebTransport is web only

Dart has no WebTransport outside the browser, and writing a QUIC stack was out of scope. On Android, iOS and the desktops, a stream bound only to a WebTransport route fails with `TransportUnavailable`, naming the endpoint. The subscription manager reports it once and doesn't retry. When the same channel also has a WebSocket or SSE binding, you put the two behind `fallbackConnection` and the manager uses the one that exists.

If your app ships beyond the web, give every WebTransport route a WebSocket sibling. See [Transports by platform](/docs/dart-client/invalidation#transports-by-platform).

### Web storage will protect files, not the browser profile

Offline storage doesn't exist on the web yet (see [Offline storage on the web](#offline-storage-on-the-web) below). The design for when it does is a non-extractable WebCrypto key kept in IndexedDB. Someone who copies or reads the storage files gets nothing. Code running as that browser profile, such as an extension or a script injected into your origin, can still use the key without extracting it.

`passphraseKey` is the answer for apps that need more, at the price of a passphrase every session. See [The web is weaker](/docs/dart-client/offline-and-security#the-web-is-weaker).

### Full sync covers Grove entities only

Two-way sync works for entities stored in Grove's CRDT engine. Every other entity gets the encrypted cache and the outbox, and a conflict on one of them reaches your app as an `OutboxConflict`, never merged behind your back.

There's no change feed for data outside Grove yet. The `SyncSource` seam the runtime routes through is shaped so a source for one can plug in later without changing your app code.

### An uncertain write is reported, not retried

When a write was sent and no response came back, the outbox resends it only if repeating it is safe: a `PUT`, a `DELETE`, or any route that uses Forge's idempotency middleware. A `POST` or `PATCH` without the middleware comes back as `OutboxUncertain`, and your app decides what to do.

Add `forge.WithIdempotency()` to the routes you want retried automatically. See [Uncertain writes and idempotent routes](/docs/dart-client/offline-and-security#uncertain-writes-and-idempotent-routes).

### An optimistic create with an integer id isn't shown until the server confirms it

The runtime gives an optimistic create a temporary string id, and a generated integer field can't decode that. So the typed view keeps showing the value it last decoded, never an error, and the new row appears when the server answers. A list that holds the temporary id behaves the same way.

If the entity's id is a string, there's no limit: the row shows at once. For an integer id, show your own pending row until the answer lands.

### A mutation in flight at sign-out completes for its caller only

When a user signs out, or the account switches, while a mutation is still in flight, the call completes and returns its response to whoever made it. Nothing from that response is written to the cache, and the write's optimistic change doesn't come back. That's how a late answer can never reach the next user's data. The cost is that the signed-out user's screen, if it's still showing, doesn't update from it.

### Runtime edges carried over from the web client

The Dart runtime is a port of the TypeScript one, and the TypeScript test suite is its specification. It keeps three of the web runtime's known edges on purpose, so the two behave the same way:

- Frame ordering is tracked per entity, not per field. When a response carries an entity that a stream frame has already stamped, the response's copy of that record is skipped whole. It is never merged field by field. The other records in the same response are kept.
- Tombstones are capped at 256. Delete an entity, then 256 more, and the first stamp is pushed out. At that point a response that was already in flight before the first delete can put the row back. It's improbable, because it needs 256 deletes while one request is still waiting.
- Multiplexed channels are matched by message name. Where several channels share one socket and the envelope carries no channel field, a message name bound on two channels applies to both.

The web page's first edge, a new container for a refetch that returned identical data, isn't one of them. The Dart store hands back the same object when nothing changed. The web client's [list of runtime edges](/docs/web-client/not-yet-shipped#runtime-edges) is longer than this one, and it's worth reading for the rest.

## Optimistic updates

Two limits of `OptimisticUpdate` you'd otherwise find by surprise.

Keep the function to the record itself and the entities embedded in it directly. Each embedded entity it reads is first worked out with its own pending changes, so a function that walks further, through the customer to all of the customer's orders and their line items, does more work for every record it reaches. With many pending changes that all reach each other, one read costs about the square of their number. At 200 of them that took about 1.2 seconds, and a write to any entity the function read pays it again. Updates that read only their own record and its direct embeds stay linear.

While a change to an embedded entity is pending, the entity shows only the fields its model declares. A field your Dart model doesn't declare isn't lost: the stored record keeps it, and the response is merged into it when the write lands. It just isn't visible until then.

## Not shipped yet

### Offline storage on the web

On the web, the cache lives in memory. `encryptedStorage` throws an `UnsupportedError` there, `webCryptoKeys` throws on every platform, and the code that opens database files in a browser is a stub. So the web has no encrypted cache, no restore on startup and no outbox. A web app gets the in-memory cache that `configureClient` builds when you leave `storage:` out.

Everything else on the [Offline and security](/docs/dart-client/offline-and-security) page applies to Android, iOS, macOS, Linux and Windows. The Linux and Windows keystore code is tested against a fake and not against a real keystore.

### Not on pub.dev

Every package is versioned `1.0.0-dev` with `publish_to: none`, and that's deliberate. You install them from the forge repository with a git dependency, a `ref:` on every entry, as [Installation](/docs/dart-client/installation) shows. `grove_crdt` is the same, from the Grove repository.

### The devtools extension isn't built for you

The built extension is gitignored. A git dependency on `forge_client_devtools` gets you the package and no extension, so DevTools has nothing to load. Depend on it by path from a checkout and run `tool/build_extension.sh` once, as [Devtools](/docs/dart-client/devtools#installing) shows.

### A change stamped late can miss a peer

This is the Grove late-stamp gap. A change stamped earlier than a peer has already pulled can miss that peer. A phone that adds to a set while offline for a day, then reconnects, has its add merged on the server, but a device that already pulled past that stamp is never sent it. It hits counters, sets, lists and text. Last-writer-wins fields mostly escape it, because an older write loses anyway.

The client is correct here. The gap is in the Grove server, and a fix there is what closes it. [Sync](/docs/dart-client/sync#when-to-use-it) has the details.

### Joining a Grove dataset before the runtime starts

A cache hands itself to a sync source only when it starts the source, after that user's storage has opened. Until then, `join` can't tell a signed-in user from nobody and throws. Call `attach(cache)` on the source right after you build the cache, or `await cache.idle` after the first `setPrincipal`. A client from `OfflineClient.open` has already waited, so a `join` after it just works. See [Datasets](/docs/dart-client/sync#datasets).

The core runtime has no hook yet that tells a source who's signed in before it starts, which is why the extra call is needed.

### A queued update after a restart shows nothing

While the app runs, a queued write is drawn from the optimistic update you passed. After a restart nothing remembers your callback, so the outbox derives what to draw from the operation. It can only do that when the operation names exactly one entity key in `invalidates`, and a generated `PATCH`, `PUT` or `DELETE` names the collection (`Order[]`) instead. So after a restart a queued generated update or delete shows no optimistic change. The write is still stored, still replays, and still fails with a typed reason. The screen just shows the old value in the meantime.

`OfflineClient.open` takes no `overlayIntent:`, so there's no way yet to tell it the target. Read `offline.pending` to mark rows that are waiting. See [The outbox](/docs/dart-client/offline-and-security#the-outbox).

### Nothing is in a forge release yet

The latest forge release, v1.12.0, has no Dart generator, no `dart-packages/`, no `forge.WithSync` and no `forge.WithIdempotency`. Until the next release, `go install github.com/xraph/forge/cmd/forge@latest` gives you a CLI without `--language dart`, and a spec generated by a released forge has no `x-forge-sync` or `x-forge-idempotent` marks. The Grove side, `WithCRDTEntity` and the `crdt-dart` package, ships with the Grove release that carries the Dart client.

## What is shipped

For balance, all of this is built and tested in the forge repository, and it's waiting on a release:

- The Dart generator, `forge client generate --language dart`: models, codecs, the ops table, bindings, args classes, `RestClient`, the sealed `ApiError` hierarchy, capabilities, pagination, streaming clients and `--int64=int`
- `forge_client`: the normalized store with structural sharing, tags, the query cache, the REST transport with retries and one refresh per 401 burst, optimistic patches, time-based freshness, streams, and snapshots that load in either runtime
- The Flutter adapter, which needs no state library, and the Riverpod 3 adapter
- `forge_client_offline` on the native platforms: an encrypted database per user with keys in the platform keystore, crypto-shredding on sign-out, restore on startup, and the outbox with typed failures
- Forge's idempotency middleware and `x-forge-idempotent`
- `forge_client_grove` and `grove_crdt`: two-way sync for Grove entities, with `x-forge-sync` emitted by Grove's Forge integration
- The DevTools extension, with outbox and sync panels and the network simulator
