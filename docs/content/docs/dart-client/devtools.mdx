A query that should have refetched and didn't produces no error, no event and no request, so your screen is just wrong until somebody notices. `forge_client_devtools` adds a Forge tab to Flutter DevTools that answers the question for you: why a query did or didn't refetch, what the store holds, and what is sitting in the outbox.

## Installing

Depend on the package by path, from a checkout of the forge repository, under `dev_dependencies`:

```yaml title="pubspec.yaml"
dev_dependencies:
  forge_client_devtools:
    path: ../forge/dart-packages/forge_client_devtools
```

You need Flutter 3.47 or newer, the same as every other package here. Then build the extension once:

```bash
cd ../forge/dart-packages/forge_client_devtools
./tool/build_extension.sh
```

The script runs `fvm flutter pub get`, builds the extension into `extension/devtools/build/`, and runs the validator from `devtools_extensions` over the result. It calls `fvm`, so you need fvm installed, and it uses the Flutter version pinned in `dart-packages/.fvmrc`. Expect the first run to fetch packages your pub cache may not have yet.

Why a path and not a git dependency? The built extension is tens of megabytes, and git ignores it, so a git dependency gives you the package without an extension and DevTools has nothing to load. When you pull a newer forge later, run the script again, because nothing rebuilds it for you.

Run your app in debug or profile mode and open DevTools. The first time, it asks whether you want to enable the `forge_client_devtools` extension, and when you say yes the Forge tab appears. DevTools remembers your answer in `devtools_options.yaml` at the root of your project.

In debug and profile builds, `configureClient` attaches the devtools to the cache it creates, so there's nothing for you to call. If you built a cache with the `QueryCache` constructor, you need `registerForgeServiceExtensions(cache)` from `package:forge_client/devtools.dart`, and until you add it the tab says `forge_client` isn't running.

## Release builds pay nothing

`kForgeDevtools` is a constant. It's false in every release build, because Flutter defines `dart.vm.product` for them, and the compiler then drops everything it guards: the `ext.forge.*` VM service extensions, the recorder and the network simulator. To leave the devtools out of a debug build too, pass `--dart-define=forge.devtools=false`. The extension itself is a dev dependency, so none of it ships in your app.

That covers `configureClient`, `registerForgeServiceExtensions` and `OfflineClient.open`. If you call the rest of `package:forge_client/devtools.dart` yourself (`attach`, `Devtools`, `ControlledTransport`), those calls aren't gated, so wrap them in `kForgeDevtools`.

Reading doesn't disturb the cache either, since looking at an entity writes no store row and doesn't move the query in the LRU order. The buttons in the panels are different, because refetch, invalidate, drop and evict do what they say.

## What the tab shows

Eight panels sit under the cache counts (success, error, fetching, stale, unmounted, records):

- Queries lists every query the cache remembers, with its status, mounts, and tag and dependency counts. Open one for what it provides, its tags, its dependencies and its last error. You can refetch it, invalidate it, mark it stale or drop it, and filter by key.
- Entities pages through the store a hundred rows at a time, filtered by type or by part of a key. Open one for its fields as the store holds them, the same record with pending optimistic writes folded in, what it references and which queries reached it. You can evict it.
- Tags shows the tag graph: which queries carry each tag and which of them are mounted. You can invalidate a tag from here. Below the graph are the two questions about a query, covered next.
- Events is the event log, live, filtered by kind. An entry that another entry caused says which.
- Frames lists captured stream frames with their payloads. Capture is off until you switch it on, and the ring has a fixed capacity.
- Requests has one line per request: the operation, attempts against the limit, duration, each retry with its status and delay, and the time spent waiting on an auth refresh. It keeps no headers and no bodies.
- Outbox and Sync are new in Dart, and get their own section below.

### Why did this query not refetch?

Copy a query key from the Queries panel, type it into the Tags panel and press Explain. You'll get one of five outcomes: `missed`, `stale-while-unmounted`, `placed`, `refetched` or `not-tracked`. These are the same five the web inspector reports, and [the web page](/docs/web-client/devtools#why-did-this-query-not-refetch) explains what each one means. `stale-while-unmounted` is the one to learn. It looks like a bug, and it's really the cache declining to fetch something nobody is looking at.

For `missed`, the report lists the near misses. An invalidation of `Order:9` against a query that carries only `Order[]` is the classic one, and the hint says what to change. When some of the operation's `invalidates` templates resolved to nothing, a `{res.x}` against a response without `x`, the report says so first. That is the most common reason an invalidation silently didn't happen.

The same panel answers why a query did refetch, from the log: the mutation or stream frame that caused it. A second box previews what an operation would invalidate without running it, and which mounted queries each tag reaches. It needs the generated operations table, which `OfflineClient.open` passes for you and which you hand over yourself with `configureClient`. The `outbox` argument is for an app that built an `OfflineClient` by hand and wants Replay and Discard to work, so leave it out otherwise.

```dart
import 'package:forge_client/devtools.dart';
import 'package:forge_client/forge_client.dart';
import 'package:orders_forge_client/orders_forge_client.dart' show operations;

void showInDevtools(QueryCache cache, OutboxInspector outbox) {
  registerForgeServiceExtensions(cache, operations: operations, outbox: outbox);
}
```

On a cache that's already attached, this fills in what's still empty and never overwrites a slot that's full. The first registration wins.

## The network simulator

The quickest way for you to watch the outbox work is to switch the network off without touching the device. Above the panels sits a rail with three modes (Online, Slow and Offline), an extra delay of 250 ms, 1 s or 3 s, and a Fail next button. Pick a status beside it first, from 408, 429, 500, 503 and 409, so you can walk the retry, backoff and conflict paths by hand; it's 500 until you change it. Fail next fails one request and then disarms itself, because a failure that stayed armed would look exactly like the bug you were hunting. Revalidation toggles that the app registered, such as focus and reconnect, show up in the rail as well.

The simulator sits outside the retry loop. Offline fails the whole operation, not one attempt that then retries, and added delay holds the operation back once, not once per attempt.

The rail only has network controls when the app wired a simulator, and the wiring depends on how you built the client:

- `configureClient` wraps a `RestTransport` in the simulator for you, in debug and profile builds. Any other transport is used as it is, and the rail stays empty.
- `OfflineClient.open` doesn't go through `configureClient`, so you ask with `devtools: true`:

```dart
import 'package:forge_client/forge_client.dart';
import 'package:forge_client_flutter/forge_client_flutter.dart';
import 'package:forge_client_offline/forge_client_offline.dart';
import 'package:orders_forge_client/orders_forge_client.dart' show entities, operations;

Future<OfflineClient> signInWithDevtools(StorageAdapter storage, String userId) {
  return OfflineClient.open(
    transport: RestTransport(baseUrl: Uri.parse('https://api.example.com')),
    entities: entities,
    operations: operations,
    storage: storage,
    principal: userId,
    connectivity: ConnectivityPlusSignal(),
    devtools: true,
  );
}
```

That puts the simulator directly on the `RestTransport`, beneath the outbox, so a write you make while the panel says Offline is queued exactly as it would be on a lost connection, and a replay feels the simulated network. It also merges the simulator into your connectivity signal and registers the client as the panel's outbox inspector. If you build the client by hand, the README in `dart-packages/forge_client` shows the same steps in order. The simulator has to go beneath the outbox. Outside it, an offline write would fail before the outbox could queue it.

## Outbox and Sync

The Outbox panel lists the stored writes in the order they were queued, each with its id, its operation, its state and, for a failed one, why: `conflict 409`, `uncertain: <reason>` or `unreadable`. It never shows a write's arguments or its idempotency key. A cache with no storage session has no stored queue, so the panel lists only the writes it has seen since DevTools attached, and says so.

Every queued or failed write has Replay and Discard buttons. They're switched off until the app has passed an `OutboxInspector`, which `OfflineClient.open(devtools: true)` does. Replay sends the write now, out of its turn, ignoring both its backoff and the connectivity flag. Out of its turn means a replay of an update can reach the server ahead of the queued create it depends on, and fail with a 404 where the normal order would have worked. If the write still can't reach the server, it stays queued, the client's `replay` throws `OutboxOffline`, and the panel shows you the error. Discard drops the write and rolls back its optimistic change. It refuses a write that is on the wire right now.

The Sync panel shows each sync source and what it says about itself. The Grove source reports its protocol, its node id, its hybrid logical clock and its peers. Below the sources comes the status of each entity: its `SyncStatus`, how many changes are pending and the last error. A source that doesn't describe itself says so. An app with no sync sources sees a note that plain REST entities use the outbox instead.

## When an account changes

Nothing carries over from one account to the next. When the app changes principal, `forge_client` drops its event log, frame ring, request log and the outbox and sync mirrors, and cancels any armed Fail next. It keeps one marker that says the identity changed, with no ids or payloads in it, and the extension clears every panel when it arrives. During the switch the panels say "switching account" instead of showing an empty cache.

Every action the extension sends carries the session it last saw. If the account changed since, the app refuses the action and the panel shows you the refusal, so a click aimed at the previous user never lands on the new one. The Frames panel is the one place that shows payloads, and only while capture is on.

## When the tab doesn't connect

If the tab says `forge_client` isn't running in the connected app, check four things. The app might be a release build. It might have been built with `--dart-define=forge.devtools=false`. It might not depend on `forge_client`. Or it built its cache with the `QueryCache` constructor and never called `registerForgeServiceExtensions`. The tab connects by itself once the extensions appear, after a hot restart for example.

The other message to know is this one:

```text
This DevTools extension and the app's forge_client versions don't match; upgrade both.
```

The extension and the `forge_client` in your app both speak a numbered protocol, and they have to be the same number. The current protocol is 2. When the app answers with another number, the extension asks it nothing more, because it would read the answers with the wrong shapes, and the message adds the two numbers. You won't find a Retry button, since asking the same app again gets the same answer; the extension tries again by itself after a hot restart or a new isolate.

Most often it's two different checkouts. Your app resolved `forge_client` at one commit and the extension was built from another. Point both at the same forge commit, run `./tool/build_extension.sh` again, and restart the app.

<Callout type="info">
The rail's mode belongs to the running app, and a restart puts it back online. To see writes survive a restart, queue a few while the rail says Offline and watch them appear in the Outbox panel. Then switch the device itself to airplane mode, kill the app and start it again. After the restart they are still listed. The client reads the device's connectivity from the signal you passed, so it knows it is offline, sends nothing and counts nothing against the writes, however long you wait. Turn airplane mode off and they replay, writes to one entity type in the order you made them.

The rail's Offline mode holds writes the same way while the app runs. The limit of 8 retryable failures in a row applies only when the app thinks it is online and requests still fail: a Wi-Fi network with no internet, a server answering 503, or a client built without a `connectivity:` signal. The delay doubles from a second, so the limit is reached in about two minutes. After that a write shows as `OutboxUncertain` and stops replaying on its own, and Replay in the panel resends it.
</Callout>
