Forge generates a Dart client from the same API specification that produces the [web client](/docs/web-client). You get typed models, a typed REST client and typed errors. Add `--hooks` and you also get streaming clients and a runtime that caches **entities**, the way the TypeScript one does: `GET /orders/7` and `GET /orders` both point at one `Order:7`, and a `PATCH` that changes its total updates the detail screen, the row in the list and the badge in your app bar from the response to the write.

The Dart runtime also does two things the TypeScript one doesn't. Add `forge_client_offline` and, on iOS, Android and the desktop, the cache is persisted on the device and encrypted at rest, so a write you make offline survives a restart and replays when the network comes back. Add `forge_client_grove` and entities stored in Grove sync in both directions. The server can still reject a change, and [Sync](/docs/dart-client/sync) covers what happens then.

You decide what counts as an entity, and what a write makes stale, in Go before either client is generated, so the Dart and TypeScript clients follow the same rules. These pages cover the Dart side. The server side is shared, so for the details of declaring it you'll want the web client docs, under [entities](/docs/web-client/entities) and [invalidation](/docs/web-client/invalidation).

## What you write to get it

On the server, nothing new. This route is enough:

```go
r.GET("/orders/:id", getOrder,
    forge.WithOperationID("getOrder"),
    forge.WithResponseSchema(200, "Order", &Order{}),
)
```

The generator turns it into a row of data:

```dart title="lib/src/ops.dart"
const opGetOrder = OperationMeta(
  id: 'op_get_order',
  method: 'GET',
  path: '/orders/{id}',
  entity: 'Order',
  rootType: 'Order',
  provides: ['Order:{id}'],
  responseCodec: orderCodec,
);
```

and a one-line binding your widgets call:

```dart
class OrderTotal extends StatelessWidget {
  const OrderTotal({super.key, required this.id});

  final String id;

  @override
  Widget build(BuildContext context) {
    return ForgeQueryBuilder(
      query: getOrder(GetOrderArgs(id: id)),
      builder: (context, state) => switch (state) {
        QuerySuccess(:final data) => Text('${data.total}'),
        QueryFailure() => const Text('Could not load the order'),
        QueryIdle() || QueryLoading() => const CircularProgressIndicator(),
      },
    );
  }
}
```

`QueryState` is sealed, so the compiler checks that `switch` for you, and if you forget the failure case the app doesn't build.

<Callout type="info">
Everything on these pages is built and tested in the forge repository, and it's waiting on a release. The Grove half lives in the grove repository. The packages are versioned `1.0.0-dev` and you install them from the forge repository with a git dependency. See [Installation](/docs/dart-client/installation).
</Callout>

If you run Flutter on the web, the cache lives in memory for now, because encrypted offline storage there isn't built yet. [Not yet shipped](/docs/dart-client/not-yet-shipped) lists what else you can't have today.

## How the pieces fit

```
Go route + options
        │
        ├─ OpenAPI  (operations, entity identity, cache tags, x-forge-sync, x-forge-idempotent)
        └─ AsyncAPI (channels, stream bindings)
                │
                ▼
   forge client generate --language dart --hooks
                │
                ▼
   models/  codecs/  ops.dart  bindings/  rest.dart  errors.dart
                │
                ▼
         forge_client                     entity store, tags, transports, snapshot
                │
      ┌─────────┼───────────────────┐
      ▼         ▼                   ▼
 forge_client_flutter    forge_client_offline    forge_client_grove
      │
      ▼
 forge_client_riverpod
```

Bindings are one line each and call into `forge_client`, so a runtime fix ships as a new version of `forge_client`.
