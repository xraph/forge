You need Flutter 3.47 or newer, which ships Dart 3.13. Every package declares `sdk: ^3.13.0`, so an older toolchain fails at `pub get` with a version error.

## Add the packages

Five of the packages are on pub.dev, so you add them like any other dependency. Add the runtime and one adapter:

<Tabs items={["Flutter adapter", "Riverpod adapter"]}>
<Tab value="Flutter adapter">
```yaml title="pubspec.yaml"
dependencies:
  forge_client: ^1.12.2
  forge_client_flutter: ^1.12.2
```
</Tab>
<Tab value="Riverpod adapter">
```yaml title="pubspec.yaml"
dependencies:
  flutter_riverpod: ^3.4.3
  forge_client: ^1.12.2
  forge_client_riverpod: ^1.12.2
```
</Tab>
</Tabs>

The packages are versioned in lockstep with forge, so 1.12.2 of one goes with 1.12.2 of the others, and each package asks for its siblings at `^1.12.2`. Keep them on one version. When you upgrade, move them all together.

You add `forge_client_offline` the same way, and your app then needs a `hooks` block in its root `pubspec.yaml` that selects the encrypted SQLite build. [Offline and security](/docs/dart-client/offline-and-security) shows it. The package is optional.

`forge_client_devtools` goes under `dev_dependencies`:

```yaml title="pubspec.yaml"
dev_dependencies:
  forge_client_devtools: ^1.12.2
```

The published package carries the built extension, so there's nothing to build. The [Devtools](/docs/dart-client/devtools) page walks through turning it on.

`forge_client_grove` is the one package that isn't on pub.dev. It depends on `grove_crdt`, the Dart port of Grove's `crdt-js`, and `grove_crdt` hasn't been published, which means pub.dev wouldn't take the upload. You install it from the forge repository with a git dependency instead, and the entry needs one extra override. [Sync](/docs/dart-client/sync#on-the-device) has both, along with the `grove_crdt` pin. You can skip it unless you sync Grove entities.

## The packages

| Package | What it is |
|---|---|
| `forge_client` | Entity store, normalizer, tags, query cache, REST transport, streams and snapshots. It has no Flutter dependency, so it also runs in a CLI or a test. |
| `forge_client_flutter` | `ForgeScope`, `ForgeQueryBuilder`, `ForgeMutationBuilder` and the rest of the widget layer. Needs no state management library. |
| `forge_client_riverpod` | `queryProvider` and `mutationProvider`, for apps already on Riverpod 3. |
| `forge_client_offline` | The encrypted on-device cache and the durable outbox. Native platforms only for now. |
| `forge_client_grove` | Two-way sync for entities stored in Grove, over `grove_crdt`. |
| `forge_client_devtools` | A Flutter DevTools extension. Development only. |

You pick one adapter style per app. `forge_client_riverpod` is built on `forge_client_flutter` and installs focus and reconnect revalidation through the same installer, so both styles refetch stale queries the same way. Generated clients import neither adapter, so if you change your mind later you don't regenerate anything.

`forge_client_offline` and `forge_client_grove` are separate packages, so an app that only talks REST doesn't link SQLite, a keystore plugin or CRDT code.

## The generated client

The generator ships with the Forge CLI, so you don't need any of the packages above to run it.

The generator needs forge v1.12.2 or later, because earlier releases have no `--language dart`. Install the CLI at that version:

```bash
go install github.com/xraph/forge/cmd/forge@v1.12.2
```

`@latest` works too. Then generate:

```bash
forge client generate --from-spec ./openapi.json --language dart --output ../orders_forge_client --package orders_forge_client --base-url "https://api.example.com" --hooks
```

`--package` has to be a valid Dart package name: lowercase letters, digits and underscores, starting with a letter or an underscore, and not a Dart reserved word. Then depend on the output by path:

```yaml title="pubspec.yaml"
dependencies:
  forge_client: ^1.12.2
  orders_forge_client:
    path: ../orders_forge_client
```

A client generated with `--hooks` depends on `forge_client` from pub.dev, with the constraint `^1.0.0-dev`. That accepts 1.12.2, so your direct entry and the client land on one copy of the runtime and you have nothing to override.

The rest of the flags, and `check`, `diff` and `watch` for keeping a committed client honest in CI, work the same way they do for TypeScript. See [the CLI reference](/docs/web-client/cli).

## Generating without the runtime

Leave out `--hooks` and you get models, codecs, a typed `RestClient`, typed errors and pagination helpers. That package depends on `package:http` and nothing from forge:

```dart
import 'package:orders_forge_client/orders_forge_client.dart';

Future<void> main() async {
  final rest = RestClient(baseUrl: Uri.parse('https://api.example.com'));
  final order = await rest.getOrder(id: '7');
  print(order.status);
}
```

What you don't get is the normalized cache, the tags, the ops table, the bindings and the streaming clients. Those need `--hooks` and `forge_client`. Without `--hooks` the generator skips the streaming clients, and it warns you when your spec has streaming endpoints.

## Wiring the runtime

Generated bindings are top-level values that aren't tied to a cache, so you point the runtime at your API once, before `runApp`:

```dart title="lib/main.dart"
import 'package:flutter/material.dart';
import 'package:forge_client/forge_client.dart';
import 'package:forge_client_flutter/forge_client_flutter.dart';
import 'package:orders_forge_client/orders_forge_client.dart';

void main() {
  final cache = configureClient(
    transport: RestTransport(baseUrl: Uri.parse('https://api.example.com')),
    entities: entities,
    commitScheduler: frameCommitScheduler(),
  );
  runApp(ForgeScope(client: cache, child: const MaterialApp(home: Text('Orders'))));
}
```

`configureClient` creates the `QueryCache` and makes it the global one. `frameCommitScheduler()` commits store updates once per frame, and you have to pass it here because a cache takes its scheduler when it's built. The `ForgeScope` does the rest, and while it's mounted it refetches stale queries when the app comes back to the foreground and again when the device reconnects. If you use Riverpod, the installed client provider does that job and you don't need a scope at all.

A `ForgeScope` is optional. If you skip it, install those two behaviours yourself, once:

```dart
void main() {
  final cache = configureClient(
    transport: RestTransport(baseUrl: Uri.parse('https://api.example.com')),
    entities: entities,
    commitScheduler: frameCommitScheduler(),
  );
  installFlutterSeams(cache);
  runApp(const MaterialApp(home: Text('Orders')));
}
```

`installFlutterSeams` returns its uninstaller, and you can ignore it for a client that lives as long as the app. Put a scope above a subtree when a global is the wrong answer, which happens in a widget test that must not leak into the next one and in an app that talks to two backends. A widget finds its cache by explicit argument first, then the nearest `ForgeScope`, then the global. If you give it none of the three, `getClient()` throws a `StateError` that says so, so you never end up with a cache nothing else can see.

### Credentials

`RestTransport` asks an `AuthProvider` for headers on every request, and calls `refresh()` once when a burst of requests comes back 401, no matter how many were in flight:

```dart
final class SessionAuth implements AuthProvider {
  SessionAuth(this._renew);

  final Future<String> Function() _renew;
  String? _token;

  @override
  Map<String, String>? credentials(OperationMeta meta) {
    final token = _token;
    if (meta.security.isEmpty || token == null) return null;
    return {'Authorization': 'Bearer $token'};
  }

  @override
  Future<void> refresh() async {
    _token = await _renew();
  }
}

RestTransport authenticatedTransport(Future<String> Function() renew) => RestTransport(
      baseUrl: Uri.parse('https://api.example.com'),
      auth: SessionAuth(renew),
    );
```

`meta.security` lists the security schemes the operation declares, so a public endpoint gets no header at all. This sample starts with no token, so the first request to a secured route goes out without a header, comes back 401, and only then calls `refresh()`. Seed `_token` if you'd rather skip that round trip.

<Callout type="warn">
The runtime retries `GET`, `HEAD`, `PUT` and `DELETE` by default, because repeating them is safe. A retry happens when the request failed with no status, or with a 408, a 429 or a 5xx. It never retries a `POST` or a `PATCH` on its own, apart from the single resend after a 401 once the credential has been refreshed, because the server rejected that request before acting on it. The outbox in `forge_client_offline` has its own rules for replaying those; see [Offline and security](/docs/dart-client/offline-and-security#uncertain-writes-and-idempotent-routes).
</Callout>
