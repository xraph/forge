## 2. How the runtime knows an object's TYPE

**The typename comes from the generated manifest and is propagated
structurally; it is never derived from the shape of the JSON.**

Concretely, three rules and no fourth:

1. `normalize(value, entities, rootType)` — `rootType` is the operation's
   declared entity typename, `ops.orderGet.entity`, which
   `opsmanifest.go:writeOps` already emits and which was resolved in Go against
   the real response schema.
2. An array does not change the typename: `[]Order` is a list of `Order`, so
   the hint passes through element-wise.
3. Descending into an object's field consults `entities[Type].fields[field]`,
   a JSON-property→typename map (element typename for arrays).

An object is an entity when, and only when, the table names its type **and** it
carries that type's `idField` with a usable value (non-empty string, finite
number, or bigint). `{id: 7, total: 99}` with no `rootType`, or under a type the
table does not name, is data — 12 assertions in `__tests__/normalize.test.ts`
pin that, including the "has an id property" case explicitly.

Rule 3 is the gap. **See section 7: the generator does not emit `fields`.**

## 3. The cycle decision

`Order → Customer → Orders[] → Order` is what an ORM with eager loading
produces. There is a second source I did not anticipate and the property test
found: **merging creates cycles the response never had.** `{id: 1, related:
[{id: 1}]}` is a finite tree, but there is exactly one `Order:1`, so the merged
record references itself. That case is pinned in
`__tests__/store.test.ts` ("handles a cycle that merging introduces").

**Normalization** terminates by registering a node's skeleton in a visited map
*before* walking its children, so the second visit returns the placeholder the
first is still filling.

**Denormalization rebuilds the cycle as a cyclic object graph** rather than
stopping at the back-edge and returning the reference. Reasons, in order of
weight:

- Returning the ref pushes a cache internal into application data. Every
  component that walks an association would have to type-guard `{__ref}` before
  reading a field, which is exactly the indirection the skeleton exists to
  hide, re-exposed at the worst possible place.
- Where the cut lands is arbitrary and traversal-order dependent, so the same
  data would present differently depending on which query happened to mount
  first. That is unfalsifiable from the outside.
- The cost of the alternative is bounded and known: memoize the entity's output
  object before filling its fields, so the back-edge resolves to the same
  identity. It is the contract `structuredClone` already gives for cyclic input,
  so it is unsurprising to a reader.
- The property that makes it safe: **the store stays flat and acyclic per
  record.** Only the graph *between* records closes, so SSR serialization of the
  store and skeletons is unaffected. A test asserts every record `JSON.stringify`s.

The denormalized result of a genuinely cyclic graph is not JSON-serializable.
That is a property of the data, not of this design.

## 4. Structural sharing

Three mechanisms, all in `src/store.ts`:

1. **Nothing unchanged is rewritten.** `normalize` returns the input subtree by
   reference when no entity occurs beneath it, and marks only rebuilt containers
   in a module-level `WeakSet`. Rehydrating an unmarked node is the identity
   function — no walk, no copy, no memo entry. This is most of a real response.
2. **Rehydration is memoized per subtree**, keyed by entity key for records and
   by node identity (`WeakMap`) for skeleton containers.
3. **Invalidation walks the reverse-dependency index** (`Map<EntityKey,
   Set<Memo>>`) from the key written, transitively through memos that materialize
   an entity. Work is proportional to what changed.

A one-hop version check — "recompute if my own record or my direct deps moved" —
is wrong, and the wrongness is quiet: `Order:7 → Customer:c-3 → Order:9`, write
`Order:9`, and `Order:7`'s direct dep `Customer:c-3` has not moved, so a stale
object survives. Pinned by "propagates a change two hops away".

A fourth thing that matters as much: **a write whose data is deep-equal to what
is stored is not a write.** The version does not move, the record object is
kept, and no identity downstream changes. It has to be deep rather than shallow
because a refetch of byte-identical JSON returns entirely fresh objects; a
shallow check would report a change on every poll and re-render an application
whose data did not move. References compare by key for the same reason — two
normalization passes mint two `Ref` objects for one entity.

The one case that does not memoize is a cycle closing through **plain objects**
rather than through an entity: those memos carry incomplete dependency sets
(the back-edge returned before its own deps were known), so every node memo from
that read is discarded and the subtree is rebuilt per read. Entity-mediated
cycles are unaffected, because a reference records its key before anything else.
JSON cannot express a plain-object cycle; only a hand-built graph can.

`clear()` replaces the node `WeakMap` rather than trying to clear it. A
surviving memo would keep serving the previous principal's data to a skeleton
the caller still holds — the exact defect partitioning exists to prevent,
reintroduced by a cache. Tested.

## 5. Design notes worth knowing before the next chunk

- **References are recognised by object identity, not by a `__ref` property.**
  A `WeakSet` populated only by `makeRef`. An in-band marker would make the
  runtime lossy for any response that legitimately contains that shape — lifted
  on the way in, resolved to nothing on the way out. There is a test that
  round-trips `{note: {__ref: 'Order:999'}}`. The `__ref` property still exists
  so a skeleton serializes; SSR will need a revive pass to re-register them.
- **A reference to a record the store does not hold rehydrates to `undefined`**,
  and the dependency is still recorded, so the query recomputes when the record
  arrives. Tested both ways.
- **Merge, never replace.** A newer server sends fields this client's types do
  not name, and a narrower projection of the same record must not delete them.

## 6. The fast-check properties

`__tests__/roundtrip.property.test.ts`. Generators produce arrays of arrays,
nullable entity references (present-and-null, distinct from absent), entities at
varying depth, the same entity twice, non-entity objects at arbitrary depth, and
four response shapes (bare entity / list / envelope / no declared type at all).
Ids come from a small pool on purpose — a generator drawing unique ids never
produces the collision that exercises merging.

| Property | Statement |
|---|---|
| round trip | `denormalize(normalize(x))` deep-equals `x`, modulo entity merging |
| skeleton completeness | every reported dep and every reference in the skeleton resolves to a record |
| purity | `normalize` does not mutate the response |
| write idempotence | writing the same response twice bumps no version |
| referential identity | two reads with no write between are `Object.is` at *every* nested subtree |
| targeted recompute | after a write, no subtree that kept its identity contains the change |
| no spurious recompute | a write to an entity the skeleton does not depend on returns the identical value |

The round-trip oracle is not the raw input: when one entity occurs twice with
different fields, the store holds their union and both positions rehydrate to it.
Asserting against the input would be asserting that normalization did not happen.
The oracle recomputes that union independently, from the input alone.

The oracle is also what surfaced the merge-induced cycle — it stack-overflowed
before the runtime did anything wrong.

Soaked at 20× the committed run counts (8000 runs on the main properties) with
no failures. Committed at 200–400 runs each so the suite stays under half a
second. 42 tests total, all passing.

## 7. What the generator would need to emit and does not

**`entities[Type].fields`: a JSON-property → typename map.**

`opsmanifest.go:writeEntities` emits `{ Order: { idField: 'id' } }` and
`internal/client.EntityRef` (`ir.go:669`) has only `Type` and `IDField`. There
is nowhere for the links to live.

The consequence, precisely: **only entities of the operation's declared root
type are extracted.** A `Customer` nested inside an `Order` stays inline in the
skeleton. It is under-normalization, not incorrectness — the nested record is
simply not shared, so a write to it does not update that view and the view
refetches. It costs a round trip.

I did not invent a heuristic to close it. Shape-based detection is the
`dataIdFromObject` guess the design explicitly rejects, and on a type carrying
both `ID` and `TenantID` it keys two tenants' records to one cache entry.

The runtime is already built for the field map: `EntityMeta.fields` is optional
and the walk consults it, so emitting it is purely a Go-side change with no
runtime change. It needs:

1. `EntityRef` (or a new IR type) to carry `Fields map[string]string`,
   populated from the response schema the introspector already walks to infer
   identity — it visits every nested named type on the way.
2. `writeEntities` to render it, sorted, for determinism.
3. An entry for **non-entity wrapper types too**. The table already supports
   this with no new concept: a type whose `idField` no payload carries is never
   an entity but still routes typenames to its children, which is how `{data:
   ...}` and `{items: [...], total: n}` envelopes work. `Envelope` in
   `__tests__/schema.ts` demonstrates it. Without wrapper entries, an envelope
   blocks the hint at the root and *nothing* in the response normalizes — worth
   emphasising, because most Forge list endpoints are enveloped.

Also worth deciding at that point: whether the manifest should name the response
type of *every* operation, not only entity-returning ones, so an enveloped
response has a root hint at all.

## 10. Concerns

1. **The root `.gitignore` excludes any directory named `test` or `tests`**
   (lines 12–13, aimed at Go test binaries). It silently swallowed the entire
   test directory — `git add` reported success and staged nothing. Tests are in
   `__tests__/` as a workaround. The rules should probably be `*_test` /
   `*.test` only; any future JS package in this repo will hit the same trap, and
   the failure mode is committing a package with no tests and not noticing.
2. **There is no workspace root.** No root `package.json` and no
   `pnpm-workspace.yaml`, yet `astro-plugin` and `nextjs-plugin` declare
   `"@forge-go/bridge-client": "workspace:*"`. `packages/client-core` installs
   and tests standalone, and following the siblings it ships no lockfile. If CI
   is meant to build these, something has to declare the workspace.
3. **No sibling package has a test runner**, so "same test runner as its
   siblings" had no answer. I picked `vitest` (ESM-native, matches `"type":
   "module"`) plus `fast-check`, which the design names directly. If the repo
   later standardises elsewhere, this is one file to change.
4. **A refetch returning identical data still produces a new skeleton**, so the
   root identity moves even though no record did. Holding the previous skeleton
   when no record changed belongs to the query engine, which owns the query key.
   Flagged so it is not mistaken for a store defect.
5. **SSR revival is unimplemented.** A deserialized skeleton is not recognised
   as one, because references are identified by object identity. The `__ref`
   property is there for it; the revive pass is not.
6. **Not yet built, by design:** GC of unreferenced entities and the LRU cap,
   optimistic overlays, principal partitioning beyond `clear()`, the tag graph,
   transports, and the React adapter.
