## 1. The questions, and how the API answers them

The package is an inspection API first. The overlay is a view over it and
nothing more, so a Vue or Angular application can build its own panel, or none
at all and call `explain()` from the console.

### "Why did this query NOT refetch?" — the one that matters

A missed invalidation is silent: no event, no error, no request. Everything else
in this package exists to make this one answerable.

```ts
forge.whyNotRefetched('GET /orders');
```

```
outcome:     missed
reason:      `GET /orders` did not refetch because none of the 1 tag(s)
             mutation POST /orders raised are tags it carries. The two sets
             are disjoint.
invalidated: Order:9
carried:     Customer:c1, Order:1, Order:2, Order[]
matched:     (none)
nearest:     Order:9 vs Order[]   (instance-vs-collection)
suggestion:  the mutation invalidated the instance `Order:9` but this query
             provides the collection `Order[]`, and the two never intersect. A
             query only carries `Order:9` once a response has actually put that
             entity in its result — which a create never has. Add `Order[]` to
             the operation's Invalidates.
```

Three design decisions carry that output.

**The report is evidence, not a verdict.** Both tag sets, their intersection,
the mount count and the settled flag are all in the report. A developer who
disagrees with the conclusion can still read the working. That is the difference
between this and a tool that says "cache miss" and leaves.

**Five outcomes, because they are five different bugs.** Conflating any two of
them costs an afternoon:

| outcome | meaning |
|---|---|
| `missed` | the tag sets are disjoint. A declaration is wrong; read `nearest`. |
| `stale-while-unmounted` | they *did* intersect, but nothing has the query mounted, so no request was made. **Correct behaviour** — refetching data nobody is looking at is how a smart cache becomes a bandwidth complaint — and it is the single commonest false report of a broken cache. Reported as its own outcome, with no suggestions attached, because there is nothing to fix. |
| `placed` | a placement callback answered. If the screen is wrong, the callback is wrong, and no amount of tag work will help. |
| `refetched` | it did refetch; the problem is downstream. |
| `not-tracked` | the key is not one the cache holds. A key includes its arguments, so a hand-assembled one usually is not the real one. |

**Near misses are named, not merely shown.** `nearMisses` classifies each pair
into `instance-vs-collection`, `collection-vs-instance`, `different-instance`,
`case`, `scoped`, ranks them by how suspicious the relation is, caps the output
at eight, and attaches a hint written as an instruction — *which declaration to
change* — rather than as an observation. "These tags differ" is something the
developer can already see.

And the sixth cause, reported separately because it is invisible by
construction: a tag template that **resolved to nothing and was skipped**.
`Order:{res.id}` against a response with no `id` invalidates nothing, warns once
per template in a console nobody is reading, and produces exactly the same
symptom as a wrong tag. `cause.unresolved` is where it surfaces, and it is
promoted to the first suggestion when present.

### "Why did this query refetch?"

`whyRefetched(key)` → `{query, at, reason, cause, matched, summary}` where
`reason` is `invalidation | mount | manual` and `cause` is the mutation or
frame batch responsible.

> `GET /orders` refetched because mutation `PATCH /orders/{id}` invalidated
> `Order:1, Order[]`, of which it carries `Order:1, Order[]`.

The attribution is made **at record time**, not reconstructed on demand, because
the ordering that makes it sound only exists as the events arrive: `mutate`
reports itself and then, synchronously, reaches every hit query before control
returns. The recorder holds a "current cause" that a mutation or frame batch
sets, that invalidations and placements consume, and that any *fetching
transition* clears. A bare `cache.invalidate(tags)` therefore attributes to
nothing, which is the honest answer rather than the previous mutation's.

That last rule was subtler than it looked. Clearing on any `query` event was the
first attempt and broke the stream path outright: `applyFrames` reports itself,
then calls `notifyChanged`, which notifies every query a patch moved *before* a
single tag is applied — so every stream invalidation ended up attributed to
nothing. Clearing only on a `fetching` transition is what makes both paths
correct, and there is a test for each.

`explain(key)` picks the question for you: the refetch story if it refetched,
the miss story otherwise.

### "What is in the cache for `Order:7`, and what version?"

`entity(key)` → `{key, type, id, version, frameAt, fields, refs, dependents}`.
`version` bumps only when the data actually moved; `frameAt` is non-zero when a
stream frame wrote it; references appear in `fields` as `{__ref: 'Customer:c1'}`
because that is what the cache genuinely holds, and `refs` lists them.

### "Which queries depend on this entity?"

`dependents(key)`, and the `dependents` field of `entity`. It reaches through
nested references — a list rendering `order.customer.name` depends on
`Customer:c1` having declared nothing of the sort — and it is computed by
scanning the registry rather than by a maintained index, because the registry is
bounded by the cache's LRU cap and an index kept for a panel nobody has open is
a cost the runtime should not pay. It is deliberately *not* filled in for the
`entities()` list: that would be one registry scan per record, and a store of
fifty thousand records is an ordinary one.

### "Which sockets are open, for which channels, with what ref count?"

`sockets()` → endpoint, connected, refs, opens, attempt, reconnecting, closing,
and per-channel handler counts. Ten components on one live query are one socket
with `refs: 10`; `opens > 1` means it dropped and came back, which means frames
were missed. The manager is found through `cache.live` — a `StreamBinder` holds
one — so there is nothing to configure, with an explicit `{manager}` option for
an application that built one without a binder.

### And, without running anything

`wouldInvalidate(meta, args, response)` → `{templates, tags, unresolved, hits,
missed}`. The tags a mutation raises depend on its response, so "is `Order[]`
covered?" normally requires placing a real order to find out. This resolves the
templates through the same `resolveTags` the `Invalidator` uses and reads the
tag index. `missed` — tags no mounted query carries — is the interesting column.
Asking what a mutation would do must not be answered by doing it, and there is a
test asserting the transport call count is unchanged.

## 2. Core hooks added, and what they cost when unset

Four changes, all optional, all measured against the built output.

### `QueryCache.observer`, and five emit sites

```ts
observer: CacheObserver | undefined;
```

A bare declaration with no initializer, which under this package's `target`
emits **no code at all**. The sites:

| site | event | why there |
|---|---|---|
| `notify(record)` | `query` | the single choke point every transition already passes through — `start`, `settle`, `fail`, `adopt`, `drop`, `clear`. One expression covers dispatch, settle, failure and clear. |
| `mutate`, before `invalidator.settled` | `mutation` | the cause, emitted ahead of every invalidation it explains |
| the `onInvalidated` handler | `invalidated` | which query, and which of its tags matched |
| the `onPlace` handler | `placed` | placement is *why no refetch was owed*, and is otherwise indistinguishable from a settle |
| `applyFrames` (streams only) | `frames` | a frame batch is a mutation somebody else performed |

**Cost when unset: one property load and one nullish check per site, and no
allocation.** `f?.(args)` short-circuits the whole call expression — the
argument literal is never constructed when `f` is nullish. That is the reason
the events are object literals at the call site rather than positional
arguments; it costs nothing at runtime and reads.

A **sixth site was removed** after measuring: `setPrincipal`. `watchPrincipal`
already reports the identity change to anyone who asks, with the cache already
emptied, so an event would have been a second way to learn the same fact paid
for by every production bundle. The devtools uses `watchPrincipal` plus a
`cache.owner` comparison instead — and that turned out to be *more* correct, not
just cheaper: `setPrincipal` assigns the new principal and then calls `clear`,
which re-mounts and re-fetches every watched query, so a whole burst of events
arrives before the principal watchers ever run. Comparing `cache.owner` on each
event puts the session divider where it belongs; `watchPrincipal` is the
backstop for a change that produces no events at all.

The core keeps **no history**. Every event is handed over or forgotten. There is
a test that runs fifty mutations with nothing attached, attaches afterwards, and
asserts the log is empty — the outside-in proof that nothing was buffered.

One observer, not a list: two consumers of a debug seam is not a real scenario,
a list costs an array in every bundle, and a single slot makes "who has it"
answerable by looking at one field. `attach` chains to whatever it found and
restores it on `dispose`; a disposed inspector that cannot reclaim the slot goes
**inert** rather than staying live, because a disposed recorder still filling a
ring is a leak with no reader.

### `QueryRegistry.all()`

An iterator over the remembered entries. Needed because "which queries are
there, and what do they carry" was otherwise unanswerable: `get` needs a key you
already have and `queriesFor` needs a tag you already suspect, and a developer
asking why a mutation missed has neither. Documented read-only for the same
reason `QueryEntry` is — the entries are the live objects the tag index holds.

### `socketSnapshot(manager)`

A **free function**, not a method, and the reason is measured rather than
stylistic: as a method it cost 120 B gzipped inside the streams layer, paid by
every live application for a panel almost none of them will open. A class method
cannot be tree-shaken; a free function is paid for by the bundles that import
it. It reads the private `sockets` map through a cast **inside the module that
owns the field**, which is the trade — the field stays private and no consumer
gains access, versus making it public so a function three lines below could read
it and handing every caller a mutable map of live connections.

### The cost, exactly

| slice | before | after | delta |
|---|---|---|---|
| entity store | 1946 B | 1946 B | **0** |
| tag graph | 2073 B | 2082 B | +9 B (`all()`) |
| query engine + REST transport | 6420 B | 6495 B | +75 B (four emit sites) |
| stream binding | 3291 B | 3319 B | +28 B (the `frames` site) |
| **core, REST only** | **6461 B** | **6540 B** | **+79 B** — budget 9 kB |
| **core with streams** | **8973 B** | **9162 B** | **+189 B** — budget 14 kB |

All gzipped, `size-limit` with esbuild. The whole-file "with streams" figure
grows by more than the sum of its parts because it applies no import filter and
therefore includes `socketSnapshot`, which a real bundle tree-shakes; the
zero-cost test asserts exactly that.

**Justification.** 79 B against a 9 kB budget, for the difference between a
cache whose surprises are inspectable and one whose surprises are not. The
design's own risk table names devtools as the mitigation for the two highest
non-critical risks (normalized-cache tarpit; socket count growing with the
render tree), and a seam is the only way to have it without shipping the tool.
The one budget that moved is internal: `query engine and REST transport` from
6.5 to 6.6 kB, because 6495 against a 6500 limit is a CI failure waiting for a
rounding wobble. The headline budgets are untouched and both have room.

**One thing found on the way, not fixed here.** `live.ts`'s `development()` is
written `typeof process === 'undefined' || process?.env?.NODE_ENV !==
'production'`, and its comment claims a production build drops the unknown-
message warning and its `Set` entirely. Measured under esbuild with the standard
define, the second half folds to `false` but `typeof process` cannot, so the
disjunction survives as `typeof process > "u"` — which is `true` in a browser
bundle. The warning path ships and runs. It is capped at 32 entries so it is not
a leak, and changing it is a core behaviour change outside this chunk's scope,
but the comment currently overstates what happens. Flagged rather than touched.

## 3. How zero production cost was proved from the built output

`__tests__/zero-cost.test.ts` compiles the package with `tsc` — so the fixtures
import `dist/`, not source — then bundles three fixture applications with
esbuild exactly as a real build would (`bundle`, `minify`, `format: esm`,
`platform: browser`, `define: process.env.NODE_ENV = "production"`) and reads
the bytes.

| fixture | raw | gzipped |
|---|---|---|
| `production.ts` — uses the runtime, never imports the devtools | 20282 B | **6722 B** |
| `guarded.ts` — the dynamic import behind a `NODE_ENV` check | 20255 B | **6714 B** |
| `instrumented.ts` — imports the devtools statically | 33095 B | **11115 B** |
| the tool's entire cost | | **4393 B** |

The assertions:

- The production bundle contains **none** of six marker strings — the relation
  names and hint prose, which no minifier renames and which nothing else in the
  runtime contains — nor `whyNotRefetched` nor `nearMisses`. Markers are
  literals rather than identifiers on purpose; an identifier-only list would
  pass vacuously against a minifier.
- The instrumented bundle contains **all six**, which is what makes the absence
  meaningful, plus a floor on the size delta so that a future change which
  tree-shakes the analysis out of the *instrumented* build — making the tool
  useless while making this file pass — is caught.
- The production bundle **does** contain the core (`no client configured`), so
  the check is not passing because the fixture failed to pull anything in.
- The production bundle does not contain `reconnecting:`, i.e. `socketSnapshot`
  tree-shook away.
- The guarded bundle contains no marker, no `client-devtools`, and **no
  `import(` at all** — the branch folded and the chunk was never emitted — and
  is byte-for-byte no larger than the control.

The guarded fixture also established, the hard way, the spelling applications
must use. Written defensively as `typeof process === 'undefined' ||
process?.env?.NODE_ENV !== 'production'`, the whole package ships: the second
half folds, the first cannot, the disjunction survives and the import stays. The
bare `process.env.NODE_ENV !== 'production'` (or `import.meta.env.DEV`) is what
folds. That is now documented in the fixture, the README and the package's entry
doc.

The complementary runtime proof is in `log.test.ts`: fifty mutations with no
inspector attached, `cache.observer` asserted `undefined`, then attach and find
the log empty. The core retained nothing.

## 4. The log bound, and what happens when it fills

A fixed-size ring, **500 entries by default**, allocated once at capacity and
never grown. When it fills, **the oldest entry is overwritten** and `dropped`
counts how many are gone, so a timeline that begins mid-story says so instead of
pretending it begins at the beginning. `seq` keeps counting across the wrap, so
a `cause` reference to an entry that has been dropped resolves to `undefined`
rather than to whatever now occupies the slot. The overlay renders the dropped
count above the table.

Bounding the count is the easy half. The half that is easy to get wrong is
what is *in* an entry, and nothing here retains anything that could keep a page
of data alive:

- **no response body** — tags are resolved when the event arrives and only the
  resolved strings are kept;
- **no arguments object** — reduced to a cache key truncated at 200 characters;
- **no error object** — reduced to a short string, because an error retains its
  stack and every closure on it;
- **no rehydrated value** — which would additionally keep entities alive that
  the store's own garbage collection had let go.

Tested: a mutation with a 5 kB argument and a 5 kB response leaves a whole log
under 3 kB, with the argument key truncated.

The recorder's own per-query bookkeeping is bounded too — three maps keyed by
query key, and a query key includes its arguments, so a search box calling
`useOrderList({q})` on every keystroke mints one per keystroke. Above 512 keys
it drops the ones the registry no longer remembers (exactly the set that can
never be asked about again); if that is not enough it starts over, and the only
consequence is that the next request for a forgotten key is labelled `mount`
rather than `manual`.

`capacity` is configurable. Raising it raises memory and nothing else, because
the per-entry size is already bounded — the product is predictable.

## 5. Inspection does not mutate

The constraint that shaped `inspect.ts` more than any other, and it is less
obvious than it sounds. `cache.getState(meta, args)` — the natural way to read a
query — calls `open`, which **moves the record to the back of the LRU order** and
creates one if it is missing, then `snapshot`, which calls `read`, which
rehydrates the skeleton, builds store memos, links them into the
reverse-dependency index and assigns the result onto the registry entry's
`value`. An inspector built on it would change which query is evicted next,
change what a placement callback is handed as `current`, and populate memos for
queries nobody rendered — **only while somebody has the panel open**, which is
the worst possible failure mode for a debugging tool. A previous review of this
codebase found that exact shape of defect (`getState` opening records as a
render-phase side effect); reintroducing it from the outside would be worse.

So the whole read surface is map lookups and counters: `registry.all/get/
queriesFor`, `store.keys/getRecord/size/version/frameVersion/tombstones`,
`socketSnapshot`. Nothing calls `getState`, `fetch`, `read`, `denormalize` or
`dependencies`. `getRecord` returns the store's own record, so `fields` is
copied one level on the way out — a panel that wrote to a snapshot would
otherwise move the store's data with no version bump and no memo invalidation,
which is the most confusing failure this cache can have.

The test runs every read the API offers over everything, then asserts:

- record count, store version, frame version, tombstone count;
- tracked/remembered/mounted counts, indexed and stamped tag counts;
- **the private LRU order, in order**, read straight off `cache.records`;
- every record's version;
- full registry state per entry — mounts, stale, settledAt, tags, deps, and
  `value` **by identity**, which a rehydration would replace even for unchanged
  data.

And it carries its own discriminator: a sibling test calls `getState` on the
query at the front of the LRU order and asserts the order **changed**. A passing
assertion over a check that cannot fail proves nothing.

## 6. Sizes

### The devtools

| entry | gzipped | budget |
|---|---|---|
| inspection API (`dist/index.js`) | 4850 B | 5.5 kB |
| overlay (`dist/overlay.js`) | 2773 B | 3.5 kB |
| both together | 7655 B | 8.5 kB |

**The budget, and why.** The design gives this package none, and it is the one
package with no end user to protect: it never reaches a production bundle, which
is proved above rather than asserted. So the budget's job is not to protect
users from bytes — it is to catch *accidental* bloat, the day somebody reaches
for a charting library to draw a table. It is set so the inspector cannot
quietly grow past the runtime it inspects: 5.5 kB against a core of 6.5 kB
REST-only, with roughly 13% headroom on each entry, which is enough for a
feature and not enough for a dependency.

The overlay is measured separately because it is a separate entry point, and it
is genuinely separable — `overlay.ts` imports only *types* from `devtools.ts`,
so a consumer who wants the API and their own UI pays 4850 B and not 7655.

The devtools suite, by file:

- **`explain.test.ts`** — the two questions. The near miss is a *real* one, run
  end to end: a list mounted and settled carrying `Order[]`, a create declaring
  `Order:{res.id}`, and the test first asserts the list genuinely did not
  refetch (by counting `GET /orders` transport calls) before asserting the
  report explains why. Plus the four other outcomes, unresolved templates,
  `explain` picking the question, and `wouldInvalidate` not running anything.
- **`inspect.test.ts`** — the non-mutation pass and its discriminator; snapshots
  being copies; entity, dependents through a nested reference, and the tag graph
  separating carriers from mounted queries.
- **`log.test.ts`** — the ring bound, the zero-capacity edge, 200 mutations into
  a 32-entry ring, payload bounding, the pruning of per-query bookkeeping, the
  identity boundary and session numbering, and the attach/dispose/chaining
  behaviour including "the core buffered nothing".
- **`live.test.ts`** — a frame batch as a cause; a `patch` frame that correctly
  refetches nothing, explained; and the connection panel with two subscribers on
  one socket.
- **`tag.test.ts`** — parsing and every near-miss relation, including the cap.
- **`overlay.test.ts`** — renders, explains, keeps its styles inside the shadow
  root, removes itself, and survives a listener that throws.
- **`zero-cost.test.ts`** — the bundling experiment above. Runs under `node`
  rather than `jsdom`, because esbuild refuses to run where `TextEncoder` does
  not produce a real `Uint8Array`.

**Determinism.** Nothing sleeps. The invalidation scheduler, the frame scheduler
and the socket-release scheduler are all `manualScheduler`; the clock is a
counter; the transport is a map from `METHOD path` to a reply, deep-cloned per
request so the store's identity checks never compare a value against itself.

**Flake: none.** 12 rounds × 5 packages = 60 suite runs, 60 green, 0 failures.
