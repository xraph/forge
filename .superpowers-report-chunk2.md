## Unresolvable templates: skip the tag and report it

`resolveTag` returns `undefined` rather than a partially substituted string —
never `Customer:`, which is an invalidation that matches no query, fires
nothing and reports nothing. At the point of use the `Invalidator` **drops that
one tag, keeps the rest of the list, and calls `onUnresolved`**, which warns
once per template by default.

The three alternatives are each worse:

- **Emit the empty substitution.** The silent failure the design explicitly
  forbids. Not a candidate.
- **Throw.** The template is resolved on *mutation settle* — the server has
  already committed the write. Throwing converts a cache defect into an
  application-visible error for work that succeeded, so the user sees a broken
  screen instead of a stale row, and the mutation's own success path never
  runs. A cache is not entitled to fail a completed write.
- **Drop the whole `invalidates` list.** One bad cross-entity declaration would
  cost the nine tags beside it that resolved fine, converting a narrow
  under-invalidation into a broad one.

The spec's position is that an unresolvable template **fails generation**, and
that remains the real gate: this is the runtime's report that one got past it,
not a substitute for it. Skipping keeps the blast radius at exactly the tag
that is broken, and the report is what makes it findable — the failure mode
being designed against is the one nobody can see.

One detail that falls out of "first match wins": a match is the first source
that has the property *at all*, so a body holding `customerId: null` stops the
search and resolves to nothing. Falling through to the response there would
invalidate some other customer's list on the strength of a value nobody
supplied.

## Coalescing, made deterministic

The scheduler is injected: `type Scheduler = (flush: () => void) => void`.

- Default `microtaskScheduler` — `Promise.resolve().then(flush)`. Never a
  timer. A delay that is "long enough" on a laptop is a flake on a loaded CI
  box and a visible pause on a slow phone.
- `manualScheduler()` runs nothing until `flush()` is called.

Every coalescing test uses `manualScheduler`, so the assertions are about what
the code did, not about whether a machine got round to it in time. No test in
this chunk sleeps, and none uses fake timers either.

One test does exercise the default microtask scheduler, and it is deterministic
by *ordering* rather than by timing: the invalidations are synchronous, so the
batch's microtask is queued before the test awaits, and a microtask queued
first runs first. `await Promise.resolve()` is a guarantee, not a delay.

The batch is a `Set<QueryEntry>` plus a `scheduled` flag. The set is what makes
N invalidations one batch and a query hit by two tags one refetch; the flag is
what makes it one scheduled callback rather than N that each find an empty
queue. `Invalidator#flush()` also runs it on demand, for SSR.

## Registry and index: one structure

One. `QueryRegistry` owns `entries`, the tag index, and the invalidation
stamps; the index is private and has no mutator of its own. Every mount,
unmount and settle has to touch both, and a path that updates one without the
other produces either a leak (a bucket holding a query nobody watches, which
then refetches on every invalidation forever) or a query that quietly stops
updating. Making it impossible to write one without the other removes the class
of bug instead of documenting it.

The hard part was that the two lifetime requirements pull in opposite
directions:

- The index must hold **mounted queries only** — the last unmount removes the
  entry from every bucket and deletes the buckets it emptied.
- An invalidation arriving while a query is **unmounted** must still be
  observed when it mounts again, or a tab switch swallows a write.

Reconciled with a clock rather than by keeping unmounted queries indexed: each
invalidation bumps a counter and stamps it onto the tags it touched, each
settle stamps it onto the query, and a query mounting with a tag stamp newer
than its own missed something. The stamps are one number per tag ever
invalidated — bounded by the API's tag vocabulary, not by how many queries have
ever mounted. Placement stamps the clock forward too, so the invalidation a
callback just handled does not undo the escape hatch on the next mount.

A mounted query's tag set is `provides` (resolved against args, re-resolved
against the response at settle) unioned with the entity keys `normalize`
reported. Those keys are already spelled `Type:id`, which is exactly the tag a
mutation to `Order:7` invalidates, so chunk 1's dependency tracking *is* the
per-entity half of the tag index. Nothing was duplicated.

## Placement

`(created, current, args) => list | undefined`, declared per tag at the
mutation site. Returning a list skips that query's refetch; `undefined` falls
back to it. All-or-nothing per query: a query matched by `Order[]` and
`Customer:3` where only the first has a callback still refetches, because
placing one while the other is unhandled leaves it looking updated while being
wrong. Callbacks chain when several tags match, so the second sees the first's
result as `current`. A throwing callback is reported through `onError` and
treated as `undefined` — one application callback does not take the batch down.

## What this chunk deliberately does not do

- No fetching. `execute` is injected and called once per batch.
- No in-flight request tracking. A query that goes stale is reported every
  time it goes stale; whether two invalidations one tick apart can share one
  request is a question about requests, which the transport chunk owns.
  Suppressing here would answer it wrongly, by serving a response fetched
  before the second write.
- No GC policy. `QueryRegistry#drop` exists and nothing calls it, so an
  application mounting unboundedly many distinct argument combinations grows
  the registry. The LRU/idle policy lands with the query cache.
