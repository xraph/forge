# Chunk 7 — `live` on all three adapters

`useQuery(op, args, {live: true})`, `useQuery(op, args, {live: ref})` and
`injectQuery(op, args, {live: signal})` now exist and subscribe through the
chunk-5 runtime. Nothing in the stream layer was reimplemented; the whole of the
work was resolving channels, reaching the binder from a call site, and getting
three teardown paths right.

## The channel-resolution rule

> **A query's live channels are every channel with a `streams[]` binding whose
> `entity` is reachable from the query's declared result type — its
> `ops[x].entity`, plus everything `entities[T].fields` descends into,
> transitively.**

That set is exactly the set of typenames `normalize` can lift out of this
operation's response, which is to say exactly the entities that can appear in
its skeleton. It needs nothing the manifest does not already emit: `writeOps`
emits `entity` per operation, `writeEntities` emits the `fields` edges, and
`writeStreams` emits `{channel, message, entity, intent, invalidates}`.

`StreamBinder.channelsFor` previously answered with the root entity's channels
alone. That is the smaller rule and is wrong in a way that is hard to see from
the outside: an order list rendering `order.customer.name` holds `Customer`
records in its skeleton, and a `customer.updated` frame changes what is on
screen. A client subscribed to `/ws/orders` alone renders that name stale
forever with every order around it perfectly current — which is the exact class
of "looks correct while being wrong" defect the rest of this layer is built to
prevent. The walk is iterative and `seen`-guarded because the generated schema
is a graph, not a tree (`Order.customer → Customer.orders → Order` is ordinary),
and memoized per root typename because the schema is generated and frozen.

Deliberately **not** derived from the registry's settled `deps`, even though
they are available and more precise. See below.

## Before the first settle

**Subscribed optimistically at mount, from the declared result type.** A live
query holds its channels from the moment it is created; `deps` are never
consulted.

Two reasons, pointing the same way:

- Deps do not exist until the first response lands, so a deps-based rule is deaf
  during exactly the window whose frames matter most — the ones that arrive
  while the first load is in flight. Subscribing on settle would mean the design
  document's "one socket per `(endpoint, principal)`" has a hole in it precisely
  where a busy channel is busiest.
- Deps follow the *data*, not the type. A second page of orders that happens to
  contain no `Invoice` would drop the invoice channel and re-acquire it on the
  page after: subscription churn driven by pagination, against a manager whose
  whole job is to not open and close sockets.

The static rule is a superset of the deps rule and is stable for the lifetime of
the query, which is what makes ref counting across queries meaningful at all.

## Toggling semantics

The live subscription is a **second, independent lifetime beside the query's**
in all three adapters — a separate release handle, a separate effect/watcher.

- `false → true` subscribes from that moment. It does **not** remount the query,
  does not refetch, and does not move `status` or `isFetching`.
- `true → false` releases the subscription. The query keeps the value it has and
  issues no request.
- An **argument** change re-subscribes the live half against the new key as well,
  so `{live: true}` on `useOrderGet(() => ({path: {id: id()}}))` is live on
  whichever order is on screen and is registered under that key for gap
  recovery.

Turning `live` on deliberately does not refetch to cover the window it was off
for. Freshness is the cache's business — invalidation and staleness — and making
`live` a hidden refetch trigger would mean a prop or a `ref` that flips costs a
request per flip. The gap that genuinely is the runtime's fault, a dropped
socket, is recovered by `StreamBinder.recover`, which is unchanged.

Omitting the option entirely means the call site is not live and cannot become
live. Vue and Angular create no watcher at all in that case, so a query that
never mentions `live` pays nothing.

## Did the core need changing

Yes, in two small places, and one of them is a genuine gap rather than plumbing.

1. **`QueryCache.live` + `QueryCache.watchLive` (`cache.ts`).** There was no way
   for an adapter to reach a `StreamBinder` from a `QueryCache`. `StreamBinder`'s
   constructor now assigns `cache.live = this` — the same "wired here so it
   cannot be left unwired" argument that already applies to `manager.onReconnect`
   — and `dispose()` gives the slot up, but only if it is still holding it.
   Adapters call `cache.watchLive(op.meta, args)`, so all three cache-resolution
   paths (per-call `client`, provider, module default) reach the right binder
   with no second provider to wire and nothing in a generated file that has to
   know streams exist.

   The seam is declared in `cache.ts` as a structural `LiveBinding` interface
   rather than imported from `live.ts`. Importing `StreamBinder` into an adapter
   would have put the whole 2.5 kB streams layer into every REST-only
   application that uses `useQuery`; a structural interface is erased by the
   compiler and costs nothing.

   `watchLive` exists rather than `cache.live?.subscribe(...)` for one reason:
   a call site that asked for `live` against a client with no stream runtime
   attached must not silently be handed a query that never updates. It reports
   through the cache's own error channel and survives — the query is perfectly
   good, it just fetches rather than streams.

2. **`StreamBinder.channelsFor` (`live.ts`).** Widened from the root entity to
   the closure described above, memoized per root.

No change to `SubscriptionManager`, `applyFrames`, gap recovery, batching or the
ordering guarantee. The adapters subscribe once per *query* (never per
component), so the existing ref counting does the sharing unmodified.

## Lifecycle parity

| | subscribe | release |
|---|---|---|
| React | `useEffect`, keyed `[client, op, key, live]` | effect cleanup — unmount, and the StrictMode phantom unmount, which the manager's deferred close makes free |
| Vue | at setup + `watch([key, live])` | `onScopeDispose` (component *or* bare `effectScope`) and the explicit `dispose()` |
| Angular | at bind + `effect` on the live getter, and inside the existing args effect | `DestroyRef.onDestroy`, and the explicit `destroy()`, which stops the live effect as well as the subscription |

Angular's `destroy()` releasing the live subscription **and** stopping the live
effect is chunk 6's divergence, applied to the new half: releasing without
stopping the effect leaves a watcher whose next tick re-acquires a socket the
caller has explicitly finished with.

**Principal change.** Confirmed by test in all three adapters: the previous
principal's socket is closed and a replacement is opened for the new one,
without the component doing anything. `StreamBinder` watches the cache's
principal and calls `manager.repartition()`, which reopens with the same handler
set and fires `onReconnect` → `recover`, so the query refetches under the new
identity rather than going quietly deaf.

## Tests

`packages/client-{react,vue,angular}/__tests__/*live*.test.ts{,x}`, nine per
adapter, using each framework's real test setup — Testing Library + `act`,
`@vue/test-utils`, a zoneless `TestBed`. No sleeps, no real sockets, no real
timers: the transport, the sockets, the frame scheduler and the deferred-close
scheduler are all hand-driven.

Per adapter: a frame updates a live query with no request behind it; two
consumers share one subscription; two different live queries on the same entity
share one channel; the last consumer's teardown releases it and the
second-to-last does not; the framework's own teardown path releases it (React
unmount, Vue `effectScope().stop()` **and** `dispose()`, Angular injector
`destroy()` **and** `destroy()`); toggling `live` subscribes and unsubscribes
with no refetch in either direction; a query that never says `live` opens no
socket at all; and a principal change re-subscribes.

Six more in `client-core`: the closure rule, a frame on a nested entity reaching
a query rooted elsewhere, subscription before first settle, the cache
registration, the missing-runtime diagnostic, and two binders contending for the
slot.

Verified discriminating: stubbing `watchLive` to a no-op fails 8 of the 9 tests
in each adapter (the ninth asserts an *absence* and correctly still passes).
