## How `getSnapshot` stays stable

By passing `handle.getState` through **untouched**, and building the convenience
shape after the `useSyncExternalStore` call rather than inside it.

`QueryCache.snapshot()` already returns the same `QueryState` object on every
read until `data`, `status`, `error` or `isFetching` actually changes, and
`data`'s identity comes from the entity store's per-subtree memo. Chunks 1–3
were built for this. The only way this layer could lose it is by wrapping the
value on the way out — a `{...state}`, a `.map()`, a `useMemo` with the wrong
deps — so the code does none of those things and the comment above the call says
why.

I verified the failure mode rather than assuming it. A scratch hook identical to
the real one but with `() => ({...handle.getState()})` as `getSnapshot` makes
React throw, verbatim:

```
The result of getSnapshot should be cached to avoid an infinite loop
```

The second half of stability is the `subscribe` argument, which must be stable
across renders *and* must change when the query changes. Both come from
memoising the handle on `client.key(op.meta, args)` — the cache key string —
**not** on the `args` object, which is a new literal on every render for a
caller writing `useQuery(useOrderGet, {path: {id: 7}})`. Measured, with the same
scratch harness, memoising on `args` instead:

```
re-mounts over 5 renders: 5   mount-count dips: [0, 0, 0, 0]   final mounts: 1
```

Five unnecessary unsubscribe/resubscribe cycles over five renders, each dropping
the registry mount count to zero — which unlinks the query from the tag index
and, while the count is zero, makes its cache record LRU-evictable. Chunk 3's
invalidation stamps mean the query recovers rather than silently dying, which is
why this presents as churn rather than as a bug report; it is still five
teardowns of a subscription nothing asked to tear down.

`useMemo` is a cache React may discard, so this is a hint, not a guarantee. That
is survivable in the direction it can fail — a discarded memo costs one
resubscribe of the same query, which the cache ref-counts correctly. The
direction that would be fatal, a `subscribe` that stays stale after the key
changes, is impossible because the key is a dependency. Pinning the handle in a
ref would invert exactly that trade, which is why it is not done.

Pinned by two tests: ten parent-driven re-renders leave the result object
referentially identical, the mount count at 1, and the request count at 1; and
changing `args` moves the mount from the old key to the new one.

## StrictMode: before and after

**Before — and this is a real failure in this package's own code, not a
hypothetical.** `useMutation` guards its state updates with a liveness ref so a
response landing after unmount does not schedule work nobody reads. The obvious
spelling is:

```ts
const alive = useRef(true);
useEffect(() => () => { alive.current = false; }, []);
```

Development double-invokes effects: mount, unmount, mount. Nothing ever sets
`alive` back to `true`, so the *phantom* unmount disarms the hook permanently,
before the component has rendered anything a user could click. The StrictMode
test failed on exactly that:

```
FAIL  useMutation > still reports status after a StrictMode mount / unmount / mount
AssertionError: expected 'pending' to be 'success'
```

Note what that means in an application: the mutation ran. It reached the server,
committed its entities, invalidated its tags, and the new row appears in the
list beside the button — while the button spins forever. And it reproduces in
development only, which is why it arrives as "works in production, broken
locally", sounds like an environment problem, and is dismissed.

**After** — re-arm on mount instead of only disarming on cleanup:

```ts
useEffect(() => {
  alive.current = true;
  return () => { alive.current = false; };
}, []);
```

Initial value stays `true` so a mutation fired from a layout effect, before
passive effects run, is not dropped on a genuine first mount.

`useQuery` needed no equivalent fix, and that is the argument for
`useSyncExternalStore` rather than a claim about care taken. React owns the
subscription lifecycle there, so the phantom cycle is subscribe → unsubscribe →
subscribe against `QueryCache`'s own ref counting, which handles it. The test
asserts the outcome rather than trusting it: after a StrictMode mount, exactly
one registry mount survives — not zero (the query silently stops updating) and
not two (one invalidation fans out into two refetches) — the phantom unmount
provokes no second request, and an invalidation raised afterwards still lands
and re-renders the component.

## What `getServerSnapshot` returns, and why

A single frozen module-level constant: `{status: 'idle', data: undefined,
error: undefined, isFetching: false}`. Never a cache read.

Three constraints, and the constant is the only thing that satisfies all three:

1. **Stability, under a harder condition than `getSnapshot`.** It is called for
   queries no cache has ever opened, so there is no per-record memo to lean on.
   A constant is stable by construction.
2. **It must match the client's first hydration pass.** React compares them and
   treats a difference as a mismatch. This chunk ships no store serialisation,
   so a hydrating client necessarily starts with an empty cache — which is
   `idle`. Returning server-fetched data would not be an optimisation; it would
   be a guaranteed mismatch on every query on the page.
3. **It must not touch a cache.** On a server the module-level client is shared
   by every concurrent request, and `getState` opens a record as a side effect,
   so one request's server render would create entries under another's cache.
   And `getClient()` throws when nothing is configured, which would turn "SSR is
   not supported yet" into "your server render crashes".

The consequence is deliberate and stated in the README: **a server render emits
the loading branch**, and data arrives after hydration. That is the honest
rendering of what this chunk can deliver. Chunk 5 replaces the constant with a
snapshot read from the serialised store, at which point 2 and 3 are satisfied by
machinery rather than by abstaining. Tested with a real `renderToString`: the
markup is `idle:-:false`, no request is issued, and `cache.size` is still 0.

## Peer dependencies

`react` (`^18 || ^19`) and `@forge-go/client-core` (`^0.1.0`) are both peers.
React for the usual reason. The core for a reason one layer down and just as
sharp: two copies means two module-level `active` caches, so the client the
application handed to `configureClient()` is not the one its generated `hooks.ts`
reads from, and every query fetches into a cache nothing renders.

## Test coverage

`@testing-library/react` v16 on jsdom, driving React's `act()` and the core's
injected `manualScheduler`. No sleeps, no fake timers, no polling anywhere.

Required by the brief:

- query renders its value and re-renders when a dependent entity changes ✓
- a component reading an unchanged sibling entity does not re-render ✓
- StrictMode mount/unmount/mount leaves a live subscription ✓ (query and mutation)
- two components on one query share one request ✓
- a mutation updates dependent queries ✓
- unmounting the last consumer releases the subscription ✓

Also covered: an unchanged entity keeps its identity across a refetch;
`getSnapshot` survives ten unrelated re-renders; changing args re-subscribes;
a failed refetch keeps the last good value beside the error; a failed first
fetch is an error state, not a render throw; placement callbacks are applied and
skip the refetch; the *latest* render's placement callbacks are used;
overlapping mutations let the last win; client resolution precedence
(explicit > provider > module-level) and the named error when there is none;
`getServerSnapshot` under real `renderToString`.

One assertion I had to correct against reality rather than against intent. I
first asserted that a refetch returning structurally-equal data preserves the
identity of the whole array. It does not, and should not: the store memoises by
skeleton node, a fresh response is a fresh skeleton, and the store declines to
claim it knows the shape of a list is unchanged. What *is* preserved is
`Order:1` itself, which is what a `memo`'d row consumes. The test now asserts
both halves — `data[0]` is identical, `data` is not — and the README says so, so
nobody has to rediscover it.
