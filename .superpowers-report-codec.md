# Codec parity: the generated client stops contradicting its own generated types

Branch `feat/client-codec-parity`, from `d38dfe34`.

## The defect, and why the two halves are one change

The runtime's `RestTransport` drives the generated `HTTPClient#request`, not the
typed per-endpoint methods -- those take positional, per-endpoint parameters
(`(orderId, body, options)`) that a generic caller holding only an
`OperationMeta` cannot fill. `request` applies `encode`/`decode` only for the
codec ids the config it is handed names, and `RestRequestConfig` in
`packages/client-core/src/transport.ts` did not even declare them. So under
`--field-naming camel` or `--field-overrides`, hooks returned WIRE-cased fields
while the typed REST methods returned RENAMED ones, from one package,
contradicting the generated TypeScript types.

Plumbing the codecs through alone would have been worse than the bug.
`opsmanifest.go` emits `idField` and the KEYS of `fields` as verbatim wire names
(they trace to `schema.Properties` keys, pre-rename). Decode a response into
camelCase without renaming the entities table and the normalizer stops finding
ids -- silently, because a type whose id field is absent simply is not an
entity. That is a cache that quietly stops caching: no error, no warning.
Verified, not assumed -- see "Both halves proven necessary" below.

## 1. Where the codec ids ride, and why

`OperationMeta` in the generated `src/ops.ts`, mirrored in
`packages/client-core/src/transport.ts`.

`OperationMeta` is already the complete generation-time description of one
operation that the runtime is handed: method, path, entity, rootType, cache
tags. A codec id is another per-operation fact resolved in Go by the same pass
over the same endpoint. Any other home -- a second table, a lookup keyed by
operation id -- would mean the transport doing a second lookup keyed by the
object it is already holding, and a second thing to keep in step with the first.

`RestRequestConfig` now declares `bodyCodec`/`responseCodec`, and
`RestTransport.execute` forwards them from the meta. They are assigned only when
present (not assigned-as-undefined) so the config still satisfies a generated
client compiled with `exactOptionalPropertyTypes`.

Both the two `OperationMeta` fields and the values emitted into them are gated
on `codecsNeeded(config)` -- the same gate `generator.go` uses for `src/codecs.ts`
and `fetch_client.go` uses for `RequestConfig`'s copy of the fields. A manifest
that named a codec table which was never emitted would be a dangling reference.

## 2. Which renamer was reused

`tsFieldName` (`internal/client/generators/typescript/fieldname.go`) -- the same
function `generator.go` renders every interface property through and `codecs.go`
builds every codec entry from. `renameEntityField` is a four-line wrapper over
it, deliberately not a second copy of the camel/pascal/snake rule: a second
implementation of a naming rule is how two tables drift, and a drift between the
codec table and the entities table is invisible at runtime.

`tsFieldName`'s schema-name argument is the entity's typename, because an
entity's typename IS its component-schema name -- the same id `codecIDFor`
derives for that schema's own properties. That is what makes a schema-scoped
`FieldOverrides["Order.order_number"]` reach the codec table and the entities
table identically. An empty `IDField` (an envelope, a routing hop) is returned
untouched rather than handed to `tsFieldName`, whose override lookup would
otherwise consult the meaningless key `"Order."`.

## 3. How typenames stayed untouched

`fields` maps a property name to a typename, and only the property side is a
field name. `renameEntityFields` renames keys and copies values verbatim:

```go
for wireName, targetTypeName := range fields {
    renamed[renameEntityField(typeName, wireName, config)] = targetTypeName
}
```

A value is the name of another row in this very table and of a generated
TypeScript interface. Renaming it would emit `primaryCustomer: 'customer'` -- an
edge naming a table key that does not exist -- breaking the entities lookup for
every nested entity in the document. The test asserts this as its own negative
(`assert.NotContains(ops, "'customer'")`), not merely as a side effect of the
positive assertion.

## 4. A third wire-named datum, found while doing this

`provides`/`invalidates` are resolved by `QueryRegistry#settle` against the
request arguments and then the RESPONSE -- and after half 1, that response is
decoded. `DeriveTags` builds the item tag as `Type:{IDField}`, a wire name, so
`Order:{order_number}` would have resolved to nothing against a payload carrying
`orderNumber`: the query registered under no item tag, and a later write to that
order invalidating nothing. Same silent stops-caching failure, one table over,
and newly introduced by half 1 rather than pre-existing -- so it is fixed here.

`renameDerivedIDTags` rewrites only the exact tag `DeriveTags` would have
produced for that endpoint's entity. A route may declare arbitrary templates
(`Customer:{req.customerId}`, `Shipment:{res.shipment.id}`) whose segments name
properties of types this function cannot resolve a namespace for; a general pass
would have to guess, and a wrong guess produces a tag that silently matches
nothing. Hand-declared templates are left alone.

## 5. Supporting change

`requestBodyContentType`, `requestBodyCodecRef` and `responseCodecRef` became
package-level functions in `rest.go` (they read no receiver state; `warnings` is
returned, not appended to). The manifest calls the SAME resolvers `rest.go` calls
for the typed methods -- two resolvers would be two answers to "which codec
encodes this body", and the runtime would silently pick the other one. The
warning half of each return is dropped at the manifest call site: `rest.go`
already reports it for the identical endpoint, and reporting it twice would say
a spec has two problems where it has one.

## The proof

`internal/client/generators/typescript/e2e_codec_parity_test.go`. A snake_case
OpenAPI document on disk, through `SpecParser.ParseFile`, into
`Generator.Generate`. Identities are pinned with `x-forge-id` on `order_number`
and `customer_id` specifically so the id is a name that visibly changes under
renaming -- a fixture keyed on `id` would pass under a broken implementation.

- `TestEntitiesTableIsRenamedToMatchTheDecodedPayload` -- the manifest carries
  `Order: { idField: 'orderNumber', fields: { primaryCustomer: 'Customer' } }`,
  `responseCodec: 'Order'`, `provides: ['Order:{orderNumber}']`; no wire name
  survives anywhere in the entities table; no typename was renamed.
- `TestCodecParityEndToEndThroughTheRuntime` -- the generated client plus the
  working tree's `client-core` sources, bundled with esbuild and run under Node.
  A `RestTransport` over the generated client executes `ops['orders.get']` with
  global fetch answering a wholly snake_case document, and the test asserts the
  transport resolved with camelCase, that `store.write` put `Order:ord-7` and
  `Customer:cus-3` in the store with the edge followed through the renamed key,
  and that `resolveTags` resolved `Order:ord-7` with nothing unresolved.
- `TestPreserveNamingLeavesTheManifestByteIdentical` -- the negative, as a
  WHOLE-FILE comparison against the exact bytes `ops.ts` had before this change.
  A substring check is not an assertion that anything is byte-identical.

Go-side assertions alone would prove the manifest, not the feature. The runtime
half is what proves the manifest is read.

### Both halves proven necessary

Each half was reverted in isolation and the end-to-end test re-run:

- codec forwarding removed from the transport: the transport resolves with
  `{"order_number": "ord-7", ...}` -- the original defect, reproduced.
- entities renaming removed from the manifest (codecs still plumbed): the
  transport decodes correctly and **the store is empty**. `keys` is `[]`,
  `Order:ord-7` is nil, and nothing errors. That is the silent
  non-normalization this change exists to avoid trading the visible bug for.

### Adjusted existing tests

- `e2e_envelope_test.go`: two `wantOp` blocks gained the `responseCodec` line
  they now correctly carry. `TestGenerateFromSpecFileOmitsUnreachableAndUselessTypes`
  was scoped to the entities table (new `entitiesTable` helper) -- `PickPack` now
  legitimately appears as `bodyCodec: 'PickPack'`, which is a statement about
  wire encoding and says nothing about normalization. A positive pin was added
  so the scoping cannot start passing because the codec id vanished.
- `e2e_specfile_test.go`: `Order: { idField: 'order_number' }` ->
  `'orderNumber'`. `baseConfig` targets TypeScript, hence camel; the wire name
  there named a property the decoded payload does not have.
- `packages/client-core/__tests__/transport.test.ts`: three new cases -- both ids
  forwarded, both keys ABSENT (not undefined) when the operation declares none,
  and both surviving the credential-refresh retry, where `authorize` rebuilds the
  config as a spread.

## Not done

- WebSocket/SSE/WebTransport transports were not examined for the same
  contradiction. Their codec ids are emitted at their own generated call sites
  (`websocket.go`, `sse.go`, `webtransport.go`); whether a generic runtime caller
  drives those the way `RestTransport` drives `HTTPClient#request` was out of
  scope here.
- Hand-declared cache tag templates remain in wire space (see section 4).
