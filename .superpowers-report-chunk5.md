## Review round 2: the fix that opened a narrower hole

The Finding-2 fix (stamping `mutate`) reintroduced the eviction defect through a
narrower door, and the reviewer reproduced the original stack.

`mutate` commits with `skip` and then reads the skeleton back. When the raced key
is the mutation's **own** and the winning frame was an **evict**, the record is
gone — so a scalar root returned `undefined` typed as `T`, and an array root
silently lost an element. This could not happen before that fix, because
`store.write` re-put the record unconditionally.

The return value was the smaller half. `created` goes to placement,
`[created, ...current]` yields `[undefined, {...}]`, `adopt` re-normalizes it,
and a **literal** `undefined` is deliberately not a hole — only a dangling
reference is, which is the boundary drawn on purpose in round 1 — so it survived
into the rendered value and `data.map(o => o.id)` threw.

**Fix.** A raced key the store no longer holds is treated as the delete it is:
the caller gets what the server actually said rather than a corpse read out of a
store with no row in it, and **placement is declined** for that mutation.

Declining turned out to be load-bearing for a second reason I checked rather than
assumed: `adopt` re-normalizes a placement result straight back into the store
with no frame stamp and no skip, so placing the response would have
**resurrected the deleted entity**. Reverting just that clause makes
`store.has('Order:7')` come back `true`. Declining costs nothing — `undefined`
from placement already means "refetch instead", and the eviction frame
synthesized `${entity}[]` on its way through.

Two tests, both load-bearing: reverting the corpse-read guard fails 2, reverting
the placement guard fails 1. Note the first interleaving I wrote did *not*
reproduce it — a delete for a never-cached key correctly leaves no tombstone, so
nothing raced. The test had to use an entity the store actually held, which is
the only shape that leaves a stamp.

### `live.ts` is no longer binary to git

It held two NUL bytes as a `(channel, message)` key separator — collision-free,
and a mistake for a reason unrelated to correctness: a file containing a NUL is
binary to git and grep, so `git show` would not render a diff of the largest file
in the chunk. Replaced with a length-prefixed key, which is collision-free and
plain ASCII. `git diff --numstat` now reports line counts for it.

The relocation commit `698a6e8f` remains binary **in history**, because the blob
on its old side still contains the NULs. I did not rewrite it: the coordinator is
tracking these SHAs, and history surgery was not what was asked for. It is

### Tombstone eviction, recorded not raised

Recorded in the README's known gaps as asked, without touching the cap: evict
`Order:7`, then 256 further deletes of *cached* keys, and its stamp is pushed
out, at which point a pre-delete response still in flight puts the row back. The
cap makes this **improbable, not impossible** — a tombstone is only read by a
request straddling the delete, so 256 is far more than that window needs, and
that is what makes it survivable rather than prevented. Only reachable where the
tag path cannot help (unmounted, prefetch, SSR in flight); mounted, the
synthesized `Order[]` restarts the request and nothing resurrects. The real fix
is a GC policy keyed on the oldest live dispatch stamp, which needs the cache to
tell the store about it.

Also fixed the stale `QueryCache.applyFrames` doc reference left by the
relocation.

**Left as is, as directed:** the per-field caveat — a frame touching `total`
making an in-flight mutation's unrelated `note` write vanish from cache,
self-healing on any later fetch. Real, low severity, and documented as a
non-claim rather than papered over.

## Review round 1: what changed

Three findings, all real, all fixed and each covered by a test that fails when
the fix is reverted.

### Finding 1 (critical) — the evict hole, closed at both ends

`store.evict` dropped the record and nothing rewrote the settled skeletons still
pointing at the key, so `QueryState.data` became `[undefined, {id: 8, ...}]` and
any `data.map(o => o.id)` threw.

**Half one, the skeleton.** A reference with no record behind it is now a *hole*
and is dropped from the array rather than pushed as `undefined`
(`store.ts` `materializeNode`). Only a reference — a literal `null` the server
actually sent is passed through, because shortening that array would be the
runtime lying about the response. An object *field* still reads `undefined`,
which is what `order.customer` after the customer was deleted should look like.
The element returns if the record does, because the memo records the key as a
dependency before looking it up. This is the half that matters for route (ii):
the subscriber is notified synchronously, before any refetch can land.

**Half two, the tag.** The evict path now synthesizes `${entity}[]` whatever the
binding declared, exactly as `recover()` already did. That closes route (i) — a
delete binding reaching the client with `invalidates: []`, which the generator
permits since it passes the annotation through verbatim. Deliberately *not* done
for `upsert` or `patch`: synthesizing `Order[]` for `order.updated` would refetch
every mounted list on every update and destroy the property that makes a live
query worth having, and there is a test asserting it does not.

Reverting half one fails 6 tests; reverting half two fails
*"refetches a list after a delete whose binding declares no invalidation"*.

### Finding 2 (important) — `mutate` stamped, never re-issued

`mutate` now takes `dispatchedAt` before the request and runs the same
`stage` / `racedSince` check. It **does not re-run** — that shape was the point
of the finding, and re-issuing a write is the duplicate-orders hazard. It
commits with skip instead: the raced entities keep the frame's value, every
other entity in the response lands normally, and `created` is read back out of
the store so the caller receives the current truth rather than its own
superseded write. Reverting fails 2 tests.

Wording corrected in all three places (`README.md`, the applier's doc comment,
this report). The guarantee is now stated as **"a committed write never
overwrites an entity with a value older than a frame the client has already
applied"**, with the convergence difference spelled out per path, plus the
explicit note that it is per entity and not per field.

### Finding 3 (important) — tombstones bounded

The stamp was written before the existence check, so deletes for never-cached
keys accumulated forever. Now written only for keys the store actually held — a
tombstone for a key never present protects nothing, since no request can be
carrying a record nobody asked for — and capped at 256 with the oldest evicted.
A tombstone is only ever read by a request dispatched before the delete and
still in flight, so its useful life is one round trip and the cap is three
orders of magnitude more than that needs. `store.tombstones` is exposed so the
bound is testable. The 5000-delete repro now leaves 0 stamps for uncached keys
and ≤256 for cached ones.

### Minors

- The unknown-message warning is gated to development via a bare
  `process.env.NODE_ENV` reference (written that way on purpose — bundlers
  substitute it textually and fold the branch, which reading through
  `globalThis` would defeat), and the set is capped at 32 with a single
  "further warnings suppressed" line. It is keyed by what the *server* sends, so
  its growth was not this client's to control.
- A rejected query response now commits the entities the frame did *not* touch
  before re-running, so a re-run that then fails no longer leaves the query on
  `status: 'error'` holding data older than an answer it already received.
  Reverting fails 1 test.

### Relocation

`applyFrames` is now a free function `applyFrames(cache, frames)` exported from
the streams surface, over `cache.store`, `cache.entities`,
`cache.notifyChanged()` and `cache.invalidate()` — the same seams `mutate` uses.
Same implementation relocated, not the parallel applier I wrongly posed as the
only alternative. It also answers the "one code path, not two" note better than
the method did: the streams surface is explicit rather than a second top-level
write method sitting beside `mutate` on `QueryCache`.

## The ordering guarantee

> **A committed write never overwrites an entity with a value older than a
> stream frame the client has already applied.**

It covers **both** kinds of write — a query response and a mutation response.
The first version of this report said "a committed response", which read as
covering both while only the query path was stamped. That was review Finding 2,
and it is now true as written.

### How it works

Each request — query *and* mutation — records `EntityStore.frameVersion` **at
dispatch**, per attempt. Each batch of frames takes one fresh reading
(`nextFrame()`) and stamps every record it writes with it —
`EntityRecord.frameAt`, carried forward by `Math.max` so a later response
merging extra fields cannot erase it. An eviction leaves a **tombstone**
carrying the same stamp, because a deleted record has nothing left to hold one.

On arrival a response is **normalized but not committed** (`store.stage`). The
entity keys it actually carries are then compared against the store's stamps
(`store.racedSince(keys, dispatchedAt)`). If a frame stamped any of them since
dispatch, that data does not commit.

**How the loser converges differs by path, deliberately.** A *query* response is
discarded and the sequence re-run, through the loop chunk 3 already had for the
`restart` path — re-reading is free and idempotent. A *mutation* response is
never re-issued; retrying a write is the duplicate-orders hazard. It commits
around the raced keys instead, so the frame's value stands for those entities
and the rest of the response lands, and the value handed back to the caller is
read out of the store rather than being its own superseded write.

### Why this one and not the alternatives

The brief offered two shapes. This is the first — stamping at dispatch and
rejecting older responses — chosen over "treat a frame as an invalidation when a
request is outstanding" for one reason that decides it:

**The invalidation route runs through the tag index, and the tag index holds
mounted queries only.** `registry.invalidated(tags)` reads `this.index`, which
`unlink` empties on the last unmount. So the third of chunk 3's three bugs —
*unmounted, with a request in flight* — is structurally unreachable that way: a
prefetch, an SSR pass, or a component that unmounted while its request was out
has no entry for an invalidation to find. The stamp comparison is against the
response's own contents and the store's own records; mount state is not part of
the question. `frame-ordering.test.ts` asserts this directly with
`registry.mounted === 0`.

It is also more precise in both directions. A frame touching `Order:9` does not
restart a response carrying only `Order:7`, which a tag-shaped fix over `Order[]`
would. And it catches a response carrying an entity that no query's tag set
mentions at all.

Both mechanisms are live, and they are complementary rather than redundant: a
frame's *declared* `invalidates` still goes through `Invalidator.apply`, exactly
as a mutation's does. An `upsert` declaring `Order[]` still restarts a mounted
list's in-flight refetch through chunk 3's `stale()` hook — membership moved, and
the stamp comparison would not have noticed because the pre-create response is
not *wrong* about any entity it carries, only incomplete. Both cases have a test.

### Convergence, and the bound

For a query: one re-run per frame, not a retry loop. The re-run is dispatched
*after* the frame, so it carries a stamp the frame cannot be newer than, and it
commits whatever it returns — including the same stale body it was just rejected
for, if the server is genuinely lagging. There is a test that asserts exactly
that, because it is the difference between a guarantee and a spin.

The rejected response is not thrown away wholesale: the entities the frame did
*not* touch are committed before the re-run, so a re-run that then fails leaves
the query on `status: 'error'` holding the freshest data it actually received
rather than data older than an answer that arrived. (Review minor.)

Unbounded, the re-run livelocks: a channel busy enough that a frame lands inside
*every* request window restarts the sequence forever, and a query that never
settles is worse than the defect avoided. `frameRestarts` (3 by default) caps it,
past which the query falls back to the mutation rule below.

For a mutation: **never re-issued**, always commit-with-skip. Re-sending a write
the server may already have processed is how duplicate orders happen.

### What is deliberately not claimed

- **Per entity, not per field.** A raced record is skipped whole. Merging a
  stale response's *other* fields into a frame-written record would need
  field-level stamps.
- **Two frames on one channel apply in arrival order.** The transport is ordered
  and there is no server clock to do better with. Frames on two *different*
  channels have no defined order relative to each other, for the same reason.
- **The frame is not claimed right forever** — only that it will not be undone by
  an answer that was already in flight when it landed.

Mutation-tested. Replacing the query path's `racedSince(...)` with `[]` fails

## Gap recovery

**Triggered** by `SubscriptionManager` on a *reopen*, never on a first connect
(`onReconnect` fires only from the `reconnect()` path — there is no gap to
recover from while the query is still loading), and on `repartition()` after an
identity change, which is the same thing from the store's point of view. The
binder claims `manager.onReconnect` in its own constructor so it cannot be left
unwired; the cost is that one manager belongs to one binder, and that is
documented on the class.

**Two halves, because neither subsumes the other:**

1. `cache.invalidate(tags)` over every tag bound to the channel — each binding's
   resolvable `invalidates`, plus `${entity}[]`. This catches a filtered list on
   another screen that holds `Order[]` and no subscription of its own.
2. `cache.refetch(meta, args)` for every registered live query on the channel.
   This catches a **patch-only** channel: `order.updated` correctly declares no
   invalidations, so there is no tag to raise, and the missed patches would stay
   missed for the life of the session.

Invalidation runs first, so a query refetched in step 2 is already marked stale
and `refetchAll` skips it (`inflight !== undefined`) rather than spending a
second request. Asserted: reconnect produces exactly one extra call per query.

**Tested** with an injected `Sleep` (`manualClock`) and a fake socket — no real
timers, no sleeps. `sockets.last().drop(); await clock.advance(1000)` is the
whole outage. Both halves have an isolating test:

- removing the tag invalidation fails *"marks a query the channel's tags reach,
  even though it is not itself live"*
- removing the live-query refetch fails *"refetches a live query no channel tag
  reaches"*

Backoff is exponential with jitter (`random` injected, pinned to 0 in tests), so
the ladder is asserted exactly: 500, 1000, 2000, 4000, 4000 against
`baseDelay: 1000, maxDelay: 8000`. Any traffic resets it. The manager gives up
after `attempts` and reports rather than retrying forever.

## Batching, made deterministic

`StreamBinder` queues decoded frames and schedules **one** flush through an
injected `Scheduler` — the same `(flush) => void` type chunk 2 introduced, with
`manualScheduler()` as the test driver. Default is `animationFrameScheduler`,
falling back to a microtask where there is no `requestAnimationFrame`. No test
touches a real `requestAnimationFrame`.

One flush produces one `applyFrames` call, which takes one frame-clock reading,
one `refresh` pass and at most one `invalidator.invalidate`. The test delivers
200 frames and asserts `pending === 200` with the store untouched, then after
`frames.flush()`: `store.frameVersion` bumped by exactly 1, `total === 200`, and
the subscriber notified exactly once. A second test counts scheduler callbacks —
50 frames, one callback, and a fresh one for the next burst.

Notification is by state-object identity: `snapshot` reuses the previous object
when nothing moved, so only the queries whose rendered value actually changed
are notified. Removing it fails *"patches an entity with no request at all"* —
which is the spec's claim that `order.updated` costs nothing, asserted as one
render, zero requests, and a `customer` subtree that kept its object identity.

## StrictMode

The last release does **not** close the socket. It marks it `closing`, adds it to
a pending set, and schedules one flush; a `subscribe` arriving first clears the
flag and the socket is never closed. Mount → unmount → mount leaves one socket,
open, still delivering to the surviving handler.

The pending set plus a single scheduled callback matters: `manualScheduler` holds
exactly one queued flush, so N independent schedules would lose all but the last
and leak the rest. There is a test for that too.

Mutation-tested: closing immediately at `refs === 0` fails *"leaves a live
subscription after mount, unmount, mount"* and *"does not open a second socket for
the phantom remount"* (5 cycles → 10 sockets instead of 5).

## Principal partitioning

Three independent guards, because the cost of being wrong is one principal's rows
appearing under another's:

- `SubscriptionManager.socketFor` never adopts a socket opened for a different
  principal, and `repartition()` swaps live ones while keeping subscribers.
- `QueryCache.watchPrincipal` fires **after** `clear()`; the binder empties its
  frame queue and repartitions synchronously.
- Every queued frame carries the `cache.owner` it was decoded under, and `flush`
  drops the ones that no longer match.

The test queues a frame, changes principal, flushes, and asserts the entity is
absent, the old socket closed and inert, and the new one working.

## Sizes

```
entity store                     limit 2 kB      1.95 kB
tag graph                        limit 2.2 kB    2.07 kB
query engine and REST transport  limit 6.5 kB    6.35 kB
stream binding                   limit 3.4 kB    3.17 kB
core, REST only                  limit 9 kB      6.39 kB
core with streams                limit 14 kB     8.80 kB
```

**Streams do not push core past 14 kB** — 8.80 kB gzipped, 5.2 kB of headroom.

**REST-only is 6.39 kB against 9 kB**, up from 5.95 kB before this chunk.
Relocating `applyFrames` to a free function recovered 0.19 kB, as the reviewer
measured; stamping `mutate` and filtering holes spent part of that back. The
residue — frame clock, per-record stamps, staged commit, `racedSince` — is
genuinely on the query path and cannot be moved, because `mutate` is stamped
too. It buys the ordering guarantee for the writes an application makes as well
as the ones it reads.

The `stream binding` sub-budget moved 3 → 3.4 kB in the same change, because the
apply logic moved *into* that surface from the query engine. That is a
reallocation, not erosion: the two budgets the design actually sets, 9 kB and
14 kB, are unchanged and both met with room.

## One footgun worth knowing about

Where several channels are multiplexed onto one socket and the envelope carries
no `channel` field, a message name bound on two of those channels applies for
both. The default decoder narrows it when the field is present; a custom
`FrameDecoder` can always supply one. Documented in the README's known gaps.
