## The ordering guarantee

> **A committed response never contains an entity older than a stream frame the
> client has already applied.**

### How it works

Each request records `EntityStore.frameVersion` **at dispatch**, per attempt.
Each batch of frames takes one fresh reading (`nextFrame()`) and stamps every
record it writes with it — `EntityRecord.frameAt`, carried forward by
`Math.max` so a later response merging extra fields cannot erase it. An
eviction leaves a **tombstone** carrying the same stamp, because a deleted
record has nothing left to hold one.

On arrival a response is **normalized but not committed** (`store.stage`). The
entity keys it actually carries are then compared against the store's stamps
(`store.racedSince(keys, dispatchedAt)`). If a frame stamped any of them since
dispatch, the response is discarded and the sequence re-run through the loop
chunk 3 already had for the `restart` path.

### Why this one and not the alternatives

The brief offered two shapes. This is the first — stamping at dispatch and
rejecting older responses — chosen over "treat a frame as an invalidation when a
request is outstanding" for one reason that decides it:

**The invalidation route runs through the tag index, and the tag index holds
mounted queries only.** `registry.invalidated(tags)` reads `this.index`, which
`unlink` empties on the last unmount. So the third of chunk 3's three bugs —
*unmounted, with a request in flight* — is structurally unreachable that way: a
prefetch, an SSR pass, or a component that unmounted while its request was out
has no entry for an invalidation to find. The stamp comparison is against the
response's own contents and the store's own records; mount state is not part of
the question. `frame-ordering.test.ts` asserts this directly with
`registry.mounted === 0`.

It is also more precise in both directions. A frame touching `Order:9` does not
restart a response carrying only `Order:7`, which a tag-shaped fix over `Order[]`
would. And it catches a response carrying an entity that no query's tag set
mentions at all.

Both mechanisms are live, and they are complementary rather than redundant: a
frame's *declared* `invalidates` still goes through `Invalidator.apply`, exactly
as a mutation's does. An `upsert` declaring `Order[]` still restarts a mounted
list's in-flight refetch through chunk 3's `stale()` hook — membership moved, and
the stamp comparison would not have noticed because the pre-create response is
not *wrong* about any entity it carries, only incomplete. Both cases have a test.

### Convergence, and the bound

One re-run per frame, not a retry loop. The re-run is dispatched *after* the
frame, so it carries a stamp the frame cannot be newer than, and it commits
whatever it returns — including the same stale body it was just rejected for, if
the server is genuinely lagging. There is a test that asserts exactly that,
because it is the difference between a guarantee and a spin.

Unbounded, though, it livelocks: a channel busy enough that a frame lands inside
*every* request window restarts the sequence forever, and a query that never
settles is worse than the defect avoided. `frameRestarts` (3 by default) caps it.
Past the bound the response **commits with the overtaken entity keys skipped** —
the store already had `commit(staged, {skip})` from the same split — so the
frame's value stands for those records, everything else the response carried
lands normally, and nothing visibly reverts.

### What is deliberately not claimed

- **Per entity, not per field.** A rejected response is rejected whole; past the
  bound it is skipped whole for the raced keys. Merging a stale response's
  *other* fields into a frame-written record would need field-level stamps.
- **Two frames on one channel apply in arrival order.** The transport is ordered
  and there is no server clock to do better with. Frames on two *different*
  channels have no defined order relative to each other, for the same reason.
- **The frame is not claimed right forever** — only that it will not be undone by
  an answer that was already in flight when it landed.

### Demonstration, not just passing

Mutation-tested. Replacing `racedSince(...)` with `[]` fails five tests:

```
× is not overwritten by the response that predates it
× converges in exactly one re-run, because the re-run postdates the frame
× holds for an unmounted query, which no tag index can reach
× does not resurrect it through a query the delete's tags cannot reach
× commits around the frames rather than looping, once the restart bound is spent
```

The first test records every value a subscriber could have rendered `Order:7` at
and asserts the pre-frame value never appears among them — not merely that the
final state is right.

## Gap recovery

**Triggered** by `SubscriptionManager` on a *reopen*, never on a first connect
(`onReconnect` fires only from the `reconnect()` path — there is no gap to
recover from while the query is still loading), and on `repartition()` after an
identity change, which is the same thing from the store's point of view. The
binder claims `manager.onReconnect` in its own constructor so it cannot be left
unwired; the cost is that one manager belongs to one binder, and that is
documented on the class.

**Two halves, because neither subsumes the other:**

1. `cache.invalidate(tags)` over every tag bound to the channel — each binding's
   resolvable `invalidates`, plus `${entity}[]`. This catches a filtered list on
   another screen that holds `Order[]` and no subscription of its own.
2. `cache.refetch(meta, args)` for every registered live query on the channel.
   This catches a **patch-only** channel: `order.updated` correctly declares no
   invalidations, so there is no tag to raise, and the missed patches would stay
   missed for the life of the session.

Invalidation runs first, so a query refetched in step 2 is already marked stale
and `refetchAll` skips it (`inflight !== undefined`) rather than spending a
second request. Asserted: reconnect produces exactly one extra call per query.

**Tested** with an injected `Sleep` (`manualClock`) and a fake socket — no real
timers, no sleeps. `sockets.last().drop(); await clock.advance(1000)` is the
whole outage. Both halves have an isolating test:

- removing the tag invalidation fails *"marks a query the channel's tags reach,
  even though it is not itself live"*
- removing the live-query refetch fails *"refetches a live query no channel tag
  reaches"*

Backoff is exponential with jitter (`random` injected, pinned to 0 in tests), so
the ladder is asserted exactly: 500, 1000, 2000, 4000, 4000 against
`baseDelay: 1000, maxDelay: 8000`. Any traffic resets it. The manager gives up
after `attempts` and reports rather than retrying forever.

## Batching, made deterministic

`StreamBinder` queues decoded frames and schedules **one** flush through an
injected `Scheduler` — the same `(flush) => void` type chunk 2 introduced, with
`manualScheduler()` as the test driver. Default is `animationFrameScheduler`,
falling back to a microtask where there is no `requestAnimationFrame`. No test
touches a real `requestAnimationFrame`.

One flush produces one `applyFrames` call, which takes one frame-clock reading,
one `refresh` pass and at most one `invalidator.invalidate`. The test delivers
200 frames and asserts `pending === 200` with the store untouched, then after
`frames.flush()`: `store.frameVersion` bumped by exactly 1, `total === 200`, and
the subscriber notified exactly once. A second test counts scheduler callbacks —
50 frames, one callback, and a fresh one for the next burst.

Notification is by state-object identity: `snapshot` reuses the previous object
when nothing moved, so only the queries whose rendered value actually changed
are notified. Removing it fails *"patches an entity with no request at all"* —
which is the spec's claim that `order.updated` costs nothing, asserted as one
render, zero requests, and a `customer` subtree that kept its object identity.

## StrictMode

The last release does **not** close the socket. It marks it `closing`, adds it to
a pending set, and schedules one flush; a `subscribe` arriving first clears the
flag and the socket is never closed. Mount → unmount → mount leaves one socket,
open, still delivering to the surviving handler.

The pending set plus a single scheduled callback matters: `manualScheduler` holds
exactly one queued flush, so N independent schedules would lose all but the last
and leak the rest. There is a test for that too.

Mutation-tested: closing immediately at `refs === 0` fails *"leaves a live
subscription after mount, unmount, mount"* and *"does not open a second socket for
the phantom remount"* (5 cycles → 10 sockets instead of 5).

## Principal partitioning

Three independent guards, because the cost of being wrong is one principal's rows
appearing under another's:

- `SubscriptionManager.socketFor` never adopts a socket opened for a different
  principal, and `repartition()` swaps live ones while keeping subscribers.
- `QueryCache.watchPrincipal` fires **after** `clear()`; the binder empties its
  frame queue and repartitions synchronously.
- Every queued frame carries the `cache.owner` it was decoded under, and `flush`
  drops the ones that no longer match.

The test queues a frame, changes principal, flushes, and asserts the entity is
absent, the old socket closed and inert, and the new one working.

## Sizes

```
entity store                     limit 2 kB      1.85 kB
tag graph                        limit 2.2 kB    2.07 kB
query engine and REST transport  limit 6.5 kB    6.4  kB
stream binding                   limit 3 kB      2.77 kB
core, REST only                  limit 9 kB      6.45 kB
core with streams                limit 14 kB     8.46 kB
```

**Streams do not push core past 14 kB** — 8.46 kB gzipped, 5.5 kB of headroom.

Reported plainly: **REST-only went from 5.95 kB to 6.45 kB.** `applyFrames`, the
frame stamps and the staged-commit split live on `QueryCache` and `EntityStore`,
which a REST-only importer pulls in whole, so they cannot be tree-shaken away.
That is what the frame apply being the *same* code path as the mutation apply
costs someone who never opens a socket. It is paid inside a 9 kB budget with
2.5 kB left, and the alternative — a parallel applier that tree-shakes — is the
two-code-paths defect the brief specifically ruled out.

  the mechanism and is ref-counted per query; surfacing it belongs with the
  adapter, on a binder that has run.

  adapter is the same four-line object literal as the WebSocket one — but none
  is written or tested here.
- Devtools.

## One footgun worth knowing about

Where several channels are multiplexed onto one socket and the envelope carries
no `channel` field, a message name bound on two of those channels applies for
both. The default decoder narrows it when the field is present; a custom
`FrameDecoder` can always supply one. Documented in the README's known gaps.
