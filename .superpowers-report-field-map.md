# Entity field map: nested entities now normalize

## What shipped

`internal/client.EntityRef` gained `Fields map[string]string` — JSON property
name to the typename of what that property contains, the ELEMENT typename for
arrays. It is populated by a pass over the finished spec and emitted into
`ops.ts`, which closes the gap the client-core README named: the runtime was
already written to walk `schema[type].fields` and the generator never gave it
one, so a `Customer` nested in an `Order` stayed inline.

## Where the shared pass lives, and how both builders call it

`internal/client/entity_fields.go`, one file, one exported-to-the-package
function:

    func resolveEntityFields(spec *APISpec)

Called from exactly two places, both at the end of intermediate-representation
construction, once every entity is known:

- `Introspector.Introspect` (`internal/client/introspector.go`), immediately
  before `return spec, nil` — the live-router path.
- `SpecParser.ParseFile` (`internal/client/spec_parser.go`), immediately after
  the openapi/asyncapi switch — the file path, covering both document kinds
  with one call.

It has to be a post-pass rather than part of `InferEntity`. `InferEntity` is
handed one schema and cannot resolve a `$ref`; and the entity set is not
complete until every endpoint and every stream binding has been resolved, so
the edge `Order.customer -> Customer` is only knowable once both types are in
`spec.Entities` and `spec.Schemas` is whole. `TestParseFileWiresEntityFields`
and `TestIntrospectWiresEntityFields` assert the same edge from the two paths;
a fixture whose `Customer` is registered by a *different* operation than the
one registering `Order` is what makes the ordering requirement bite.

The function is idempotent (`Fields` is replaced, never merged), so running it
twice — or after a future filter pass — is safe.

## Ref shapes handled

`namedSchemaTarget` resolves a property to at most one component name:

1. **Direct `$ref`.** How this repo's own OpenAPI generator emits a nested
   struct field (verified against `internal/router/testdata/openapi.json`:
   `goldenOrder.address -> goldenAddress`).
2. **`$ref` with `nullable: true`.** Falls out of (1) — the ref still names its
   target — which is the OpenAPI 3.0 spelling of an optional reference.
3. **Array whose items resolve to a name**, including nested arrays. The
   ELEMENT name is recorded, never an array marker: `[]LineItem` records
   `LineItem`, because the runtime carries a typename through an array
   unchanged. Present in the golden document as
   `goldenPage_goldenWorkspace.items`.
4. **`oneOf` / `anyOf` / `allOf` naming exactly one type**, with `type: "null"`
   members ignored — the OpenAPI 3.1 spelling of a nullable reference.

   I checked rather than assumed: **nothing in `internal/router` or
   `internal/shared` ever assigns `OneOf`, `AnyOf` or `AllOf`**, so Forge's own
   generator never produces this shape. It is handled anyway because
   `SpecParser` accepts arbitrary third-party OpenAPI documents, `convertSchema`
   already preserves the keywords, and the package has a live test fixture for
   the idiom (`generators/typescript/yaml_ref_oneof_e2e_test.go`).

A wrapper naming two different types, or holding one unnamed member, resolves
to nothing — the same refuse-on-ambiguity rule `InferEntity` applies to two
identity-shaped fields, for the same reason: picking one of two candidate
typenames files records under another type's keyspace.

An inline object resolves to nothing: a cache key needs a stable typename and
an anonymous struct has none.

A depth bound (16) guards a hand-built `APISpec` whose schemas point at each
other. No parser can produce one — both `convertSchema` implementations build a
finite tree from decoded JSON — but nothing in the type system stops an
in-memory builder, and without the bound that input is a stack overflow rather
than a refusal.

## Decision: properties typed by a named NON-entity

**No edge is recorded.** An edge is only recorded when its target is itself in
`spec.Entities`.

The reasoning is the runtime's, not aesthetics. `walkObject` does exactly one
thing with a typename: `schema[type]`. For a type with no table entry that
yields `undefined`, so the walk descends with no metadata and normalizes
nothing — the identical outcome to having no edge. Emitting it would put bytes
into a file CI byte-diffs in exchange for nothing.

Tested from three angles: `TestResolveEntityFieldsSkipsNonEntityNamedTypes`
(an enum target), `TestResolveEntityFieldsSkipsInlineObjects`, and the
end-to-end `TestGenerateFromSpecFileEmitsEntityFieldMap`, which asserts
`OrderStatus` appears nowhere in `ops.ts`.

The price is case (b) below, and it is real.

## Determinism

`fields` keys are sorted in `tsFieldMap`; typenames were already sorted.
Covered by `TestOpsManifestFieldMapIsDeterministic` (50 regenerations,
byte-compared) and `TestGenerateFromSpecFileEntityFieldMapIsDeterministic`
(20 full generations from a file on disk).

## Both halves of the proof

- Go: `internal/client/generators/typescript/e2e_entity_fields_test.go` drives
  a real OpenAPI file on disk through `SpecParser.ParseFile` into
  `Generator.Generate` and asserts the emitted `ops.ts` carries
  `Order: { idField: 'id', fields: { customer: 'Customer', items: 'LineItem', parent: 'Order' } }`.
- TypeScript: `packages/client-core/__tests__/generated-fields.test.ts` holds
  that table **copied verbatim from the generated output** and asserts
  `Customer:c-3` reaches the store, that an array edge lifts every `LineItem`,
  that the `Customer -> Order` back edge recurses, that a property with no edge
  stays inline by reference, and that a later `put` on the nested record shows
  through the order's skeleton.

Either half alone proves nothing: Go can emit a map the runtime does not read,
and the runtime can read a map Go does not emit.

# (a) Envelopes — investigated, NOT implemented

## What is actually true today (measured, not assumed)

I generated a client for `GET /orders -> {$ref: PageOrder}` where
`PageOrder = {items: [$ref Order], total: int}`. The result:

    'orders.list': {
      method: 'GET',
      path: '/orders',
      provides: [],
      invalidates: [],
    },

**The operation has no `entity` at all.** The situation is worse than the task
brief's framing of "passing `ops.X.entity` as `rootType` would look up the
wrong field". `endpointEntity` calls `InferEntity` on the response's root
schema; `PageOrder` has no identity-shaped property, so it is not an entity,
and the endpoint drops out of the cache entirely — no root type, no entity, no
tags, no invalidation. Only a *bare* top-level array is unwrapped
(`successResponseSchema` handles `{type: array, items: $ref}`); an object
wrapper is not looked through.

## What closing it requires

**Go side**

1. **An envelope policy.** Something must decide which property of the envelope
   carries the payload. Two candidates: an explicit `x-forge-envelope: {field:
   "items"}` extension, or a rule — "the single array-valued property whose
   element type is an entity" — refusing when two properties qualify, matching
   this package's existing style. This is a design decision, not a mechanical
   one, and it is the reason (a) is not a free ride on the field map.
2. **`Endpoint` gains a root typename** (`RootType string`), distinct from
   `Entity.Type`. `Entity.Type` names what the operation's *cache tags* are
   about; the root type names what the *response* is. For an enveloped list
   they differ (`Order` vs `PageOrder`); today one field is doing both jobs.
3. **`endpointEntity` must see through the envelope** to set
   `ep.Entity = Order` and `isList = true`, or `orders.list` still contributes
   no `provides`/`invalidates` and never participates in invalidation.
4. **Envelope types must be put into the table** (`spec.Entities`, or a
   parallel map merged at emit time) with `Fields` populated and no `IDField`.
   `resolveEntityFields` needs almost nothing here — it already computes edges
   for every type in the table; its one filter, "target must be an entity",
   relaxes to "target must be in the table".
5. **`writeOps` emits `rootType`** and `OperationMeta` declares
   `readonly rootType?: string`. **`writeEntities` emits an entry with no
   `idField`.**

**TypeScript side (runtime change required)**

6. `EntityMeta.idField` becomes optional: `readonly idField?: string`.
7. `normalize.ts:69` —
   `const id = meta === undefined ? undefined : node[meta.idField];` — stops
   compiling, because a `Record<string, unknown>` cannot be indexed by
   `string | undefined`. It becomes
   `meta?.idField === undefined ? undefined : node[meta.idField]`.
   That line is the **only** reader of `idField` in `packages/client-core/src`
   (grepped). Everything downstream already handles "metadata present, no key":
   `walkObject` descends using `meta.fields` and returns a plain rewritten
   object.
8. Call sites pass `ops.X.rootType ?? ops.X.entity` instead of
   `ops.X.entity` — including the README's example.

**The workaround that needs no runtime change**, for completeness: give the
envelope an `idField` no payload ever carries (`'__never'`). It works today —
`packages/client-core/__tests__/schema.ts` already exercises exactly this — but
it is a landmine, because a payload that happens to carry that property
silently becomes an entity keyed on it. I would not ship it.

**Also worth scheduling with it:** `diff.go`'s `diffSpecEntities` compares only
`Type` and `IDField`. Once envelope types are in the table, removing one is
reported as `ChangeBreakingCache` ("a persisted store still holding X: keys
cannot reach them") which is false for a type that was never keyed. And a
`Fields` change — an edge added or removed — is invisible to the diff today
regardless; that is a gap the current change introduces and does not close.

# (b) Intermediate non-entity types — investigated, NOT implemented

`Order -> Shipment` (no identity field, so not an entity) `-> Carrier` (an
entity). Confirmed against a generated client: `Order` gets no `fields` entry
for `shipment`, so `Carrier` is unreachable no matter what `Carrier`'s own
entry says.

## What closing it requires

**Go side**

1. `resolveEntityFields` becomes transitive. Starting from each entity, follow
   property refs into named non-entity object types and register those in the
   table too, recursively.
2. **Retain only intermediates from which an entity is reachable.** Without
   that filter every value struct in the API lands in the manifest — pure bloat
   in a byte-diffed file. This is a reachability computation over the component
   graph, needing a visited set, because component graphs cycle.
3. Retained intermediates are stored with `Fields` and no `IDField`, and the
   "target must be an entity" filter relaxes to "target must be in the table" —
   the same one-line relaxation (a) needs.

**TypeScript side**

Identical to (a) items 6 and 7, and nothing else. No new manifest field: (b)
needs no per-operation root type, because the root of the response is still the
operation's entity.

## Is either subsumed by the mechanism just built?

Partly, and not enough to fold in. Both reduce to "put more types in the table"
plus one shared runtime relaxation (`idField` optional, one guarded line in
`normalize.ts`), and `resolveEntityFields` already computes edges for whatever
is in the table. But (a) additionally needs an envelope *policy* decision and a
new per-operation `rootType` in both `Endpoint` and `OperationMeta`, and both
need `EntityMeta` to change shape — a published-runtime change coordinated with
a generator change. So: reported, not implemented, per instruction.

Sequencing note if you schedule them: do the `EntityMeta.idField` relaxation
once, as its own change, then (b) — which needs only that — then (a), which
needs the policy decision on top.
