# Chunk 6 — Vue and Angular adapters

Two packages, siblings of `client-react`, written against a core that had already
shipped and run. Nothing in the core was changed. Both adapters are bindings and
nothing else: no invalidation logic, no identity logic, no staleness logic.

| | React (baseline) | Vue | Angular |
|---|---|---|---|
| gzipped, whole adapter | 751 B | **825 B** | **908 B** |
| gzipped, one entry point | 319 B (`useQuery`) | 431 B (`useQuery`) | 498 B (`injectQuery`) |
| budget | 2 kB | 2 kB | 2 kB |
| src lines (incl. comment) | 440 | 458 | 480 |
| tests | 27 | 30 | 29 |

Both are comfortably inside the 2 kB per-adapter budget. The two frameworks cost
74 B and 157 B over React respectively, and the money went to exactly two places:
resolving reactive arguments (`toValue` / a getter check plus a derived key) and
the four per-field `computed`s each returns, which React does not need because a
React hook returns one plain object per render. The Angular figure additionally
carries `runInInjectionContext` for the `{injector}` escape hatch and the
`untracked` wrapper described below. Neither framework imposed a structural cost;
the core's surface is what both bind to, unchanged.

## How identity was kept alive in each framework

### Vue: `shallowRef`, and that is the whole story

`ref(state)` hands back `reactive(state)` — recursively. `data.value` would be a
proxy of the array, `data.value[0]` a proxy of the entity, and none of them the
objects the entity store holds. The identity three chunks were built to preserve
would survive inside the cache and be destroyed on the way out of it. It would
also make the cache's objects writable through the proxy, turning a stray
`order.total = 0` in a template into a silent mutation of shared state that no
subscriber is notified about.

So the snapshot lives in a `shallowRef`, assigned whole and never merged,
spread or mapped. Assigning the *same* object into a `shallowRef` is a no-op —
Vue compares with `Object.is` — so a notification that changed nothing produces
no re-render at all, which is exactly the granularity the cache publishes at.
The four public fields are `computed`s over that ref, so each notifies only when
its own field's identity moves: a refetch returning an equal `data` moves
`isFetching` twice and `data` not at all.

The re-subscription watches a `computed` **cache key**, not the arguments
object. A getter spelt `() => ({path: {id: id.value}})` mints a fresh literal on
every evaluation; watching it would tear the subscription down and put it back
on every unrelated tick, and against a ref-counted cache each cycle drops the
query's mount count to zero, unlinks it from the tag index, and makes a query
that is on screen a candidate for LRU eviction.

Lifetime is `onScopeDispose`, not `onUnmounted`, so a query created inside a bare
`effectScope()` — a store, a route guard, a plugin — is released when *that*
scope stops. Called with no scope at all, Vue emits its own development warning,
which is correct, and `dispose()` is the escape hatch. `useMutation` guards that
registration because a mutation outside a scope holds nothing and the warning
would be noise.

### Angular: signals hold what they are given; the danger is the binding

Angular does not rewrite values. A signal holds the object it is handed, and its
default equality is `Object.is`, so the core's "same object when nothing moved"
maps onto Angular's change detection directly: setting an identical snapshot
notifies nobody, and an `OnPush` child whose `[order]` did not move is never
checked.

The hazard is therefore the binding itself. One `{...state()}` in a `computed`,
one `.map` on the way to a template, and every read mints a new object — and
because equality is `Object.is`, such a `computed` is *never equal to itself*, so
it does not merely waste a copy: it marks its consumers dirty on every change
detection, permanently. Nothing in `injectQuery.ts` or `injectMutation.ts`
copies; `state` is `state.asReadonly()` and each field is a plain
`computed(() => state().field)`.

Reactive arguments re-subscribe through an `effect` over the derived cache key,
for the same reason as Vue. Two details are load-bearing:

- The effect exists **only when `args` is a function**. A plain object cannot
  change, so for the majority of queries in an application there is no effect to
  schedule on every change detection.
- Its signal writes run inside `untracked`. Angular before 19 rejects a signal
  write during an effect's tracked execution outright (`NG0600`), and the
  `allowSignalWrites` option that used to permit it has since been removed from
  the effect signature. `untracked` clears the active consumer, which makes one
  binding correct across 17 → 22 without a version-conditional option.

Teardown is `DestroyRef`, so the lifetime is the injection context's — a
component, a lazy route's injector, a service, or one built by hand — rather
than a component's `ngOnDestroy`, which would only ever cover the first.

Naming: `injectQuery` / `injectMutation`, because `inject*` is what Angular calls
a function that must run in an injection context, and both do (they resolve the
cache and the `DestroyRef` from the injector). Angular 19's `resource()` was the
other candidate shape and was rejected on substance rather than taste: a
`resource` owns its request and re-runs a loader when its params change, and this
owns nothing — request, cache entry, tag graph and invalidation all belong to the
core, and the query is *shared* with every other caller asking the same question.
Wearing a `resource`'s clothes would advertise a lifecycle this does not have.

## The identity tests, and how they were proved to discriminate

The instruction that mattered most: a test that passes under the wrong
implementation proves nothing. Both suites were checked by breaking the
implementation and watching them fail.

### Vue — `packages/client-vue/__tests__/identity.test.ts`

The trap is real and would have caught a naive suite. **Vue memoises one proxy
per raw target in a `WeakMap`**, so `reactive(x) === reactive(x)`, and the
obvious test — "the same object across two reads with no writes between" —
passes under `shallowRef` *and* under `ref`. It is in the file, labelled as
proving nothing on its own.

The assertions that do the work compare what the component reads against what the
cache **holds**, or ask Vue directly whether it has wrapped anything:

- `expect(seen.state.value).toBe(cache.getState(orderList))` — the snapshot
- `expect(seen.data.value).toBe(held.data)` — the array
- `expect(seen.data.value?.[0]).toBe(held.data?.[0])` — the entity
- `expect(isReactive(...)).toBe(false)` at all three levels
- `expect(toRaw(v)).toBe(v)`

Verification: `shallowRef` was replaced with `ref` in `src/useQuery.ts` and the
suite re-run. **4 of 5 failed** —

```
× hands the component the object the cache holds, not a proxy of it
× keeps a sibling entity identical when its neighbour changes
× leaves a mutation result unwrapped too
× returns refs, so a caller can watch a field without unwrapping a snapshot
```

The fifth — "does not re-render a child whose entity did not change" — passes
under both, and the file says so in a comment. That is the proxy memoisation
again: `props.order` is a stable proxy of a stable target, so the child skips
either way. It stays because it states what the identity is *for*; the four above
it are what pin the mechanism down.

That test is also careful in a way worth recording: the child has a single object
prop and **no slot children**. Vue's `shouldUpdateComponent` force-updates a child
of a hand-written render function when it has children, and only falls through to
the shallow prop comparison when it has none. A version with children would have
passed for the wrong reason.

### Angular — `packages/client-angular/__tests__/identity.test.ts`

Same shape, different failure mode. The assertions compare against
`cache.getState(...).data` at both the element and the container level, and
across two reads.

Verification, twice:

- `state: state.asReadonly()` → `computed(() => ({...state()}))`: the first test
  fails on `expect(seen.state()).toBe(held)`.
- `data: computed(() => state().data)` → a `computed` that shallow-copies arrays
  and objects: **4 of 5 fail**, including the mutation-result test and the
  "derived signal does not notify" test.

The fifth is the child-check test again, and again for a defensible reason: a
shallow copy of the array leaves the *elements* identical, so `@for (… track
order.id)` still hands each `OnPush` row the same object. The container-level
assertion added to two other tests (`expect(after).toBe(cache.getState().data)`)
is what catches that class of mistake.

Both suites use real framework test setups: `@vue/test-utils` with `mount` and
`flushPromises`, and Angular's `TestBed` with real components, `OnPush`, and
zoneless change detection. No sleeps anywhere: the fake transport resolves on the
microtask queue, and the tests drain it and then apply change detection.

## Lifecycle coverage, per adapter

Both suites cover, in the framework's own terms:

- renders a value, and updates when an entity it depends on changes;
- a consumer reading an unchanged sibling entity is not re-rendered / re-checked;
- two consumers of one query are one cache entry, one registry mount and one
  request;
- teardown releases the subscription, on the *last* consumer only;
- teardown outside a component — a bare `effectScope()` in Vue, a
  `createEnvironmentInjector(...).destroy()` in Angular;
- release is idempotent: `dispose()`/`destroy()` twice plus a scope stop leaves
  the mount count at zero, not negative;
- a mutation updates the queries the write invalidated;
- an argument change re-subscribes to the new query and releases the old;
- ten unrelated re-renders churn nothing: same snapshot object, same mount count,
  one request;
- a mutation's result does not publish into a scope/context that has already
  been destroyed;
- `mutate` resolves and raises no `unhandledrejection` from the documented
  handler; `mutateAsync` throws.

## `mutate` resolves, `mutateAsync` throws — kept in both

The React adapter's split was adopted unchanged, and the check was not a formality:
in each framework the question is whether the framework has an error channel that
would *see* a rejected promise returned from an event handler, which would make
rejecting the safer default rather than the noisier one.

- **Vue**: `app.config.errorHandler` receives render, watcher and lifecycle
  errors. A promise returned from a template `@click` is none of those, so the
  rejection would be nobody's.
- **Angular**: `ErrorHandler` receives errors thrown *through* Angular — a
  template expression, a lifecycle hook, an effect. A rejected promise returned
  from an event binding is not one, so again the rejection would be nobody's.

Neither framework argues the other way, so both keep React's split and its
reasoning: the spelling a caller copies out of the README must be the one that
cannot misbehave.

## Where the core was not quite framework-agnostic enough

**No core change was needed, and none was made.** `subscribe`, `getState`,
`fetch`, `refetch`, `mutate` and `key(meta, args)` were sufficient for both
adapters, and `QueryBinding.meta` gave both their re-subscription key without a
new API. Two observations, one of them material.

### 1. The core assumes a consumer that re-reads, and Vue/Angular do not (material)

`QueryCache.mutate` calls `this.refresh(false)` before invalidating — it
recomputes every tracked query's memoised state **without notifying anybody**.
The intent is visible and reasonable: placement callbacks must see fresh values.
The consequence is not.

For a query whose entities the write committed but whose tags the operation did
not declare, the new value is now sitting in the cache and **no subscriber will
ever be told about it**. Worse, because `refresh(false)` has already advanced
`record.state`, a subsequent `notifyChanged()` — the core's own documented seam
for "something wrote to the store" — compares `before !== after`, finds them
equal, and cannot recover the change either.

This is invisible under React and visible under both new adapters, which is
precisely the shape of a framework-agnosticism gap:

- React's `useSyncExternalStore` calls `getSnapshot` **during every render**, so
  any unrelated re-render surfaces the value. In practice a mutation re-renders
  the component that fired it, so it usually self-heals.
- Vue's `shallowRef` and Angular's signal hold the last *notified* snapshot.
  A change that is never notified never appears, however many times the component
  renders.

It was found by a test that assumed the propagation worked (a detail query on
`Order:9`, a create that returns `Order:9`), reproduced against the core alone
with no adapter involved, and then designed around rather than patched: the tag
graph is the declared path and covers the normal case, and changing `mutate`'s
notification semantics is a core decision, not an adapter's. Both READMEs record
it under "what it does not do yet". **The one-line candidate fix is
`this.refresh(false)` → `this.refresh(true)` in `QueryCache.mutate`**; it belongs
to whoever owns the core's mutation semantics, with the placement ordering
re-examined at the same time.

### 2. `getState()` opens a record as a side effect (already known)

Both adapters build a handle and read it once at construction, which creates the
cache record before anything subscribes — the same wrinkle the React chunk
documented, with the same bounded cost (one empty record, zero requests, a
possible LRU eviction of something nobody is watching). The clean fix is still a
read-only `peek` on the cache, and it is still a core API addition rather than
anything an adapter can do. Neither new adapter makes it worse: Vue and Angular
construct the handle **once** per binding rather than per render, so if anything
they touch it less than React does.

Nothing else leaked. The core has no framework import, and neither adapter needed
to reach past the published surface — `cache.registry` is touched only by tests,
asserting mount counts.

## Test infrastructure notes

- **Vue**: `@vue/test-utils` with `enableAutoUnmount(afterEach)`, components
  written as render functions with `h()` rather than templates — no runtime
  template compiler, no feature-flag warnings, and the child-skip test needs
  hand-written render functions to be meaningful anyway.
- **Angular**: `TestBed` with `provideZonelessChangeDetection()`. Zone.js is not
  installed: change detection driven by the signals this adapter writes is what
  is under test, and a zone patching every promise in the process would hide a
  missing notification behind a tick that happened for an unrelated reason.
  Components are compiled JIT (`import '@angular/compiler'` in the setup file),
  which required telling vitest's oxc transform that Angular's decorators are the
  legacy kind — vitest 4 uses oxc, not esbuild, and silently ignores an `esbuild`
  block. One consequence worth knowing: **signal inputs (`input()`) are AOT-only**
  — the compiler discovers them by reading the class body — so the test
  components use `@Input()`. The change-detection semantics under test are
  identical.
- The library itself builds with plain `tsc` in both packages. The Angular
  package contains no components, no templates and no decorators, so it needs no
  ngc build: `InjectionToken` and `inject()` are ordinary JavaScript.
